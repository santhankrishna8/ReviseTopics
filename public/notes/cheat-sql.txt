# 01 | SQL Cheat Sheet | Concepts on one page: what each SQL feature is, when to use it, how the alternatives compare, and only the tricky queries | SQL on one page

## SQL & Relational Databases
> **What:** **SQL** (Structured Query Language) is the declarative language for relational databases: you say what data you want, the optimiser decides how to get it.
- **RDBMS**: data in **tables** (rows + columns) linked by **keys**, with constraints and ACID transactions: PostgreSQL, MySQL, SQL Server, Oracle, SQLite.
- **SQL vs NoSQL**: SQL = fixed schema, joins, strong consistency, complex queries; NoSQL (MongoDB, Redis, Cassandra) = flexible schema, easy horizontal scaling, simpler access patterns.

## SQL Sub-Languages
- **DDL** (structure): `CREATE`, `ALTER`, `DROP`, `TRUNCATE`.
- **DML** (rows): `INSERT`, `UPDATE`, `DELETE`, `MERGE`. **DQL**: `SELECT`.
- **DCL** (permissions): `GRANT`, `REVOKE`. **TCL** (transactions): `BEGIN`, `COMMIT`, `ROLLBACK`, `SAVEPOINT`.

## Logical Execution Order
```text
FROM / JOIN -> WHERE -> GROUP BY -> HAVING -> SELECT
-> DISTINCT -> ORDER BY -> LIMIT
```
- That is why a `SELECT` alias can't be used in `WHERE`, aggregates can't go in `WHERE` (use `HAVING`), and window functions must be wrapped in a subquery/CTE to filter on them. `ORDER BY` can use aliases.

## Keys & Constraints
- **Primary key**: uniquely identifies a row; unique + NOT NULL; one per table (may be composite).
- **Foreign key**: references another table's key; enforces referential integrity; actions `ON DELETE CASCADE / SET NULL / RESTRICT`.
- **Unique**: no duplicates but allows NULLs; many per table. **NOT NULL**, **CHECK** (`price >= 0`), **DEFAULT**.
- **Candidate key**: any minimal unique column set; **surrogate** key (auto id/UUID) vs **natural** key (email).
- Auto-increment: `GENERATED AS IDENTITY` (PostgreSQL/Oracle), `AUTO_INCREMENT` (MySQL), `IDENTITY(1,1)` (SQL Server).

## Data Type Choices
- `CHAR(n)` fixed length (padded) vs `VARCHAR(n)` variable length vs `TEXT` unlimited.
- `DECIMAL/NUMERIC(p,s)` exact (money) vs `FLOAT/DOUBLE` approximate (science). Never store money in float.
- `DATE`, `TIME`, `TIMESTAMP` (no zone) vs `TIMESTAMPTZ` (stored as UTC); `BOOLEAN`; `JSON/JSONB`; `UUID`.

## DELETE vs TRUNCATE vs DROP
```text
           DELETE         TRUNCATE         DROP
removes    chosen rows    all rows         the table itself
WHERE      yes            no               no
speed      slow (logged)  fast             fast
triggers   fire           don't fire       -
rollback   yes            PG/SQL Server    no (MySQL/Oracle
                          only             auto-commit DDL)
identity   continues      resets           gone
```

## NULL & Three-Valued Logic
> **What:** `NULL` means *unknown/missing*. Any comparison with NULL is **UNKNOWN** (not true, not false); `WHERE` keeps only TRUE rows.
- Test with `IS NULL` / `IS NOT NULL`; replace with `COALESCE(x, default)`; `NULLIF(a, b)` returns NULL when equal (avoids divide-by-zero).
- Aggregates ignore NULLs; `NULL + 1` is NULL; `'a' || NULL` is NULL.
```sql
SELECT name FROM employees WHERE email = NULL;   -- 0 rows, always
SELECT name FROM employees WHERE email IS NULL;  -- Arjun
SELECT name FROM employees WHERE dept_id <> 1;   -- skips Arjun (NULL dept)!
SELECT name FROM customers WHERE customer_id NOT IN (SELECT NULL::INT);  -- 0 rows
```

## WHERE vs HAVING
- **WHERE** filters **rows before** grouping; can't use aggregates.
- **HAVING** filters **groups after** `GROUP BY`; can use `COUNT`, `SUM`...
- Put conditions in WHERE whenever possible: fewer rows to group = faster.

## Aggregate Functions
- `COUNT`, `SUM`, `AVG`, `MIN`, `MAX`, `STRING_AGG`/`GROUP_CONCAT`/`LISTAGG`.
- `COUNT(*)` counts rows · `COUNT(col)` counts non-NULL values · `COUNT(DISTINCT col)` counts unique non-NULL values.
- `SUM` over zero rows returns **NULL**, not 0 (use `COALESCE`).
- `GROUP BY` rule: every selected column must be grouped or aggregated. `ROLLUP`/`CUBE` add subtotal rows.

## Joins
```text
INNER JOIN   only matching rows from both
LEFT JOIN    all left rows + matches (else NULLs)
RIGHT JOIN   all right rows + matches
FULL JOIN    all rows from both sides
CROSS JOIN   every combination (cartesian product)
SELF JOIN    a table joined to itself (manager/employee)
```
- **Anti-join** (rows with no match): `LEFT JOIN ... WHERE right.id IS NULL` or `NOT EXISTS`. **Semi-join** (has a match): `EXISTS` / `IN`.
- **Join vs subquery**: joins combine columns from both tables; subqueries filter or compute values. Optimisers often produce the same plan.

## LEFT JOIN Trap: ON vs WHERE
```sql
SELECT c.name, o.order_id FROM customers c
LEFT JOIN orders o ON o.customer_id = c.customer_id AND o.status = 'placed';
-- keeps every customer: Anil 106, Bina 105, Chetan NULL, Divya NULL

SELECT c.name, o.order_id FROM customers c
LEFT JOIN orders o ON o.customer_id = c.customer_id
WHERE o.status = 'placed';
-- Anil 106, Bina 105: the WHERE removed the NULL rows = an INNER join
```
- Filter the **right** table of a LEFT JOIN in `ON`, not `WHERE`.

## Set Operations
- `UNION`: combine results and **remove duplicates** (extra sort/hash). `UNION ALL`: keep everything (faster).
- `INTERSECT`: rows in both. `EXCEPT` (Oracle `MINUS`): rows in the first but not the second.
- Same number of columns, compatible types; column names come from the first query.

## Subqueries
> **What:** a query inside another query.
- **Scalar** (one value): `WHERE salary > (SELECT AVG(salary) FROM employees)`.
- **Multi-row**: with `IN`, `ANY`, `ALL`. **Derived table**: a subquery in `FROM` (needs an alias).
- **Correlated**: references the outer row, so it logically runs once per row (e.g. "earns more than their department's average").
- **EXISTS vs IN**: `EXISTS` stops at the first match and is NULL-safe; `NOT IN` returns nothing if the subquery has a NULL, so prefer `NOT EXISTS`.

## CTE (WITH clause)
> **What:** a named temporary result for one statement: `WITH high AS (SELECT ...) SELECT ... FROM high`.
- **vs subqueries**: readable, can be referenced several times, can be **recursive**. **vs temp tables**: no storage, exists only for the statement.
- **Recursive CTE**: anchor query `UNION ALL` recursive step: walks hierarchies (org charts, categories) or generates series.

## Window Functions
> **What:** functions computed over a **set of rows related to the current row** with `OVER (PARTITION BY ... ORDER BY ... frame)`, **without collapsing rows**.
- **vs GROUP BY**: GROUP BY returns one row per group; a window keeps every row and adds the group value next to it.
- Ranking: `ROW_NUMBER`, `RANK`, `DENSE_RANK`, `NTILE`. Offset: `LAG`, `LEAD`, `FIRST_VALUE`, `LAST_VALUE`. Aggregates as windows: `SUM(...) OVER (ORDER BY date)` = running total.
- Frames: `ROWS BETWEEN 2 PRECEDING AND CURRENT ROW` (moving average).
```text
salary   ROW_NUMBER  RANK  DENSE_RANK
150000   1           1     1
120000   2           2     2
120000   3           2     2
115000   4           4     3
```

## CASE Expressions
- **Searched**: `CASE WHEN salary > 100000 THEN 'high' ELSE 'low' END`. **Simple**: `CASE dept WHEN 1 THEN 'Eng' END`.
- Works in `SELECT`, `ORDER BY`, `GROUP BY`, `UPDATE`, and inside aggregates for **pivots**: `SUM(CASE WHEN month = 1 THEN amount END) AS jan`.

## Views vs Materialised Views
```text
            table          view             materialised view
stores      data           only the query   query result
freshness   live           always current   stale until REFRESH
speed       -              same as query    fast reads
use         base data      security,        heavy reports,
                           simplify queries dashboards
```

## Procedures, Functions & Triggers
- **Function**: returns a value, used inside SQL (`SELECT f(x)`), usually no transaction control.
- **Stored procedure**: called with `CALL`/`EXEC`, can return result sets / OUT params, manage transactions, run business logic in the DB.
- **Trigger**: code that runs automatically `BEFORE`/`AFTER` `INSERT/UPDATE/DELETE` (row or statement level): auditing, derived columns.
- Languages: PL/pgSQL (PostgreSQL), T-SQL (SQL Server), PL/SQL (Oracle).

## Transactions & ACID
> **What:** a group of statements that succeed or fail **as one unit**: `BEGIN; ... COMMIT;` or `ROLLBACK;` (`SAVEPOINT` for partial rollback).
- **Atomicity**: all or nothing. **Consistency**: constraints always hold. **Isolation**: concurrent transactions don't interfere. **Durability**: committed data survives crashes (write-ahead log).

## Isolation Levels
```text
level             dirty read  non-repeatable  phantom
READ UNCOMMITTED  possible    possible        possible
READ COMMITTED    no          possible        possible
REPEATABLE READ   no          no              possible*
SERIALIZABLE      no          no              no
* PostgreSQL REPEATABLE READ also prevents phantoms
```
- **Dirty** = read uncommitted data · **non-repeatable** = same row changes between reads · **phantom** = new rows appear in a range.
- Defaults: READ COMMITTED (PostgreSQL, SQL Server, Oracle), REPEATABLE READ (MySQL).

## Locking & Concurrency
- **MVCC**: writers create new row versions; readers see a snapshot and don't block (PostgreSQL, Oracle, InnoDB).
- **Pessimistic locking**: `SELECT ... FOR UPDATE` locks rows until commit. **Optimistic locking**: a `version` column checked on update; retry on conflict (JPA `@Version`).
- **Deadlock**: two transactions wait for each other's locks; the DB aborts one. Avoid: lock in a consistent order, keep transactions short, retry.
- `FOR UPDATE SKIP LOCKED`: job queues where workers take different rows.

## Indexes
> **What:** a separate sorted structure (usually a **B-tree**) that finds rows without scanning the whole table: O(log n) instead of O(n).
- **Clustered**: the table rows are physically ordered by it (one per table; InnoDB PK). **Non-clustered**: separate structure pointing to rows (many per table).
- **Composite** `(a, b)`: serves `a` and `a + b`, **not** `b` alone (leftmost prefix rule). **Covering**: contains every column the query needs (index-only scan). **Unique**, **partial** (`WHERE status = 'open'`), **expression** (`LOWER(email)`).
- **Trade-off**: faster reads, slower writes and more storage. Index foreign keys and frequent `WHERE`/`JOIN`/`ORDER BY` columns.

## When an Index Is Not Used
- Function or math on the column: `WHERE YEAR(d) = 2026` → write `d >= '2026-01-01' AND d < '2027-01-01'` (**sargable**).
- Leading wildcard `LIKE '%son'`; implicit type conversion; `OR` across different columns.
- Low selectivity (gender, status), tiny tables, stale statistics.
- Check with **EXPLAIN** / **EXPLAIN ANALYZE**: look for full scans (Seq Scan / type ALL), bad row estimates, sorts spilling to disk.

## Query Optimisation Tips
- Select only needed columns (no `SELECT *`), filter early, index join/filter columns.
- Avoid N+1 queries from the app; batch inserts; use keyset pagination (`WHERE id > last`) instead of big `OFFSET`.
- `EXISTS` instead of `COUNT(*) > 0`; `UNION ALL` instead of `UNION` when duplicates are impossible.
- Keep statistics fresh (`ANALYZE`), use connection pooling, cache hot reads.

## Normalisation
> **What:** organising tables to remove redundancy and **update/insert/delete anomalies**.
- **1NF**: atomic values, no repeating groups (no comma lists in a column).
- **2NF**: 1NF + no **partial dependency** on part of a composite key.
- **3NF**: 2NF + no **transitive dependency** (non-key column depending on another non-key column).
- **BCNF**: every determinant is a candidate key.
- **Denormalisation**: deliberately duplicate data for faster reads (reporting, OLAP). **OLTP** = many small normalised transactions; **OLAP** = large analytical queries (star schema).

## Relationships
- **One-to-one**: FK + UNIQUE (user ↔ profile).
- **One-to-many**: FK on the "many" side (customer → orders).
- **Many-to-many**: a **junction table** with two FKs (students ↔ courses via enrolments).

## Upsert & MERGE
- **Upsert** = insert, or update if the row exists. PostgreSQL `INSERT ... ON CONFLICT (id) DO UPDATE`; MySQL `ON DUPLICATE KEY UPDATE`; SQL Server/Oracle/PostgreSQL 15+ `MERGE` (matched → update, not matched → insert).
- `RETURNING` (PostgreSQL) / `OUTPUT` (SQL Server) return the changed rows.

## Scaling: Partitioning, Sharding, Replication
- **Partitioning**: split one big table inside one database (by range/list/hash, e.g. per month); queries prune partitions.
- **Sharding**: split data across **multiple servers** by a shard key (e.g. customer_id); scales writes, complicates joins.
- **Replication**: copies of the same data on other servers: read replicas (scale reads) and failover (availability). Sync = safe but slower; async = fast but may lag.

## SQL Injection
- **What**: user input changes the meaning of a query (`' OR 1=1 --`).
- **Prevent**: **parameterised queries / prepared statements** (`WHERE id = ?`), ORMs, least-privilege DB users, input validation. Never concatenate input into SQL.

## Nth Highest Salary
```sql
SELECT MAX(salary) FROM employees
WHERE salary < (SELECT MAX(salary) FROM employees);   -- 2nd: 120000

SELECT DISTINCT salary FROM employees
ORDER BY salary DESC OFFSET 1 LIMIT 1;                 -- 2nd: 120000

SELECT salary FROM (
  SELECT salary, DENSE_RANK() OVER (ORDER BY salary DESC) AS r
  FROM employees) t
WHERE r = 3 LIMIT 1;                                   -- Nth (3rd): 115000
```
- Use `DENSE_RANK` so ties (two 120000s) count once.

## Find & Delete Duplicates
```sql
SELECT salary, COUNT(*) FROM employees
GROUP BY salary HAVING COUNT(*) > 1;          -- 120000 appears 2 times

CREATE TEMP TABLE emails (id INT, email TEXT);
INSERT INTO emails VALUES (1, 'a@x'), (2, 'b@x'), (3, 'a@x');
DELETE FROM emails WHERE id IN (
  SELECT id FROM (
    SELECT id, ROW_NUMBER() OVER (PARTITION BY email ORDER BY id) AS rn
    FROM emails) t
  WHERE rn > 1);                              -- keeps ids 1 and 2
```

## Top N per Group
```sql
SELECT dept_id, name, salary FROM (
  SELECT e.*, DENSE_RANK() OVER (
    PARTITION BY dept_id ORDER BY salary DESC) AS r
  FROM employees e) ranked
WHERE r <= 2;
-- Eng: Asha, Ravi, Meena (tie) · Sales: Karan, John · HR: Neha · NULL: Arjun
```

## Self-Join Classics
```sql
SELECT e.name, m.name AS manager FROM employees e
JOIN employees m ON m.emp_id = e.manager_id
WHERE e.salary > m.salary;                 -- Karan (115000) > John (110000)

SELECT c.name FROM customers c
WHERE NOT EXISTS (SELECT 1 FROM orders o
                  WHERE o.customer_id = c.customer_id);   -- never ordered: Divya
```

## Running Total
```sql
SELECT order_id, amount,
  SUM(amount) OVER (ORDER BY order_date) AS running_total
FROM orders;                    -- 250, 350, 750, 900, 950, 1250
```

## Interview One-Liners
- **WHERE vs HAVING**: rows before grouping vs groups after.
- **UNION vs UNION ALL**: dedupe vs keep all (faster).
- **Primary key vs unique key**: not null + one per table vs nullable + many.
- **RANK vs DENSE_RANK vs ROW_NUMBER**: 1,2,2,4 · 1,2,2,3 · 1,2,3,4.
- **Clustered vs non-clustered index**: physical order vs separate pointer structure.
- **DELETE vs TRUNCATE**: logged row removal with WHERE vs fast wipe of all rows.
- **View vs materialised view**: stored query vs stored result.
- **Correlated subquery**: references the outer row, evaluated per row.
- **ACID**: atomicity, consistency, isolation, durability.
- **Normalisation**: remove redundancy and anomalies; 3NF is the usual target.
