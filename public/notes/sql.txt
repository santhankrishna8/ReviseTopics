# 00 | SQL Basics: Start Here | Database servers and clients, installing MySQL, PostgreSQL or SQL Server, connecting, creating a database and user, your first session, client commands in each database, running SQL files, GUI tools, users and permissions | Start Here

## Servers, Clients and Connections | rose
- Most relational databases run as a **server** process that listens on a network port: **MySQL 3306**, **PostgreSQL 5432**, **SQL Server 1433**, **Oracle 1521**. **SQLite** is the exception: a library inside your application that reads and writes one file, with no server.
- You talk to the server through a **client**: a command-line tool (`mysql`, `psql`, `sqlcmd`, `sqlplus`, `sqlite3`), a GUI (MySQL Workbench, pgAdmin, SSMS, DBeaver), or application code using a **driver** (JDBC for Java, psycopg for Python, `pg` / `mysql2` for Node.js).
- The client sends SQL text over the connection; the server parses, plans and runs it, then streams the result rows back (sheet 01).
- **Hierarchy**: server (also called instance or cluster) → **databases** → **schemas** → tables, views, functions. In MySQL, "database" and "schema" mean the same thing.
- A **connection string** holds everything needed to connect:
```text
postgresql://app_user:secret@localhost:5432/shop                  (PostgreSQL URL, used by psql and most drivers)
jdbc:postgresql://localhost:5432/shop                              (Java JDBC)
jdbc:mysql://localhost:3306/shop                                   (Java JDBC, MySQL)
jdbc:sqlserver://localhost:1433;databaseName=shop;encrypt=true     (Java JDBC, SQL Server)
```
- Never hard-code passwords in code: read them from environment variables or a secrets manager.

## Installing a Database | blue
- **Official installers**: MySQL Community Server (MySQL Installer on Windows), PostgreSQL (EDB installer on Windows, Postgres.app on macOS), SQL Server **Developer** edition (free for development) or **Express** (free, limited), Oracle Database **Free**.
- **Package managers**: `brew install postgresql@18`, `sudo apt install postgresql` or `mysql-server`.
- **Docker** (quickest and disposable; one command per database):
```bash
docker run --name pg -e POSTGRES_PASSWORD=secret -p 5432:5432 -d postgres:18
docker run --name mysql -e MYSQL_ROOT_PASSWORD=secret -p 3306:3306 -d mysql:8.4
docker run --name mssql -e ACCEPT_EULA=Y -e "MSSQL_SA_PASSWORD=Str0ng!Passw0rd" -p 1433:1433 -d mcr.microsoft.com/mssql/server:2022-latest
docker exec -it pg psql -U postgres          # open a client inside the container
```
- **Managed cloud databases**: Amazon RDS / Aurora, Azure SQL Database, Google Cloud SQL, Neon or Supabase (PostgreSQL).
- **No install at all**: browser playgrounds such as DB Fiddle let you practise queries against MySQL, PostgreSQL or SQLite.
- Default administrator accounts: PostgreSQL **`postgres`**, MySQL **`root`**, SQL Server **`sa`**, Oracle **`SYS`** / **`SYSTEM`**. Use them only for administration and create a separate application user.

## Connect and Create Your First Database | green
```bash psql
psql -h localhost -U postgres             # PostgreSQL: connect as the admin user (prompts for the password)
mysql -h localhost -u root -p             # MySQL
sqlcmd -S localhost -U sa                 # SQL Server
```
```sql PostgreSQL
CREATE USER app_user WITH PASSWORD 'secret';
CREATE DATABASE shop OWNER app_user;      -- the owner can create tables in its public schema
-- then reconnect to it:  \c shop app_user
```
```sql MySQL
CREATE DATABASE shop;
CREATE USER 'app_user'@'%' IDENTIFIED BY 'secret';     -- '%' = may connect from any host
GRANT ALL PRIVILEGES ON shop.* TO 'app_user'@'%';
USE shop;                                               -- make shop the current database
```
```sql SQL-Server
CREATE DATABASE shop;
GO
CREATE LOGIN app_user WITH PASSWORD = 'Str0ng!Passw0rd';    -- server-level login
GO
USE shop;
CREATE USER app_user FOR LOGIN app_user;                     -- database-level user mapped to the login
ALTER ROLE db_owner ADD MEMBER app_user;
GO
```
- PostgreSQL 15+ no longer lets every user create tables in the `public` schema. Making the application user the **owner** of the database (as above), or granting `CREATE ON SCHEMA public`, avoids "permission denied for schema public".
- SQL Server separates a **login** (authenticates to the server) from a **user** (has permissions inside one database). `GO` is a batch separator understood by `sqlcmd` and SSMS.

## Your First Session | amber
```sql
CREATE TABLE students (
  id     INT PRIMARY KEY,
  name   VARCHAR(50) NOT NULL,
  city   VARCHAR(50),
  marks  INT CHECK (marks BETWEEN 0 AND 100)
);

INSERT INTO students (id, name, city, marks) VALUES
  (1, 'Ann', 'Chennai', 91),
  (2, 'Bala', 'Pune', 78),
  (3, 'Chitra', 'Chennai', 85);

SELECT * FROM students;                                                  -- 3 rows
SELECT name, marks FROM students WHERE city = 'Chennai' ORDER BY marks DESC;   -- Ann 91 | Chitra 85
UPDATE students SET marks = 80 WHERE id = 2;                             -- Bala now has 80
DELETE FROM students WHERE id = 3;                                       -- Chitra removed
SELECT COUNT(*) AS total, AVG(marks) AS average FROM students;           -- 2 | 85.5
```
- That is the whole cycle: **create** a table (DDL), **insert**, **read**, **update** and **delete** rows (DML). `DROP TABLE students;` removes the table when you no longer need it (keep it for the permissions example below). The remaining sheets go deep on each step; sheet 01 sets up the sample database used everywhere else.

## Client Commands in Each Database | violet
- These are **client commands**, not SQL: each tool has its own.
- **psql (PostgreSQL)**: `\l` list databases, `\c shop` connect to a database, `\dt` list tables, `\d students` describe a table, `\dn` schemas, `\du` roles, `\i setup.sql` run a file, `\x` expanded display, `\timing` show query times, `\?` help, `\q` quit.
- **mysql (MySQL)**: `SHOW DATABASES;`, `USE shop;`, `SHOW TABLES;`, `DESCRIBE students;`, `SHOW CREATE TABLE students;`, `SELECT DATABASE();` (current database), `SOURCE setup.sql;`, `exit`.
- **sqlcmd / SSMS (SQL Server)**: `SELECT name FROM sys.databases;`, `USE shop;`, `SELECT * FROM INFORMATION_SCHEMA.TABLES;`, `EXEC sp_help 'students';`, end each batch with `GO`; run a file with `sqlcmd -S localhost -U sa -i setup.sql`.
- **SQL\*Plus (Oracle)**: `SELECT table_name FROM user_tables;`, `DESC students`, `@setup.sql`, `exit`.
- **sqlite3 (SQLite)**: `sqlite3 shop.db` opens or creates the file; `.tables`, `.schema students`, `.headers on`, `.mode column`, `.read setup.sql`, `.quit`.
- **Running a SQL file from the shell**: `psql -U postgres -d shop -f setup.sql`, `mysql -u root -p shop < setup.sql`, `sqlcmd -S localhost -U sa -i setup.sql`.
- **The portable way** to list tables and columns is the standard **`INFORMATION_SCHEMA`** (PostgreSQL, MySQL, SQL Server; Oracle uses its own `USER_TABLES` and `ALL_TAB_COLUMNS` views):
```sql
SELECT table_name FROM information_schema.tables WHERE table_schema = 'public' ORDER BY table_name;
-- customers, departments, employees, logins, logs, orders, person, weather  (with the practice tables loaded)
SELECT column_name, data_type, is_nullable
FROM information_schema.columns
WHERE table_name = 'customers'
ORDER BY ordinal_position;
-- id integer NO | name character varying NO | city character varying YES
```

## GUI Tools | rose
- **MySQL Workbench** (MySQL), **pgAdmin** (PostgreSQL), **SSMS**, SQL Server Management Studio (SQL Server), **Oracle SQL Developer** (Oracle).
- **DBeaver** (free, works with almost every database) and **DataGrip** (JetBrains, paid): handy when you use several databases.
- **VS Code** extensions for running queries next to your code.
- GUIs help you explore schemas, edit data, read execution plans visually and build ER diagrams; the command-line clients are what you'll use on servers and in scripts.

## Users, Roles and Permissions (DCL) | blue
```sql
CREATE ROLE reporting;                                       -- a group of permissions
GRANT SELECT ON students TO reporting;                       -- read-only access to one table
CREATE USER analyst WITH PASSWORD 'secret';                  -- PostgreSQL: a role that can log in
GRANT reporting TO analyst;                                  -- analyst inherits reporting's permissions
REVOKE SELECT ON students FROM reporting;                    -- take the permission back
```
- **DCL (Data Control Language)** manages access: `GRANT` gives privileges (`SELECT`, `INSERT`, `UPDATE`, `DELETE`, `EXECUTE`, `CREATE`...), `REVOKE` removes them.
- Grant privileges to **roles** and put users into roles, rather than granting to each user individually.
- **Principle of least privilege**: the application connects as a user that can only do what the app needs (never as `root`, `postgres` or `sa`); reports use a read-only account; schema migrations use a separate account with DDL rights.
- MySQL users are identified by name **and host** (`'app_user'@'localhost'` and `'app_user'@'%'` are different accounts).

## Interview Q&A | sky | wide
Q: What is the difference between a database server and a client?
A: The server stores the data and executes queries; a client (CLI, GUI or application driver) connects to it over the network, sends SQL and receives the results. SQLite is embedded, so there is no separate server.
Q: What are the default ports of MySQL, PostgreSQL, SQL Server and Oracle?
A: 3306, 5432, 1433 and 1521.
Q: How do you list all tables in MySQL, PostgreSQL and SQL Server?
A: MySQL `SHOW TABLES;`, PostgreSQL `\dt` in psql, SQL Server `SELECT * FROM INFORMATION_SCHEMA.TABLES;`. The INFORMATION_SCHEMA query works in all three.
Q: How do you see the structure of a table?
A: MySQL `DESCRIBE t;`, PostgreSQL `\d t`, SQL Server `EXEC sp_help 't';`, Oracle `DESC t`, or query information_schema.columns.
Q: What is the difference between a database and a schema?
A: A database is a separate container with its own schemas, users and settings; a schema is a namespace inside a database that groups tables and other objects. In MySQL the two terms are synonyms.
Q: What is the difference between a login and a user in SQL Server?
A: A login authenticates to the whole server; a user is mapped to a login inside one database and holds that database's permissions.
Q: What is a connection string?
A: A string with the driver or protocol, host, port, database name, credentials and options needed to open a connection, for example `postgresql://user:pass@localhost:5432/shop`.
Q: How do you run a .sql file?
A: `psql -f file.sql` (or `\i file.sql` inside psql), `mysql db < file.sql` (or `SOURCE file.sql`), `sqlcmd -i file.sql`, `@file.sql` in SQL*Plus.
Q: What is DCL? Give examples.
A: Data Control Language manages permissions: GRANT and REVOKE, usually applied to roles that users belong to.
Q: What is the principle of least privilege for database accounts?
A: Each account gets only the permissions it needs: the application can't drop tables, reporting users can only read, and admin accounts aren't used by applications.

# 01 | SQL & Relational Database Basics | Databases, DBMS vs RDBMS, the relational model, SQL sub-languages, keys, relationships, SQL vs NoSQL, the 7-day plan and sample schema | SQL Basics

## What a Database Is | rose
- A **database** is an organised, persistent collection of data. A **DBMS (Database Management System)** is the software that stores it, answers queries and handles **concurrency, crash recovery, security and backups**.
- An **RDBMS (Relational DBMS)** follows the **relational model** published by **E. F. Codd (IBM, 1970)**: data lives in **relations (tables)** made of **tuples (rows)** and **attributes (columns)**, tables are linked through **keys**, and everything is queried with **SQL**.
- Examples: **MySQL, PostgreSQL, Microsoft SQL Server, Oracle Database, SQLite, MariaDB, IBM Db2**.
- **DBMS vs RDBMS**: a DBMS may store files, hierarchies or documents. An RDBMS stores tables, enforces relationships and **integrity constraints** (keys, NOT NULL, CHECK), and supports **ACID transactions** and normalisation.
- **Schema**: the structure (tables, columns, types, constraints). **Instance**: the data stored at one moment.
- Vocabulary: **table = relation**, **row = record = tuple**, **column = field = attribute**, **degree** = number of columns, **cardinality** = number of rows (also used for the number of distinct values in a column and for relationship types such as 1:N).

## SQL: The Language | blue
- **SQL (Structured Query Language)** is the standard language for relational databases. It was built at **IBM in the early 1970s by Donald Chamberlin and Raymond Boyce** as **SEQUEL**, later renamed SQL. Say "S-Q-L" or "sequel".
- SQL is **declarative**: you describe **what** result you want; the **query optimiser** decides **how** to get it (which index, join order and algorithm).
- Standardised by **ANSI (1986)** and **ISO (1987)**. Milestones: **SQL-92** (explicit JOIN syntax), **SQL:1999** (recursive CTEs, triggers), **SQL:2003** (window functions, MERGE), **SQL:2008** (TRUNCATE, FETCH FIRST), **SQL:2011** (temporal tables), **SQL:2016** (JSON), **SQL:2023** (property graph queries, JSON type).
- Each product implements the core standard plus its own **dialect** (sheet 02).
- Keywords are **case-insensitive** (`select` = `SELECT`). Statements end with `;`. Comments: `-- to end of line` and `/* block */` (MySQL also accepts `#`). Whether `'abc' = 'ABC'` is true depends on the database's collation.
- **SQL vs MySQL**: SQL is the **language**; MySQL is one **RDBMS product** that speaks SQL. The same goes for PostgreSQL, SQL Server and Oracle.
> One-liner: "SQL is a declarative, standardised language. Every RDBMS speaks a dialect of it."

## SQL Sub-Languages | green
- **DDL (Data Definition Language)**: defines structure. `CREATE`, `ALTER`, `DROP`, `TRUNCATE`, `RENAME`, `COMMENT`.
- **DML (Data Manipulation Language)**: changes data. `INSERT`, `UPDATE`, `DELETE`, `MERGE`.
- **DQL (Data Query Language)**: reads data. `SELECT`. Many textbooks count it as part of DML.
- **DCL (Data Control Language)**: permissions. `GRANT`, `REVOKE`.
- **TCL (Transaction Control Language)**: `BEGIN`/`START TRANSACTION`, `COMMIT`, `ROLLBACK`, `SAVEPOINT`, `SET TRANSACTION`.
```sql overview
CREATE TABLE t (id INT PRIMARY KEY);          -- DDL
INSERT INTO t (id) VALUES (1);                -- DML
SELECT id FROM t;                             -- DQL
GRANT SELECT ON t TO reporting_user;          -- DCL
COMMIT;                                       -- TCL
```

## Keys | amber
- **Primary key (PK)**: uniquely identifies each row. It is **UNIQUE + NOT NULL**, there is **one per table**, and it can be **composite** (several columns).
- **Candidate key**: any minimal set of columns that could serve as the PK. **Alternate key**: a candidate key that was not chosen. **Super key**: any column set that identifies rows uniquely (a candidate key plus optional extra columns).
- **Unique key**: enforces uniqueness without being the PK. A table can have many. It allows NULLs (how many differs by database, sheet 03).
- **Foreign key (FK)**: column(s) that reference a PK or unique key in another table (or the same table). The database enforces **referential integrity**: no orphan rows.
- **Composite key**: a key made of several columns, for example `(order_id, product_id)`.
- **Surrogate key**: an artificial id (`BIGINT` identity, UUID). **Natural key**: a real-world value (email, ISBN, PAN). A common design is a surrogate PK **plus** a UNIQUE constraint on the natural key.
> One-liner: "PK = unique + not null, one per table. FK = a reference to another table's key that the database keeps valid."

## Relationships | violet
- **One-to-one (1:1)**: `users` and `user_profiles`. Use an FK with a UNIQUE constraint (or share the PK).
- **One-to-many (1:N)**: one department has many employees. The FK goes on the **many** side: `employees.dept_id`.
- **Many-to-many (M:N)**: students and courses. Use a **junction (bridge) table** `enrollments(student_id, course_id)` with a composite PK and two FKs.
- **Self-referencing**: `employees.manager_id → employees.id` for hierarchies.
- An **ER (Entity-Relationship) diagram** shows entities (tables), attributes (columns) and relationships with their cardinality, usually in crow's-foot notation.

## SQL vs NoSQL | sky
- **SQL (relational)**: predefined schema, tables and joins, **ACID** transactions, strong consistency, scales up first (then replicas and sharding). Best for structured, related data: payments, orders, inventory, HR.
- **NoSQL**: flexible schema, built for horizontal scale, often eventual consistency (many now offer transactions). Families: **document** (MongoDB), **key-value** (Redis, DynamoDB), **wide-column** (Cassandra), **graph** (Neo4j).
- Choose by **access patterns, consistency needs and scale**, not fashion. Many systems use both (polyglot persistence).

## Interview Q&A | sky | wide
Q: What is the difference between a DBMS and an RDBMS?
A: A DBMS is any software that manages stored data. An RDBMS stores data in related tables, enforces keys and integrity constraints, supports ACID transactions and is queried with SQL. MySQL, PostgreSQL, SQL Server and Oracle are RDBMSs.
Q: What is SQL and why is it called declarative?
A: The standard language for relational databases. You state the result you want, not the steps; the optimiser picks the execution plan.
Q: What is the difference between SQL and MySQL?
A: SQL is the language and standard. MySQL is a database product (an RDBMS) that implements SQL plus its own extensions.
Q: Name the SQL sub-languages.
A: DDL (CREATE, ALTER, DROP, TRUNCATE), DML (INSERT, UPDATE, DELETE, MERGE), DQL (SELECT), DCL (GRANT, REVOKE) and TCL (COMMIT, ROLLBACK, SAVEPOINT).
Q: Primary key vs unique key?
A: Both enforce uniqueness. A table has one primary key, which can never be NULL and usually is the clustered or main lookup key. It can have many unique keys, and they allow NULLs.
Q: Primary key vs foreign key?
A: A primary key identifies rows in its own table. A foreign key in another table references that key and the database rejects values that have no matching parent.
Q: What are candidate, alternate and super keys?
A: A super key is any column set that identifies rows uniquely. A candidate key is a minimal super key. The chosen one becomes the primary key and the others are alternate keys.
Q: How do you model a many-to-many relationship?
A: With a junction table that holds the two foreign keys, usually with a composite primary key on them, for example enrollments(student_id, course_id).
Q: Surrogate vs natural key?
A: A natural key comes from the data (email); a surrogate key is generated (identity or UUID). Surrogates are stable and compact, so they are the usual PK, with a unique constraint on the natural key.
Q: When would you choose SQL over NoSQL?
A: When data is structured and related, needs joins, constraints and multi-row ACID transactions, such as payments, orders or inventory. NoSQL suits flexible schemas, huge scale with simple access patterns, or special models such as graphs.

# 02 | SQL Dialects: MySQL vs PostgreSQL vs SQL Server vs Oracle vs SQLite | The major products, their procedural languages, syntax differences, behaviour differences and when to pick each | Dialects Compared

## The Main Products | rose
- **MySQL**: open source (GPL) with a commercial edition, owned by **Oracle** (MySQL AB released it in 1995; Sun bought it in 2008; Oracle bought Sun in 2010). Default storage engine **InnoDB**. Huge in web apps (LAMP stack, WordPress). Default port **3306**. **MariaDB** is a community fork (2009) by MySQL's original author, Michael "Monty" Widenius.
- **PostgreSQL ("Postgres")**: community-developed, liberal **PostgreSQL License**. Grew out of the **POSTGRES** project at UC Berkeley (1986, Michael Stonebraker); SQL was added in 1995 (Postgres95) and it was renamed in 1996. An **object-relational** database known for standards compliance and extensions (**PostGIS**, **pgvector**, Citus, TimescaleDB). Port **5432**. One major release a year.
- **Microsoft SQL Server**: commercial, with free **Express** and **Developer** editions. Started in 1989 with Sybase; runs on **Windows and Linux** (since 2017); cloud version **Azure SQL**. Dialect **T-SQL**. Tools: **SSMS**, `sqlcmd`. Port **1433**.
- **Oracle Database**: commercial, the first commercially available SQL RDBMS (**1979**). Dialect **PL/SQL**. Strong in banks and large enterprises (RAC clustering, Data Guard). Port **1521**.
- **SQLite**: public domain (2000, D. Richard Hipp). **Embedded and serverless**: the whole database is **one file** inside your app. Ships in every phone and browser. No users, no network server, **dynamic typing** (type affinity) unless you use `STRICT` tables.

## Procedural Extensions | blue
- **T-SQL (Transact-SQL)**, SQL Server: variables `DECLARE @total INT`, `IF`/`WHILE`, `TRY...CATCH`, temp tables `#temp`, `TOP`, `OUTPUT`, `MERGE`, `CROSS APPLY`.
- **PL/SQL**, Oracle: block-structured `DECLARE ... BEGIN ... EXCEPTION ... END;`, packages, cursors, `%TYPE`, `BULK COLLECT`.
- **PL/pgSQL**, PostgreSQL: functions, procedures and anonymous `DO` blocks. PostgreSQL can also run PL/Python, PL/Perl and others.
- **MySQL**: stored procedures, functions and triggers in SQL/PSM-style syntax (`BEGIN ... END`, `DECLARE`, handlers), written with the client's `DELIMITER` command. There is no separate brand name.
- **SQLite**: no stored procedures. Logic lives in the application; triggers and views are supported.
> "SQL vs PL/SQL vs T-SQL": SQL is the standard declarative language. PL/SQL (Oracle) and T-SQL (Microsoft) are vendor procedural extensions that add variables, loops, error handling and stored programs.

## Syntax Differences You Get Asked About | green
- **Limit rows**: MySQL, PostgreSQL, SQLite `LIMIT 10 OFFSET 20`. SQL Server `SELECT TOP (10)` or `ORDER BY ... OFFSET 20 ROWS FETCH NEXT 10 ROWS ONLY` (2012+). Oracle 12c+ `OFFSET 20 ROWS FETCH NEXT 10 ROWS ONLY` (older code uses `ROWNUM`). The standard `FETCH` form also works in PostgreSQL.
- **Auto-increment id**: MySQL `AUTO_INCREMENT`. PostgreSQL `GENERATED ALWAYS AS IDENTITY` (10+; older code uses `SERIAL`). SQL Server `IDENTITY(1,1)`. Oracle `GENERATED AS IDENTITY` (12c+) or a sequence. SQLite `INTEGER PRIMARY KEY`.
- **String concatenation**: standard `||` in PostgreSQL, Oracle and SQLite. MySQL uses `CONCAT()` (by default `||` means logical OR there). SQL Server uses `+` or `CONCAT()`. `CONCAT()` exists in all of them (Oracle's takes only two arguments).
- **Quoting identifiers**: standard `"double quotes"` (PostgreSQL, Oracle, SQLite, and SQL Server by default). MySQL uses backticks. SQL Server also uses `[brackets]`. String literals are always `'single quotes'` (MySQL also accepts double-quoted strings by default).
- **Booleans**: PostgreSQL has a real `BOOLEAN`. MySQL's `BOOLEAN` is an alias for `TINYINT(1)`. SQL Server uses `BIT`. Oracle added `BOOLEAN` only in 23ai (before that `NUMBER(1)` or `CHAR(1)`). SQLite stores 0 and 1.
- **Replace NULL**: standard `COALESCE` works everywhere. Two-argument shortcuts: MySQL `IFNULL`, SQL Server `ISNULL`, Oracle `NVL`.
- **Current date and time**: `CURRENT_TIMESTAMP` everywhere. MySQL and PostgreSQL `NOW()`. SQL Server `GETDATE()` / `SYSDATETIME()`. Oracle `SYSDATE` / `SYSTIMESTAMP`.
- **Date arithmetic**: MySQL `DATE_ADD(d, INTERVAL 7 DAY)` and `DATEDIFF(a, b)` (a minus b, in days). PostgreSQL `d + INTERVAL '7 days'` and `a - b` (days, for DATE values). SQL Server `DATEADD(day, 7, d)` and `DATEDIFF(day, start, end)` (end minus start: note the order). Oracle `d + 7`.
- **String aggregation**: MySQL `GROUP_CONCAT(name SEPARATOR ', ')`. PostgreSQL and SQL Server 2017+ `STRING_AGG(name, ', ')`. Oracle `LISTAGG(name, ', ') WITHIN GROUP (ORDER BY name)`.
- **Upsert**: PostgreSQL and SQLite `INSERT ... ON CONFLICT (key) DO UPDATE`. MySQL `INSERT ... ON DUPLICATE KEY UPDATE`. SQL Server and Oracle `MERGE` (PostgreSQL 15+ also has MERGE).
- **Return changed rows**: PostgreSQL and SQLite `RETURNING`. SQL Server `OUTPUT inserted.*`. MySQL has none (use `LAST_INSERT_ID()`). Oracle `RETURNING ... INTO` inside PL/SQL.
- **FULL OUTER JOIN**: missing in MySQL (emulate with LEFT JOIN UNION RIGHT JOIN). **EXCEPT**: Oracle traditionally writes `MINUS` (21c also accepts EXCEPT); MySQL supports INTERSECT and EXCEPT from 8.0.31.
- **Recursive CTE**: PostgreSQL, MySQL and SQLite write `WITH RECURSIVE`; SQL Server and Oracle write plain `WITH`.
- **Integer division**: `7 / 2` is `3` in PostgreSQL, SQL Server and SQLite, but `3.5000` in MySQL (which has `DIV` for integer division) and `3.5` in Oracle.
- **Case-sensitive comparison**: MySQL and SQL Server default collations are **case-insensitive** (`'abc' = 'ABC'` is true). PostgreSQL and Oracle are **case-sensitive** (PostgreSQL offers `ILIKE`, `LOWER()` or the `citext` type).
- **Unquoted identifiers**: PostgreSQL folds them to lowercase, Oracle to UPPERCASE. MySQL table-name case sensitivity follows the file system (case-sensitive on Linux, not on Windows).
- **NULL sort order**: PostgreSQL and Oracle put NULLs **last** in ascending order; MySQL, SQL Server and SQLite put them **first**. PostgreSQL, Oracle and SQLite support `NULLS FIRST` / `NULLS LAST`.
- **Empty string**: **Oracle treats `''` as NULL**. In every other database `''` is a real, non-NULL value.
- **SELECT without FROM**: `SELECT 1;` works in MySQL, PostgreSQL, SQL Server and SQLite. Oracle needed `FROM dual` (optional from 23ai).
- **Namespaces**: in MySQL a "database" and a "schema" are the same thing. PostgreSQL and SQL Server have database → schema (`public`, `dbo`) → table. In Oracle a schema is a user.

## Behaviour and Architecture Differences | violet
- **Concurrency (MVCC)**: PostgreSQL keeps old row versions inside the table, so **VACUUM** (autovacuum) must clean dead rows. MySQL InnoDB and Oracle keep old versions in **undo logs**. SQL Server uses **locks** by default under READ COMMITTED and keeps row versions in tempdb only when snapshot isolation or RCSI is turned on (Azure SQL Database turns RCSI on by default).
- **Default isolation level**: MySQL InnoDB **REPEATABLE READ**; PostgreSQL, SQL Server and Oracle **READ COMMITTED** (sheet 15).
- **Table storage**: InnoDB tables are **clustered on the primary key**. SQL Server tables are clustered when they have a clustered index (a PK creates one by default), otherwise they are heaps. PostgreSQL tables are always **heaps** and every index is secondary. Oracle uses heaps by default, with optional index-organised tables (sheet 16).
- **Connections**: PostgreSQL starts a **process per connection** (so pools such as PgBouncer matter); MySQL and SQL Server use **threads**.
- **Transactional DDL**: PostgreSQL (and mostly SQL Server) can roll back `CREATE`, `ALTER` and `DROP` inside a transaction. MySQL and Oracle **commit implicitly** before and after DDL.
- **Extras**: PostgreSQL has JSONB, arrays, ranges, enums, a `uuid` type, full-text search and extensions. MySQL has a JSON type, full-text and spatial indexes, and pluggable storage engines. SQL Server has columnstore indexes, temporal tables, In-Memory OLTP and the Microsoft BI stack (SSIS, SSRS, SSAS). Oracle has RAC, advanced partitioning and Data Guard.
- **MySQL storage engines**: **InnoDB** (default since 5.5: transactions, row-level locking, foreign keys, crash recovery) vs **MyISAM** (legacy: table-level locks, no transactions, no foreign keys).

## Which One When? | sky
- **PostgreSQL**: the default pick for a new backend: rich SQL, JSONB, strong integrity, extensions such as pgvector for AI search.
- **MySQL / MariaDB**: read-heavy web applications, cheap hosting everywhere, LAMP and WordPress, mature replication (Vitess for sharding).
- **SQL Server**: Microsoft and .NET shops, Windows or Azure, heavy reporting and BI.
- **Oracle**: large enterprises that need RAC, advanced partitioning and vendor support, and can pay for licences.
- **SQLite**: mobile, desktop and embedded apps, tests, small sites. It allows **one writer at a time**, so it is not for many concurrent writers.

## Interview Q&A | sky | wide
Q: MySQL vs PostgreSQL?
A: Both are open-source RDBMSs. PostgreSQL is more standards-compliant and extensible (JSONB, arrays, custom types, extensions, transactional DDL, many index types) and uses a process per connection with VACUUM-based MVCC. MySQL is simpler to run, very common for read-heavy web apps, clusters InnoDB tables on the primary key and uses threads and undo-log MVCC.
Q: What are T-SQL and PL/SQL?
A: Procedural extensions of SQL: T-SQL for Microsoft SQL Server and PL/SQL for Oracle. They add variables, control flow, error handling, cursors and stored programs.
Q: How do you return only the first 10 rows in MySQL, SQL Server and Oracle?
A: MySQL and PostgreSQL: `ORDER BY ... LIMIT 10`. SQL Server: `SELECT TOP (10) ... ORDER BY ...` or `OFFSET 0 ROWS FETCH NEXT 10 ROWS ONLY`. Oracle 12c+: `FETCH FIRST 10 ROWS ONLY`.
Q: Why can `'a' = 'A'` be true in one database and false in another?
A: Comparison follows the collation. MySQL and SQL Server default to case-insensitive collations; PostgreSQL and Oracle compare case-sensitively.
Q: Can you roll back a TRUNCATE?
A: It depends on the database. PostgreSQL and SQL Server can roll it back inside an explicit transaction. MySQL and Oracle treat it as DDL with an implicit commit, so no.
Q: How is auto-increment written in each database?
A: MySQL `AUTO_INCREMENT`, PostgreSQL `GENERATED ... AS IDENTITY` (or legacy `SERIAL`), SQL Server `IDENTITY(1,1)`, Oracle identity columns or sequences, SQLite `INTEGER PRIMARY KEY`.
Q: What is MariaDB?
A: A community fork of MySQL started in 2009 by MySQL's creator. It is largely compatible but has diverged (for example it has RETURNING on INSERT and DELETE).
Q: InnoDB vs MyISAM?
A: InnoDB supports transactions, row-level locking, foreign keys and crash recovery and is the default. MyISAM has only table-level locks, no transactions and no foreign keys.
Q: Which databases lack FULL OUTER JOIN?
A: MySQL (and MariaDB). Emulate it with a LEFT JOIN combined with a RIGHT JOIN through UNION. SQLite added RIGHT and FULL joins in 3.39.
Q: What is special about SQLite?
A: It is an embedded library, not a server: the whole database is a single file, there is no user management and only one writer at a time. Ideal for mobile, desktop, tests and edge devices.

# 03 | Data Types, DDL & Constraints | Choosing data types, CREATE, ALTER, DROP, TRUNCATE, all constraint types, foreign key actions, DELETE vs TRUNCATE vs DROP | DDL & Constraints

## Data Types | rose
- **Exact integers**: `SMALLINT` (2 bytes), `INT`/`INTEGER` (4 bytes, about ±2.1 billion), `BIGINT` (8 bytes). MySQL also has `TINYINT` and `UNSIGNED` variants.
- **Exact decimals**: `DECIMAL(p, s)` = `NUMERIC(p, s)`: `p` total digits, `s` after the point. `DECIMAL(10,2)` holds up to 99,999,999.99. **Use it for money.**
- **Approximate**: `REAL`, `FLOAT`, `DOUBLE PRECISION`: binary floating point, so `0.1 + 0.2` is not exactly `0.3`. Fine for measurements, never for money.
- **Strings**: `CHAR(n)` is fixed length and padded with spaces (codes such as `'IN'`); `VARCHAR(n)` is variable length up to n; `TEXT` is long text. In PostgreSQL `TEXT` and `VARCHAR` perform the same. SQL Server uses `VARCHAR(MAX)`; Oracle uses `VARCHAR2` and `CLOB`.
- **Unicode**: SQL Server needs `NVARCHAR` and `N'...'` literals (or a UTF-8 collation, 2019+). In MySQL use **`utf8mb4`**: its old `utf8` (utf8mb3) stores at most 3 bytes and cannot hold emoji.
- **Date and time**: `DATE`, `TIME`, `TIMESTAMP`. PostgreSQL **`TIMESTAMPTZ`** stores an absolute instant (recommended). MySQL `DATETIME` (no time zone, years 1000 to 9999) vs `TIMESTAMP` (stored as UTC and converted to the session time zone, range 1970 to 2038). SQL Server `DATETIME2` and `DATETIMEOFFSET`. Oracle's `DATE` includes the time to the second.
- **Others**: `BOOLEAN` (sheet 02); binary `BYTEA` (PostgreSQL), `BLOB`/`VARBINARY` (MySQL), `VARBINARY(MAX)` (SQL Server); `JSON` (PostgreSQL also `JSONB`, binary and indexable); **UUID**: PostgreSQL `uuid` with `gen_random_uuid()` (and time-ordered `uuidv7()` in PostgreSQL 18), SQL Server `UNIQUEIDENTIFIER` with `NEWID()`, MySQL `BINARY(16)` with `UUID_TO_BIN(UUID())`; **ENUM** (inline in MySQL, `CREATE TYPE ... AS ENUM` in PostgreSQL).
- Rules of thumb: the smallest type that safely fits, `DECIMAL` (or integer cents) for money, UTC instants for timestamps, `NOT NULL` unless a value can truly be missing.

## CREATE, ALTER, DROP, TRUNCATE | blue
```sql
CREATE TABLE projects (
  id         INT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  name       VARCHAR(100) NOT NULL,
  dept_id    INT NOT NULL,
  budget     DECIMAL(12,2) DEFAULT 0 CHECK (budget >= 0),
  status     VARCHAR(20) NOT NULL DEFAULT 'active',
  starts_on  DATE,
  ends_on    DATE,
  CONSTRAINT uq_projects_dept_name UNIQUE (dept_id, name),
  CONSTRAINT ck_projects_dates CHECK (ends_on IS NULL OR ends_on >= starts_on),
  CONSTRAINT fk_projects_dept FOREIGN KEY (dept_id) REFERENCES departments (id) ON DELETE CASCADE
);

ALTER TABLE projects ADD COLUMN owner_id INT;
ALTER TABLE projects ADD CONSTRAINT fk_projects_owner
  FOREIGN KEY (owner_id) REFERENCES employees (id) ON DELETE SET NULL;
ALTER TABLE projects RENAME COLUMN budget TO budget_inr;
ALTER TABLE projects ALTER COLUMN name TYPE VARCHAR(150);    -- PostgreSQL syntax
ALTER TABLE projects DROP COLUMN status;
TRUNCATE TABLE projects;                                     -- remove all rows, keep the table
DROP TABLE IF EXISTS projects;                               -- remove the table itself
```
- Changing a column type differs: MySQL `ALTER TABLE projects MODIFY COLUMN name VARCHAR(150) NOT NULL;`, SQL Server `ALTER TABLE projects ALTER COLUMN name VARCHAR(150) NOT NULL;`. In both you must **repeat `NOT NULL`**, or the column becomes nullable.
- Renaming a table: PostgreSQL and MySQL `ALTER TABLE a RENAME TO b`; SQL Server `EXEC sp_rename 'a', 'b'`.
- `CREATE TABLE copy AS SELECT ...` (CTAS) copies structure and data (SQL Server: `SELECT ... INTO copy FROM ...`). Constraints and indexes are not copied.
- **Temporary tables**: `CREATE TEMPORARY TABLE` (MySQL, PostgreSQL) live for the session; SQL Server uses `#temp` (session) and `##temp` (global).
- **Generated (computed) columns**: `total DECIMAL(10,2) GENERATED ALWAYS AS (qty * price) STORED`. PostgreSQL 18 adds `VIRTUAL` columns (computed when read), which are now its default.

## Constraints | green
- **NOT NULL**: a value is required.
- **UNIQUE**: no duplicate values. Allowed on several columns per table and on column combinations.
- **PRIMARY KEY**: UNIQUE + NOT NULL, one per table.
- **FOREIGN KEY**: values must exist in the referenced key.
- **CHECK**: a boolean rule per row, such as `CHECK (salary > 0)`. MySQL **ignored CHECK before 8.0.16**.
- **DEFAULT**: the value used when an INSERT omits the column (SQL Server lists it as a constraint).
- **Name your constraints** (`CONSTRAINT fk_orders_customer ...`) so errors and migrations are readable.
- **UNIQUE and NULL**: PostgreSQL, MySQL, Oracle (single column) and SQLite allow **many NULLs** in a UNIQUE column because NULLs are not equal to each other. **SQL Server allows only one NULL**; use a filtered unique index `WHERE col IS NOT NULL`. PostgreSQL 15+ can choose with `UNIQUE NULLS NOT DISTINCT`.
- **Deferrable constraints** (PostgreSQL, Oracle): `DEFERRABLE INITIALLY DEFERRED` checks at COMMIT instead of after each statement (useful for circular references).
```sql
INSERT INTO employees (id, name, salary, hire_date) VALUES (10, 'Test', -5, '2026-01-01');
-- ERROR: new row for relation "employees" violates check constraint "employees_salary_check"
```

## Foreign Key Actions | amber
- What happens to children when a parent row is deleted or its key is updated:
- **`NO ACTION`** (default): reject the change if children exist; checked at the end of the statement (or at COMMIT if deferred).
- **`RESTRICT`**: reject immediately. Not available in SQL Server (use NO ACTION).
- **`CASCADE`**: delete (or update) the children too.
- **`SET NULL`** / **`SET DEFAULT`**: set the child FK column to NULL or its default. InnoDB rejects SET DEFAULT.
- Oracle supports only `ON DELETE CASCADE` and `ON DELETE SET NULL`, and has no `ON UPDATE`.
- FK columns are **not indexed automatically** in PostgreSQL, SQL Server or Oracle. Index them, or joins and parent deletes become slow. MySQL InnoDB creates the index for you.
```sql
DELETE FROM departments WHERE id = 1;
-- ERROR: update or delete on table "departments" violates foreign key constraint "employees_dept_id_fkey" on table "employees"
```

## DELETE vs TRUNCATE vs DROP | violet
- **DELETE** (DML): removes the rows matched by `WHERE` (all rows without it), logs every row, fires DELETE triggers, keeps the identity counter and can be rolled back.
- **TRUNCATE** (DDL): removes **all** rows by deallocating data pages. Much faster with minimal logging, no WHERE, no DELETE triggers. Resets the identity counter in MySQL and SQL Server (PostgreSQL needs `RESTART IDENTITY`). Refused when another table's FK references the table (PostgreSQL allows `TRUNCATE ... CASCADE`). Rollback: possible in PostgreSQL and SQL Server, not in MySQL or Oracle.
- **DROP** (DDL): removes the table definition along with its data, indexes, triggers and permissions.
> Mnemonic: "DELETE = some rows, TRUNCATE = all rows but keep the table, DROP = the table is gone."

## Interview Q&A | sky | wide
Q: CHAR vs VARCHAR?
A: CHAR(n) always stores n characters, padded with spaces, which suits fixed-length codes. VARCHAR(n) stores only the actual length up to n, which suits most text.
Q: DECIMAL vs FLOAT?
A: DECIMAL is exact base-10 arithmetic, required for money. FLOAT is approximate binary floating point; it is faster and smaller but has rounding errors.
Q: Can a table have two primary keys?
A: No. It has one primary key, which may span several columns (composite), plus any number of UNIQUE constraints.
Q: Can a foreign key be NULL? Can it reference a non-primary-key column?
A: Yes to both. A NULL FK means "no parent" (unless the column is NOT NULL), and an FK can reference any column set that has a PRIMARY KEY or UNIQUE constraint.
Q: What does ON DELETE CASCADE do, and when is it dangerous?
A: Deleting a parent row automatically deletes its children. It is dangerous on deep hierarchies, where one delete can silently remove a large amount of data.
Q: DELETE vs TRUNCATE vs DROP?
A: DELETE removes selected rows with full logging and triggers. TRUNCATE quickly empties the whole table and resets identity. DROP removes the table itself.
Q: What is referential integrity?
A: The guarantee that every foreign key value matches an existing parent key, enforced by FK constraints.
Q: What is a CHECK constraint?
A: A per-row boolean rule the database enforces on INSERT and UPDATE, for example `CHECK (end_date >= start_date)`.
Q: Why does SQL Server reject a second NULL in my UNIQUE column?
A: SQL Server treats NULLs as equal for UNIQUE constraints. Use a filtered unique index `WHERE col IS NOT NULL`.
Q: Which timestamp type should you use?
A: An absolute, time-zone-aware type stored in UTC: TIMESTAMPTZ in PostgreSQL, DATETIMEOFFSET or UTC DATETIME2 in SQL Server, and in MySQL TIMESTAMP (watch its 2038 limit) or DATETIME holding UTC values.

# 04 | DML: INSERT, UPDATE, DELETE & Upsert | Inserting rows, updating with joins, deleting safely, RETURNING and OUTPUT, upsert per dialect, MERGE, transactions around DML | DML & Upsert

## INSERT | rose
```sql
INSERT INTO departments (id, name) VALUES (5, 'Finance');                    -- one row
INSERT INTO departments (id, name) VALUES (6, 'Legal'), (7, 'Support');      -- several rows in one statement
INSERT INTO customers (id, name, city)                                       -- copy rows from a query
SELECT id + 100, name, city FROM employees WHERE dept_id = 2;
```
- **Always list the columns**: the statement keeps working when columns are added. Omitted columns get their DEFAULT or NULL.
- Multi-row inserts are far faster than one statement per row (one round trip, one commit). For bulk loads use `COPY` (PostgreSQL), `LOAD DATA INFILE` (MySQL) or `BULK INSERT` / `bcp` (SQL Server).
- **Identity columns**: don't send the id. Read it back with `RETURNING id` (PostgreSQL), `OUTPUT inserted.id` or `SCOPE_IDENTITY()` (SQL Server), `LAST_INSERT_ID()` (MySQL).
- `INSERT INTO ... SELECT` adds rows to an existing table; `SELECT ... INTO new_table` (SQL Server) and `CREATE TABLE ... AS SELECT` create a new one.

## UPDATE | blue
```sql
UPDATE employees SET salary = salary * 1.10 WHERE dept_id = 2;               -- 3 rows
UPDATE employees SET city = 'Hyderabad', email = 'john@corp.com' WHERE id = 4;
```
- **An UPDATE without WHERE changes every row.** Run the WHERE as a SELECT first, work inside a transaction, and in MySQL Workbench keep "safe updates" on.
- Updating from another table is dialect-specific:
```sql PostgreSQL
UPDATE orders o
SET status = 'priority'
FROM customers c
WHERE c.id = o.customer_id AND c.city = 'Mumbai';        -- orders 101, 102, 106
```
```sql MySQL
UPDATE orders o
JOIN customers c ON c.id = o.customer_id
SET o.status = 'priority'
WHERE c.city = 'Mumbai';
```
```sql SQL-Server
UPDATE o
SET o.status = 'priority'
FROM orders o
JOIN customers c ON c.id = o.customer_id
WHERE c.city = 'Mumbai';
```
- Portable form that works everywhere:
```sql Standard
UPDATE orders SET status = 'priority'
WHERE customer_id IN (SELECT id FROM customers WHERE city = 'Mumbai');
```

## DELETE | green
```sql
DELETE FROM orders WHERE status = 'cancelled';                     -- 1 row (104)
DELETE FROM orders WHERE order_date < DATE '2026-02-01';           -- 2 rows (101, 102)
```
- Same safety rule as UPDATE: no WHERE means every row.
- **Soft delete**: `UPDATE ... SET deleted_at = NOW()` keeps history and allows undo, but every query must then filter `WHERE deleted_at IS NULL`.
- **Large deletes**: run them in batches (`DELETE ... LIMIT 10000` in MySQL, `DELETE TOP (10000)` in SQL Server, or a key range) to avoid long locks, replication lag and log growth. For time-based data, dropping an old partition is cheapest (sheet 18).

## RETURNING and OUTPUT | amber
```sql PostgreSQL
INSERT INTO customers (id, name, city) VALUES (5, 'Esha', 'Goa') RETURNING id, name;          -- 5 | Esha
UPDATE orders SET status = 'shipped' WHERE id = 105 RETURNING id, status;                     -- 105 | shipped
DELETE FROM orders WHERE status = 'cancelled' RETURNING id;                                   -- 104
```
```sql SQL-Server
INSERT INTO customers (id, name, city) OUTPUT inserted.id, inserted.name VALUES (5, 'Esha', 'Goa');
UPDATE orders SET status = 'shipped'
OUTPUT deleted.status AS old_status, inserted.status AS new_status
WHERE id = 105;
```
- One round trip instead of a write followed by a SELECT. MySQL has no equivalent (`LAST_INSERT_ID()` gives only the last generated id).

## Upsert: Insert or Update | violet
```sql PostgreSQL
INSERT INTO customers (id, name, city) VALUES (2, 'Bina', 'Noida')
ON CONFLICT (id) DO UPDATE SET city = EXCLUDED.city;      -- EXCLUDED = the row you tried to insert

INSERT INTO customers (id, name, city) VALUES (2, 'Bina', 'Noida')
ON CONFLICT (id) DO NOTHING;                               -- insert only if absent
```
```sql MySQL
INSERT INTO customers (id, name, city) VALUES (2, 'Bina', 'Noida') AS new
ON DUPLICATE KEY UPDATE city = new.city;                  -- row alias, 8.0.19+ (older: city = VALUES(city))

INSERT IGNORE INTO customers (id, name, city) VALUES (2, 'Bina', 'Noida');   -- skips duplicates, but also hides other errors
REPLACE INTO customers (id, name, city) VALUES (2, 'Bina', 'Noida');         -- DELETE + INSERT: fires delete triggers and cascades
```
- **MERGE** (SQL:2003; SQL Server, Oracle, PostgreSQL 15+) compares a source with a target and inserts, updates or deletes in one statement:
```sql SQL-Server
MERGE INTO customers AS t
USING (VALUES (2, 'Bina', 'Noida')) AS s (id, name, city)
ON t.id = s.id
WHEN MATCHED THEN UPDATE SET t.city = s.city
WHEN NOT MATCHED THEN INSERT (id, name, city) VALUES (s.id, s.name, s.city);   -- MERGE must end with ;
```
```sql PostgreSQL
MERGE INTO customers t
USING (VALUES (2, 'Bina', 'Noida')) AS s (id, name, city)
ON t.id = s.id
WHEN MATCHED THEN UPDATE SET city = s.city
WHEN NOT MATCHED THEN INSERT (id, name, city) VALUES (s.id, s.name, s.city);
```
- Concurrency: PostgreSQL's `ON CONFLICT` is atomic even when two sessions upsert the same key at once; `MERGE` can still fail with a unique violation under that race. In SQL Server, add `WITH (HOLDLOCK)` on the MERGE target to make it race-free.

## Transactions Around DML | sky
```sql transaction
BEGIN;                                   -- MySQL: START TRANSACTION   SQL Server: BEGIN TRANSACTION
UPDATE accounts SET balance = balance - 500 WHERE id = 1;
UPDATE accounts SET balance = balance + 500 WHERE id = 2;
COMMIT;                                  -- or ROLLBACK to undo both updates
```
- **Autocommit**: by default MySQL, PostgreSQL and SQL Server commit each statement on its own unless you open a transaction. Oracle has no server autocommit; SQL*Plus and SQL Developer leave it off, so you COMMIT explicitly.
- Group related writes in one transaction so they succeed or fail together (sheet 15).

## Interview Q&A | sky | wide
Q: How do you insert many rows efficiently?
A: Use multi-row INSERT statements in one transaction, or bulk loaders (COPY, LOAD DATA INFILE, BULK INSERT). Avoid one round trip and one commit per row.
Q: How do you get the id of a row you just inserted?
A: PostgreSQL `RETURNING id`, SQL Server `OUTPUT inserted.id` or `SCOPE_IDENTITY()`, MySQL `LAST_INSERT_ID()`.
Q: What happens if you run UPDATE without WHERE?
A: Every row in the table is updated. Protect yourself with a SELECT preview, a transaction and safe-update settings.
Q: How do you update a table using values from another table?
A: PostgreSQL uses `UPDATE ... FROM`, MySQL uses `UPDATE ... JOIN ... SET`, SQL Server uses `UPDATE alias SET ... FROM ... JOIN`. The portable form is a subquery in SET or WHERE.
Q: What is an upsert?
A: Insert a row, or update it if the key already exists, in one atomic statement: ON CONFLICT in PostgreSQL, ON DUPLICATE KEY UPDATE in MySQL, MERGE in SQL Server and Oracle.
Q: REPLACE INTO vs INSERT ... ON DUPLICATE KEY UPDATE?
A: REPLACE deletes the old row and inserts a new one, so it fires delete triggers, cascades to children and resets unlisted columns. ON DUPLICATE KEY UPDATE changes only the listed columns of the existing row.
Q: Soft delete vs hard delete?
A: A hard delete removes the row. A soft delete marks it (deleted_at) to keep history and allow undo, at the cost of filtering every query and larger tables.
Q: INSERT INTO ... SELECT vs SELECT ... INTO?
A: INSERT INTO ... SELECT appends query results into an existing table. SELECT ... INTO (SQL Server) creates a new table from the results.

# 05 | Day 1 · Basics: SELECT, FROM, WHERE, ORDER BY, LIMIT | Choosing columns, aliases, DISTINCT, filtering rows, sorting, NULL ordering, LIMIT/TOP/FETCH, pagination, logical order of execution | Day 1: Basics

## SELECT and FROM | rose
```sql
SELECT * FROM employees;                                  -- every column (avoid in application code)
SELECT name, salary FROM employees;                       -- projection: choose columns
SELECT name, salary * 1.10 AS raised_salary FROM employees;   -- expressions with a column alias
SELECT e.name, e.salary FROM employees AS e;              -- table alias (AS is optional)
SELECT DISTINCT city FROM employees;                      -- 6 rows: 5 cities + one NULL
SELECT DISTINCT dept_id, city FROM employees;             -- distinct combinations of both columns
SELECT 2 + 3 AS five, UPPER('sql') AS shout;              -- no FROM needed (Oracle before 23ai: FROM dual)
```
- `FROM` names the table(s); `SELECT` picks the columns or expressions to return.
- **Avoid `SELECT *`** in real code: it sends unneeded data, prevents covering-index plans and breaks when columns change. It is fine for quick exploration.
- **Aliases**: `AS raised_salary`. Aliases with spaces need quoting: `"Raised Salary"` (standard), `[Raised Salary]` (SQL Server), backticks (MySQL).
- `DISTINCT` removes duplicate **rows** (it applies to the whole select list, not one column) and treats all NULLs as one value.

## WHERE | blue
```sql
SELECT name, salary FROM employees WHERE salary > 100000;                 -- Asha, Ravi, Meera
SELECT name FROM employees WHERE city = 'Mumbai';                         -- Priya, Karan
SELECT name FROM employees WHERE hire_date >= DATE '2022-01-01';          -- John, Sara, Neha
SELECT name FROM employees WHERE dept_id <> 1;                            -- Priya, Karan, Sara, Vikram
```
- Comparison operators: `=`, `<>` (or `!=`), `<`, `>`, `<=`, `>=`. Strings and dates go in **single quotes**.
- `DATE '2022-01-01'` is a standard date literal. A plain `'2022-01-01'` string is also converted automatically in most databases.
- WHERE keeps only rows where the condition is **TRUE**. `dept_id <> 1` does not return Neha: her `dept_id` is NULL and any comparison with NULL is unknown (Day 2).
- WHERE runs **before** grouping, so it cannot use aggregates (`WHERE COUNT(*) > 1` is an error; use HAVING) or SELECT aliases.

## ORDER BY | green
```sql
SELECT name, salary FROM employees ORDER BY salary DESC;                   -- highest first
SELECT name, dept_id, salary FROM employees ORDER BY dept_id, salary DESC; -- sort by department, then salary within it
SELECT name, salary * 1.10 AS raised FROM employees ORDER BY raised;       -- ORDER BY can use a SELECT alias
SELECT name, city FROM employees ORDER BY city NULLS LAST;                 -- PostgreSQL, Oracle, SQLite
SELECT name, city FROM employees ORDER BY city IS NULL, city;              -- MySQL-friendly way to put NULLs last
```
- `ASC` (default) or `DESC`, per column. Later columns break ties.
- **Without ORDER BY, row order is not guaranteed**, even if it looks stable today. It can change with a new plan, parallelism or an update.
- You may sort by a column that is not selected (except with `SELECT DISTINCT`), by an expression, or by position (`ORDER BY 2`, fragile).
- SQL Server has no `NULLS LAST`: use `ORDER BY CASE WHEN city IS NULL THEN 1 ELSE 0 END, city`.

## LIMIT, TOP, FETCH and Pagination | amber
```sql
SELECT name, salary FROM employees ORDER BY salary DESC LIMIT 3;            -- Asha, then Ravi and Meera (tied: either order)
SELECT name, salary FROM employees ORDER BY salary DESC LIMIT 3 OFFSET 3;   -- page 2: Sara, Priya, John
SELECT name, salary FROM employees ORDER BY salary DESC
OFFSET 3 ROWS FETCH NEXT 3 ROWS ONLY;                                       -- standard form, same result
SELECT name, salary FROM employees ORDER BY salary DESC
FETCH FIRST 2 ROWS WITH TIES;                                               -- 3 rows: Meera ties with Ravi
```
```sql SQL-Server
SELECT TOP (3) name, salary FROM employees ORDER BY salary DESC;
SELECT TOP (2) WITH TIES name, salary FROM employees ORDER BY salary DESC;
SELECT name, salary FROM employees ORDER BY salary DESC OFFSET 3 ROWS FETCH NEXT 3 ROWS ONLY;
```
- MySQL also accepts `LIMIT offset, count` (`LIMIT 3, 3` = page 2).
- **Always pair LIMIT with ORDER BY**, otherwise "the top 3" is three arbitrary rows.
- Page formula: `OFFSET (page - 1) * size`.
- **OFFSET gets slow on deep pages**: the database still reads and discards every skipped row, and rows shift between page loads. **Keyset (seek) pagination** remembers the last row and continues after it, using an index:
```sql
-- next page after the last row seen (salary 95000, id 5), newest-highest first
SELECT id, name, salary FROM employees
WHERE (salary, id) < (95000, 5)
ORDER BY salary DESC, id DESC
LIMIT 3;                                                                    -- John, Karan, Vikram
```
- Row-value comparison `(a, b) < (x, y)` works in PostgreSQL and MySQL. In SQL Server write `salary < 95000 OR (salary = 95000 AND id < 5)`.

## Logical Order of Execution | violet
```text
1. FROM / JOIN    pick and combine the tables
2. WHERE          filter rows
3. GROUP BY       form groups
4. HAVING         filter groups
5. SELECT         compute expressions, aliases, window functions
6. DISTINCT       remove duplicate rows
7. ORDER BY       sort (can see SELECT aliases)
8. LIMIT / OFFSET cut the result (TOP / FETCH)
```
- This explains the classic errors: a SELECT alias is **not visible in WHERE** (WHERE runs first), aggregates are **not allowed in WHERE** (use HAVING), **window functions can't be filtered in WHERE** (wrap the query in a CTE or subquery), and **ORDER BY can use aliases** (it runs after SELECT).
- MySQL also allows aliases in GROUP BY and HAVING, and PostgreSQL allows them in GROUP BY; SQL Server allows neither.
- This is the **logical** order. The optimiser may physically do things in any order that gives the same result (for example pushing filters into joins).

## Interview Q&A | sky | wide
Q: What is the logical order of execution of a SELECT?
A: FROM and JOIN, WHERE, GROUP BY, HAVING, SELECT, DISTINCT, ORDER BY, then LIMIT or OFFSET.
Q: Why can't I use a column alias in WHERE?
A: WHERE is evaluated before SELECT, so the alias doesn't exist yet. Repeat the expression, or wrap the query in a subquery or CTE. ORDER BY can use it because it runs after SELECT.
Q: Is the order of rows guaranteed without ORDER BY?
A: No. Tables are unordered sets; without ORDER BY the database returns rows in whatever order its plan produces.
Q: DISTINCT vs GROUP BY?
A: `SELECT DISTINCT a, b` and `GROUP BY a, b` return the same rows. Use GROUP BY when you also compute aggregates per group, DISTINCT when you just want unique rows.
Q: How do you get the top 5 rows in MySQL, SQL Server and Oracle?
A: MySQL and PostgreSQL `ORDER BY ... LIMIT 5`; SQL Server `SELECT TOP (5) ... ORDER BY ...`; Oracle 12c+ `ORDER BY ... FETCH FIRST 5 ROWS ONLY`.
Q: OFFSET vs keyset pagination?
A: OFFSET is simple and allows jumping to any page, but slows down on deep pages and can skip or repeat rows when data changes. Keyset pagination filters after the last seen key, stays fast with an index and is stable, but only supports next and previous.
Q: Does DISTINCT treat NULLs as equal?
A: Yes. All NULLs collapse into a single row in DISTINCT, GROUP BY and set operations, even though `NULL = NULL` is not true in a WHERE clause.
Q: What is the difference between WHERE and ORDER BY on performance?
A: WHERE reduces rows early and can use indexes to avoid reading the table. ORDER BY needs a sort unless an index already provides the order, which is why `ORDER BY ... LIMIT` queries benefit from an index on the sort column.

# 06 | Day 2 · Filtering: AND, OR, NOT, IN, BETWEEN, LIKE, NULL | Combining conditions, precedence, lists, ranges, pattern matching, NULL and three-valued logic | Day 2: Filtering

## AND, OR, NOT and Precedence | rose
```sql
SELECT name FROM employees WHERE dept_id = 1 AND salary >= 120000;          -- Asha, Ravi, Meera
SELECT name FROM employees WHERE city = 'Delhi' OR city = 'Pune';           -- Sara, Vikram, Neha
SELECT name FROM employees WHERE NOT dept_id = 1;                           -- Priya, Karan, Sara, Vikram (not Neha)

-- Precedence: NOT first, then AND, then OR
SELECT name FROM employees WHERE dept_id = 2 OR dept_id = 3 AND salary > 90000;
-- read as: dept_id = 2 OR (dept_id = 3 AND salary > 90000)  →  Priya, Karan, Sara
SELECT name FROM employees WHERE (dept_id = 2 OR dept_id = 3) AND salary > 90000;
-- →  Priya, Sara
```
- `AND`: both conditions true. `OR`: at least one true. `NOT`: inverts.
- **Precedence: NOT > AND > OR.** Mixing AND and OR without parentheses is a classic bug. **Always add parentheses.**
- De Morgan's laws: `NOT (a AND b)` = `NOT a OR NOT b`; `NOT (a OR b)` = `NOT a AND NOT b`.

## IN and NOT IN | blue
```sql
SELECT name FROM employees WHERE city IN ('Mumbai', 'Delhi');           -- Priya, Karan, Sara, Vikram
SELECT name FROM employees WHERE dept_id NOT IN (1, 2);                 -- Vikram (Neha's NULL dept_id is unknown)
SELECT name FROM customers
WHERE id IN (SELECT customer_id FROM orders WHERE amount > 200);        -- Anil, Bina
```
- `x IN (a, b, c)` is shorthand for `x = a OR x = b OR x = c`. The list can be a subquery.
- **The NOT IN trap**: if the list or subquery contains a NULL, `x NOT IN (...)` can never be TRUE, so the query returns **no rows**:
```sql
SELECT name FROM employees
WHERE id NOT IN (SELECT manager_id FROM employees);     -- 0 rows! Asha's manager_id is NULL

SELECT name FROM employees e
WHERE NOT EXISTS (SELECT 1 FROM employees r WHERE r.manager_id = e.id);
-- non-managers: Meera, John, Karan, Sara, Vikram, Neha
```
- Why: `5 NOT IN (1, NULL)` means `5 <> 1 AND 5 <> NULL` = `TRUE AND UNKNOWN` = UNKNOWN. **Prefer NOT EXISTS**, or filter NULLs out of the subquery.

## BETWEEN | green
```sql
SELECT name, salary FROM employees WHERE salary BETWEEN 90000 AND 120000;
-- inclusive at both ends: Ravi, Meera, John, Priya, Sara
SELECT name FROM employees WHERE hire_date BETWEEN '2020-01-01' AND '2021-12-31';   -- Meera, Karan, Vikram
SELECT name FROM employees WHERE salary NOT BETWEEN 70000 AND 120000;               -- Asha, Vikram, Neha
```
- `x BETWEEN a AND b` = `x >= a AND x <= b`. The low value must come first: `BETWEEN 120000 AND 90000` returns nothing (PostgreSQL has `BETWEEN SYMMETRIC`).
- Works for numbers, dates and strings (`name BETWEEN 'A' AND 'M'` compares alphabetically by collation).
- **Timestamp trap**: `created_at BETWEEN '2026-01-01' AND '2026-01-31'` stops at midnight at the start of the 31st and misses the rest of that day. Use a **half-open range**: `created_at >= '2026-01-01' AND created_at < '2026-02-01'`.

## LIKE: Pattern Matching | amber
```sql
SELECT name FROM employees WHERE name LIKE 'S%';          -- starts with S: Sara
SELECT name FROM employees WHERE name LIKE '%a';          -- ends with a: Asha, Meera, Priya, Sara, Neha
SELECT name FROM employees WHERE name LIKE '%av%';        -- contains "av": Ravi
SELECT name FROM employees WHERE name LIKE '_a%';         -- second letter a: Ravi, Karan, Sara
SELECT name FROM employees WHERE name LIKE '____';        -- exactly 4 characters: Asha, Ravi, John, Sara, Neha
SELECT name FROM employees WHERE name ILIKE 'asha';       -- PostgreSQL case-insensitive LIKE: Asha
```
- Wildcards: **`%`** = any sequence of characters (including none), **`_`** = exactly one character.
- Literal `%` or `_`: escape it. `LIKE '50\%%'` (backslash is the default escape in PostgreSQL and MySQL) or `LIKE '50!%%' ESCAPE '!'` (portable; SQL Server has no default escape, but also accepts `[%]`).
- SQL Server adds character sets: `LIKE '[A-C]%'`, `LIKE '[^A-C]%'`.
- **Case sensitivity** follows the collation: MySQL and SQL Server usually ignore case; PostgreSQL does not, so use `ILIKE` or `LOWER(name) LIKE 'asha%'`.
- **Regular expressions**: PostgreSQL `~` and `~*`; MySQL `REGEXP` / `REGEXP_LIKE()`; Oracle `REGEXP_LIKE()`; SQL Server 2025 adds `REGEXP_LIKE()`.
- Performance: `LIKE 'abc%'` (fixed prefix) can use a B-tree index; **`LIKE '%abc'` cannot** (leading wildcard). PostgreSQL can index it with a trigram GIN index (`pg_trgm`); otherwise use full-text search.

## NULL and Three-Valued Logic | violet
```sql
SELECT name FROM employees WHERE city IS NULL;                     -- John
SELECT name FROM employees WHERE city = NULL;                      -- 0 rows, always
SELECT name FROM employees WHERE email IS NOT NULL AND city IS NOT NULL;   -- everyone except John
SELECT NULL = NULL AS equal, NULL IS NULL AS is_null;              -- NULL | true
SELECT name FROM employees WHERE city IS DISTINCT FROM 'Mumbai';   -- NULL-safe <>: includes John
```
- **NULL means unknown or missing**. It is not 0 and not an empty string (except in Oracle, where `''` is NULL).
- Any comparison with NULL (`=`, `<>`, `<`, `>`) gives **UNKNOWN**, and WHERE keeps only TRUE. So `= NULL` never matches: use **`IS NULL` / `IS NOT NULL`**.
- Truth table: `TRUE AND UNKNOWN = UNKNOWN`, `FALSE AND UNKNOWN = FALSE`, `TRUE OR UNKNOWN = TRUE`, `FALSE OR UNKNOWN = UNKNOWN`, `NOT UNKNOWN = UNKNOWN`.
- **NULL-safe comparison**: `IS DISTINCT FROM` / `IS NOT DISTINCT FROM` (standard; PostgreSQL, SQL Server 2022+); MySQL uses `<=>` (`NOT (city <=> 'Mumbai')`).
- Arithmetic with NULL gives NULL (`salary + NULL`). Concatenation: `'a' || NULL` is NULL in PostgreSQL but `'a'` in Oracle; MySQL `CONCAT('a', NULL)` is NULL; `CONCAT()` in PostgreSQL and SQL Server skips NULLs.
- Aggregates skip NULLs (Day 3). Replace NULLs with `COALESCE` (sheet 07).
- Empty or NULL check: `WHERE col IS NULL OR col = ''`, or `WHERE COALESCE(col, '') = ''`.

## Interview Q&A | sky | wide
Q: Why does `WHERE col = NULL` return nothing?
A: Comparing anything with NULL yields UNKNOWN, not TRUE, and WHERE only keeps TRUE rows. Use `IS NULL`.
Q: Explain the NOT IN NULL problem.
A: If the subquery returns a NULL, `x NOT IN (..., NULL)` expands to `... AND x <> NULL`, which is UNKNOWN for every row, so nothing is returned. Use NOT EXISTS or add `WHERE col IS NOT NULL` to the subquery.
Q: Is BETWEEN inclusive?
A: Yes, at both ends. For timestamps use a half-open range (`>= start AND < next_day`) to avoid missing the last day.
Q: What is the difference between `%` and `_` in LIKE?
A: `%` matches any number of characters including zero; `_` matches exactly one character.
Q: What is the precedence of AND and OR?
A: NOT binds tightest, then AND, then OR. `a OR b AND c` means `a OR (b AND c)`; use parentheses.
Q: How do you search case-insensitively?
A: In PostgreSQL use ILIKE or compare `LOWER(col)`, ideally with an expression index. In MySQL and SQL Server the default collation is already case-insensitive.
Q: IN vs multiple ORs?
A: They are logically the same. IN is shorter and clearer, and optimisers treat a list of constants efficiently. For very long lists, join to a temporary table or VALUES list instead.
Q: Why might `LIKE '%term%'` be slow?
A: A leading wildcard prevents a B-tree index seek, so the database scans every row. Use a trigram index (PostgreSQL pg_trgm) or full-text search.
Q: What is three-valued logic?
A: SQL conditions can be TRUE, FALSE or UNKNOWN (because of NULL). WHERE, HAVING and JOIN ON keep only TRUE; CHECK constraints reject only FALSE, so a NULL passes a CHECK.

# 07 | Built-in Functions & NULL Handling | String, numeric, date and conversion functions, COALESCE and NULLIF, with each dialect's names | Functions

## String Functions | rose
```sql
SELECT UPPER(name), LOWER(name), LENGTH(name), CHAR_LENGTH(name)
FROM employees WHERE id = 1;                                        -- ASHA | asha | 4 | 4

SELECT SUBSTRING(email FROM 1 FOR 4), SUBSTRING(email, 1, 4), LEFT(email, 4), RIGHT(email, 8)
FROM employees WHERE id = 1;                                        -- asha | asha | asha | corp.com

SELECT POSITION('@' IN email), SPLIT_PART(email, '@', 2)
FROM employees WHERE id = 1;                                        -- 5 | corp.com  (SPLIT_PART is PostgreSQL)

SELECT TRIM('  hi  '), REPLACE('a-b-c', '-', '/'), LPAD('7', 3, '0'), REVERSE('sql');
-- hi | a/b/c | 007 | lqs

SELECT CONCAT(name, ' - ', city), CONCAT_WS(', ', name, city, 'India')
FROM employees WHERE id = 4;                                        -- 'John - ' | 'John, India'  (NULL city skipped)
```
- Dialect names:
- **Length**: MySQL `LENGTH` = bytes, `CHAR_LENGTH` = characters (they differ for non-ASCII text); SQL Server `LEN` (characters, ignores trailing spaces) and `DATALENGTH` (bytes); PostgreSQL and Oracle `LENGTH` = characters.
- **Substring**: `SUBSTRING` (PostgreSQL, MySQL, SQL Server); Oracle and SQLite `SUBSTR`.
- **Find position**: PostgreSQL `POSITION` / `STRPOS`; MySQL `LOCATE('@', email)` or `INSTR(email, '@')`; SQL Server `CHARINDEX('@', email)`; Oracle `INSTR`.
- **Repeat**: `REPEAT` (PostgreSQL, MySQL) vs `REPLICATE` (SQL Server). **Title case**: `INITCAP` (PostgreSQL, Oracle).
- **Trim**: `TRIM`, `LTRIM`, `RTRIM` everywhere (SQL Server's `TRIM` arrived in 2017).

## Numeric Functions | blue
```sql
SELECT ROUND(123.456, 2), ROUND(123.456), CEIL(4.1), FLOOR(4.9), ABS(-5), MOD(17, 5), POWER(2, 10), SQRT(16);
-- 123.46 | 123 | 5 | 4 | 5 | 2 | 1024 | 4

SELECT 7 / 2 AS int_div, 7 / 2.0 AS dec_div, 7 % 2 AS remainder, TRUNC(9.876, 1) AS cut;
-- PostgreSQL: 3 | 3.5000000000000000 | 1 | 9.8
```
- Integer division truncates in PostgreSQL, SQL Server and SQLite (`7 / 2 = 3`). MySQL returns `3.5000` (use `DIV` for integer division); Oracle returns `3.5`. To force decimals, make one side decimal: `7 * 1.0 / 2` or `CAST(7 AS DECIMAL(10,2)) / 2`.
- SQL Server has `CEILING` (no `CEIL`) and the `%` operator (no `MOD()`).
- Truncate without rounding: `TRUNC` (PostgreSQL, Oracle), `TRUNCATE(x, d)` (MySQL), `ROUND(x, d, 1)` (SQL Server).
- Keep money in DECIMAL and round once, at the end, not at every step.

## Date and Time Functions | green
```sql
SELECT CURRENT_DATE, CURRENT_TIMESTAMP, NOW();

SELECT EXTRACT(YEAR FROM hire_date) AS yr, CAST(DATE_TRUNC('month', hire_date) AS DATE) AS month_start
FROM employees WHERE id = 2;                          -- 2019 | 2019-07-01  (DATE_TRUNC returns a timestamp)

SELECT hire_date + INTERVAL '30 days', hire_date + 30, DATE '2026-03-01' - DATE '2026-01-01'
FROM employees WHERE id = 2;                          -- 2019-08-14 00:00:00 | 2019-08-14 | 59

SELECT AGE(DATE '2026-10-14', hire_date) FROM employees WHERE id = 1;     -- 8 years 7 mons 13 days
SELECT TO_CHAR(hire_date, 'DD Mon YYYY') FROM employees WHERE id = 1;     -- 01 Mar 2018
```
- PostgreSQL: `date + integer` adds days, `date - date` gives days as an integer, `date + INTERVAL` gives a timestamp.
- **MySQL**: `YEAR(d)`, `MONTH(d)`, `DATE_FORMAT(d, '%d %b %Y')`, `DATE_ADD(d, INTERVAL 30 DAY)`, `DATEDIFF(a, b)` (days), `TIMESTAMPDIFF(MONTH, a, b)`, `LAST_DAY(d)`.
- **SQL Server**: `YEAR(d)`, `DATEPART(month, d)`, `FORMAT(d, 'dd MMM yyyy')`, `DATEADD(day, 30, d)`, `DATEDIFF(day, a, b)`, `EOMONTH(d)`, `DATETRUNC(month, d)` (2022+).
- **Oracle**: `EXTRACT`, `TO_CHAR(d, 'DD Mon YYYY')`, `ADD_MONTHS(d, 1)`, `MONTHS_BETWEEN`, `TRUNC(d, 'MM')`, `LAST_DAY`.
- `EXTRACT(part FROM d)` is standard SQL and works in PostgreSQL, MySQL and Oracle.
- To filter by year, compare the raw column with a range instead of wrapping it in a function, so an index can be used (sheet 16).

## Conversion | amber
```sql
SELECT CAST('42' AS INT) + 1, CAST(salary AS INT), '2026-01-31'::DATE
FROM employees WHERE id = 1;                          -- 43 | 150000 | 2026-01-31  (:: is PostgreSQL shorthand)
SELECT CAST(7 AS DECIMAL(10,2)) / 2;                  -- 3.5000000000000000
```
- `CAST(x AS type)` is standard. **MySQL does not accept `INT` as a CAST target**: use `CAST(x AS SIGNED)` or `UNSIGNED`.
- SQL Server: `CONVERT(INT, '42')`, and `TRY_CAST` / `TRY_CONVERT` return NULL instead of failing. Oracle: `TO_NUMBER`, `TO_DATE`, `TO_CHAR`. PostgreSQL also has `TO_DATE`, `TO_NUMBER`, `TO_CHAR`.
- **Implicit conversion**: MySQL is lenient (`'5abc' + 1` gives 6 with a warning); PostgreSQL is strict and raises an error. Comparing a string column with a number (`WHERE phone = 98765`) forces a conversion per row and can stop index use.

## NULL Handling Functions | violet
```sql
SELECT name, COALESCE(city, email, 'unknown') AS location_or_contact
FROM employees WHERE id = 4;                          -- John | unknown  (city and email are both NULL)

SELECT NULLIF(0, 0), NULLIF(5, 0), 10 / NULLIF(0, 0); -- NULL | 5 | NULL  (no divide-by-zero error)

SELECT GREATEST(3, 7, 5), LEAST(3, 7, 5);             -- 7 | 3
```
- **`COALESCE(a, b, c, ...)`** returns the first non-NULL argument. Standard and available everywhere.
- Two-argument variants: `IFNULL(a, b)` (MySQL, SQLite), `ISNULL(a, b)` (SQL Server; the result takes the **first argument's type**, so a longer replacement can be truncated), `NVL(a, b)` (Oracle). Oracle also has `NVL2(x, if_not_null, if_null)`.
- **`NULLIF(a, b)`** returns NULL when `a = b`, otherwise `a`. The classic guard against division by zero: `total / NULLIF(count, 0)`.
- `GREATEST` / `LEAST`: PostgreSQL ignores NULL arguments; MySQL and Oracle return NULL if any argument is NULL. SQL Server added them in 2022.

## Interview Q&A | sky | wide
Q: COALESCE vs ISNULL?
A: COALESCE is standard, takes any number of arguments and returns the type with the highest precedence among them. ISNULL is SQL Server-only, takes two arguments and uses the first argument's type, which can truncate the replacement.
Q: How do you avoid a divide-by-zero error?
A: Wrap the divisor in NULLIF: `a / NULLIF(b, 0)` returns NULL instead of failing, and COALESCE can turn that NULL into 0 if needed.
Q: How do you get the year from a date in each database?
A: `EXTRACT(YEAR FROM d)` in PostgreSQL, MySQL and Oracle; `YEAR(d)` in MySQL and SQL Server; `DATEPART(year, d)` in SQL Server.
Q: LENGTH vs CHAR_LENGTH in MySQL?
A: LENGTH counts bytes and CHAR_LENGTH counts characters, so they differ for multi-byte UTF-8 text such as 'café'.
Q: CAST vs CONVERT?
A: CAST is standard SQL. CONVERT is the SQL Server (and MySQL) function; in SQL Server it also accepts a style code for date formatting.
Q: Why does `7 / 2` return 3?
A: Both operands are integers, so PostgreSQL, SQL Server and SQLite do integer division. Make one operand decimal to get 3.5.
Q: How do you concatenate a column that may be NULL?
A: Use `CONCAT()` (which skips NULLs in PostgreSQL and SQL Server) or wrap the column in COALESCE before using `||` or `+`.
Q: How do you format a date as text?
A: `TO_CHAR` in PostgreSQL and Oracle, `DATE_FORMAT` in MySQL, `FORMAT` or `CONVERT` with a style in SQL Server. Do formatting in the application when possible.

# 08 | Day 3 · Aggregations: COUNT, SUM, AVG, MIN, MAX, GROUP BY, HAVING | Aggregate functions and NULLs, grouping rules, HAVING vs WHERE, conditional aggregation, string aggregation | Day 3: Aggregations

## Aggregate Functions | rose
```sql
SELECT COUNT(*)              AS total_rows,
       COUNT(email)          AS with_email,
       COUNT(DISTINCT city)  AS cities,
       SUM(salary)           AS payroll,
       ROUND(AVG(salary), 2) AS avg_salary,
       MIN(hire_date)        AS first_hire,
       MAX(salary)           AS top_salary
FROM employees;
-- 9 | 8 | 5 | 868000.00 | 96444.44 | 2018-03-01 | 150000.00
```
- An aggregate turns many rows into **one value**.
- **`COUNT(*)`** counts rows. **`COUNT(col)`** counts **non-NULL** values (John has no email, so 8). **`COUNT(DISTINCT col)`** counts distinct non-NULL values (5 cities; John's NULL is ignored).
- `COUNT(1)` is the same as `COUNT(*)`: no performance difference in modern databases.
- **SUM, AVG, MIN, MAX ignore NULLs.** So `AVG(col)` = `SUM(col) / COUNT(col)`, not divided by `COUNT(*)`. Use `AVG(COALESCE(col, 0))` if a missing value should count as zero.
- **Empty input**: COUNT returns 0, the others return **NULL**. Write `COALESCE(SUM(amount), 0)` when you need 0.
- **AVG of an integer column**: SQL Server returns an integer (truncated), so write `AVG(col * 1.0)`. PostgreSQL returns numeric and MySQL a decimal.
- MIN and MAX also work on text (alphabetical by collation) and dates.

## GROUP BY | blue
```sql
SELECT dept_id, COUNT(*) AS headcount, ROUND(AVG(salary), 2) AS avg_salary, MAX(salary) AS max_salary
FROM employees
GROUP BY dept_id
ORDER BY dept_id;
-- 1    | 4 | 120000.00 | 150000.00
-- 2    | 3 |  87666.67 |  98000.00
-- 3    | 1 |  65000.00 |  65000.00
-- NULL | 1 |  60000.00 |  60000.00     ← all NULL keys form one group
```
- GROUP BY returns **one row per distinct value** (or combination) of the grouping columns, and aggregates are computed per group.
- **Rule**: every column in SELECT must be **in GROUP BY or inside an aggregate**. Otherwise the database cannot know which row's value to show. MySQL enforces this with `ONLY_FULL_GROUP_BY` (on by default since 5.7.5); PostgreSQL also accepts columns that depend on a grouped primary key.
- Group by several columns (`GROUP BY dept_id, city`) or by an expression (`GROUP BY EXTRACT(YEAR FROM hire_date)`).
- To show names with counts, join first and group by the name. Use **`COUNT(e.id)`, not `COUNT(*)`**, so departments without employees show 0:
```sql
SELECT d.name AS department, COUNT(e.id) AS headcount, COALESCE(SUM(e.salary), 0) AS payroll
FROM departments d
LEFT JOIN employees e ON e.dept_id = d.id
GROUP BY d.name
ORDER BY headcount DESC, department;
-- Engineering 4 480000.00 | Sales 3 263000.00 | HR 1 65000.00 | Marketing 0 0
```
```sql
SELECT EXTRACT(YEAR FROM order_date) AS yr, EXTRACT(MONTH FROM order_date) AS mon,
       COUNT(*) AS orders, SUM(amount) AS revenue
FROM orders
GROUP BY EXTRACT(YEAR FROM order_date), EXTRACT(MONTH FROM order_date)
ORDER BY yr, mon;
-- 2026 1 2 370.00 | 2026 2 2 640.00 | 2026 3 2 390.00
```

## HAVING | green
```sql
SELECT dept_id, COUNT(*) AS headcount
FROM employees
GROUP BY dept_id
HAVING COUNT(*) >= 3
ORDER BY dept_id;                         -- 1 | 4,  2 | 3

SELECT customer_id, SUM(amount) AS spent
FROM orders
WHERE status <> 'cancelled'               -- WHERE filters rows before grouping
GROUP BY customer_id
HAVING SUM(amount) > 400                  -- HAVING filters groups after aggregation
ORDER BY spent DESC;                      -- 2 | 860.00,  1 | 460.00
```
- **WHERE vs HAVING**: WHERE filters **rows** before grouping and **cannot** use aggregates. HAVING filters **groups** after aggregation and usually does.
- Put plain row conditions in WHERE: fewer rows reach the grouping step, and indexes can help.
- HAVING without GROUP BY treats the whole table as one group: `SELECT COUNT(*) FROM orders HAVING COUNT(*) > 5` returns one row or none.
- MySQL allows a SELECT alias in HAVING (`HAVING spent > 400`); PostgreSQL and SQL Server need the expression repeated.
- **Find duplicates** (a top interview question): `GROUP BY email HAVING COUNT(*) > 1` (sheet 19).

## Conditional Aggregation | amber
```sql
SELECT COUNT(*) FILTER (WHERE status = 'delivered')                 AS delivered,   -- PostgreSQL, SQLite
       SUM(CASE WHEN status = 'pending' THEN 1 ELSE 0 END)          AS pending,     -- portable
       SUM(CASE WHEN status <> 'cancelled' THEN amount ELSE 0 END)  AS revenue
FROM orders;
-- 2 | 2 | 1320.00
```
- An aggregate over a **CASE** expression counts or sums only the rows that meet a condition, all in one pass over the table. `COUNT(CASE WHEN cond THEN 1 END)` works too, because COUNT skips the NULL from a missing ELSE.
- This is how you **pivot** rows into columns: one CASE per output column (SQL Server and Oracle also have a `PIVOT` operator).
- PostgreSQL's `FILTER (WHERE ...)` clause is the standard, more readable form.

## String Aggregation | violet
```sql
SELECT dept_id, STRING_AGG(name, ', ' ORDER BY name) AS team
FROM employees
WHERE dept_id IS NOT NULL
GROUP BY dept_id
ORDER BY dept_id;
-- 1 | Asha, John, Meera, Ravi
-- 2 | Karan, Priya, Sara
-- 3 | Vikram
```
```sql MySQL
SELECT dept_id, GROUP_CONCAT(name ORDER BY name SEPARATOR ', ') AS team
FROM employees WHERE dept_id IS NOT NULL GROUP BY dept_id;
```
```sql SQL-Server
SELECT dept_id, STRING_AGG(name, ', ') WITHIN GROUP (ORDER BY name) AS team
FROM employees WHERE dept_id IS NOT NULL GROUP BY dept_id;
```
- Oracle: `LISTAGG(name, ', ') WITHIN GROUP (ORDER BY name)`. MySQL truncates `GROUP_CONCAT` at `group_concat_max_len` (1024 bytes by default).

## Interview Q&A | sky | wide
Q: WHERE vs HAVING?
A: WHERE filters individual rows before grouping and can't use aggregates. HAVING filters groups after GROUP BY and is where aggregate conditions go.
Q: COUNT(*) vs COUNT(1) vs COUNT(column)?
A: COUNT(*) and COUNT(1) both count all rows and perform the same. COUNT(column) counts only rows where that column is not NULL.
Q: How do aggregates handle NULL?
A: SUM, AVG, MIN, MAX and COUNT(col) ignore NULLs; COUNT(*) counts every row. On no rows at all, COUNT gives 0 and the rest give NULL.
Q: Why do I get "column must appear in the GROUP BY clause"?
A: A selected column is neither grouped nor aggregated, so each group has several possible values for it. Add it to GROUP BY or wrap it in an aggregate (MIN, MAX, STRING_AGG).
Q: How do you find duplicate values in a column?
A: `SELECT col, COUNT(*) FROM t GROUP BY col HAVING COUNT(*) > 1`.
Q: Can you nest aggregates, like MAX(COUNT(*))?
A: Not in PostgreSQL, MySQL or SQL Server; Oracle allows one level. Elsewhere aggregate in a subquery or CTE and then take the MAX, or ORDER BY the count with LIMIT 1.
Q: GROUP BY vs DISTINCT?
A: Without aggregates they return the same rows. GROUP BY is needed when you compute per-group values.
Q: How do you count rows per condition in a single query?
A: Conditional aggregation: `SUM(CASE WHEN cond THEN 1 ELSE 0 END)` or `COUNT(*) FILTER (WHERE cond)` in PostgreSQL.
Q: Why does my department with no employees show a count of 1?
A: COUNT(*) after a LEFT JOIN counts the NULL-extended row. Count a column from the right table, such as COUNT(e.id), which ignores NULL.

# 09 | Day 4 · Joins: INNER, LEFT, RIGHT, FULL & More | How joins match rows, outer joins, anti-joins, ON vs WHERE, FULL JOIN in MySQL, CROSS and SELF joins, set operations | Day 4: Joins

## How Joins Work | rose
- A join combines rows from two tables wherever the **ON condition** is true. Conceptually: build every pair of rows (the cartesian product) and keep the pairs that pass ON.
- Outer joins also keep the rows that found **no** partner, filling the other side with NULLs.
```text
employees.dept_id: 1 1 1 1 2 2 2 3 NULL      departments.id: 1 2 3 4 (Marketing)

INNER JOIN  only matching pairs                       8 rows  (Neha and Marketing dropped)
LEFT JOIN   every employee, matched or not            9 rows  (Neha with NULL department)
RIGHT JOIN  every department, matched or not          9 rows  (Marketing with NULL employee)
FULL JOIN   everything from both sides               10 rows
CROSS JOIN  every employee with every department     36 rows  (9 x 4)
```

## INNER JOIN | blue
```sql
SELECT e.name, d.name AS department
FROM employees e
INNER JOIN departments d ON d.id = e.dept_id
ORDER BY e.id;
-- 8 rows: Asha Engineering ... Vikram HR  (no Neha, no Marketing)
```
- `JOIN` alone means `INNER JOIN`.
- Old implicit syntax: `FROM employees e, departments d WHERE d.id = e.dept_id`. It works, but forgetting the condition silently produces a cross join. Prefer explicit JOIN ... ON.
- `JOIN departments USING (id)` works when both columns share the same name. `NATURAL JOIN` joins on **all** same-named columns, so it breaks when someone adds a column: avoid it.
- **Multiple joins** chain left to right:
```sql
SELECT e.name, d.name AS department, m.name AS manager
FROM employees e
LEFT JOIN departments d ON d.id = e.dept_id
LEFT JOIN employees m   ON m.id = e.manager_id
WHERE e.salary > 95000
ORDER BY e.salary DESC, e.id;
-- Asha Engineering NULL | Ravi Engineering Asha | Meera Engineering Asha | Sara Sales Priya
```

## LEFT and RIGHT JOIN | green
```sql
SELECT e.name, d.name AS department
FROM employees e
LEFT JOIN departments d ON d.id = e.dept_id
ORDER BY e.id;                                  -- 9 rows, the last is Neha | NULL

SELECT d.name AS department, e.name
FROM employees e
RIGHT JOIN departments d ON d.id = e.dept_id
ORDER BY d.id, e.id;                            -- 9 rows, the last is Marketing | NULL
```
- `LEFT JOIN` keeps **every row of the left table**; `RIGHT JOIN` keeps every row of the right table. `A RIGHT JOIN B` = `B LEFT JOIN A`, so most teams write only LEFT JOINs.
- **Anti-join**: rows that have **no** match.
```sql
SELECT c.name
FROM customers c
LEFT JOIN orders o ON o.customer_id = c.id
WHERE o.id IS NULL;                             -- Dev: never ordered
```
- **ON vs WHERE in a LEFT JOIN**: a condition on the right table in **WHERE** removes the NULL-extended rows and quietly turns the query into an inner join. Put it in **ON** to keep unmatched left rows:
```sql
SELECT c.name, o.id
FROM customers c
LEFT JOIN orders o ON o.customer_id = c.id AND o.status = 'delivered'
ORDER BY c.id, o.id;
-- 5 rows: Anil 101, Anil 102, Bina NULL, Chen NULL, Dev NULL

SELECT c.name, o.id
FROM customers c
LEFT JOIN orders o ON o.customer_id = c.id
WHERE o.status = 'delivered'
ORDER BY c.id, o.id;
-- 2 rows: Anil 101, Anil 102  (the LEFT JOIN behaved like an INNER JOIN)
```

## FULL OUTER JOIN | amber
```sql
SELECT e.name, d.name AS department
FROM employees e
FULL OUTER JOIN departments d ON d.id = e.dept_id
ORDER BY d.id, e.id;
-- 10 rows, including Neha | NULL and NULL | Marketing
```
```sql MySQL
-- MySQL has no FULL JOIN: combine a LEFT JOIN and the unmatched part of a RIGHT JOIN
SELECT e.name, d.name AS department
FROM employees e LEFT JOIN departments d ON d.id = e.dept_id
UNION ALL
SELECT e.name, d.name
FROM employees e RIGHT JOIN departments d ON d.id = e.dept_id
WHERE e.id IS NULL;
```
- FULL JOIN keeps unmatched rows from **both** sides. Typical use: **reconciliation**, comparing two sources and finding what's missing on either side.
- The shorter MySQL version `LEFT JOIN ... UNION ... RIGHT JOIN` also works, but `UNION` would merge genuinely identical rows, so the `UNION ALL` + `WHERE e.id IS NULL` form is exact.

## CROSS JOIN and SELF JOIN | violet
```sql
SELECT c.name, s.size
FROM customers c
CROSS JOIN (VALUES ('S'), ('M'), ('L')) AS s (size)
ORDER BY c.id, s.size;                          -- 4 customers x 3 sizes = 12 rows

SELECT e.name AS employee, m.name AS manager
FROM employees e
LEFT JOIN employees m ON m.id = e.manager_id    -- the same table twice, with two aliases
ORDER BY e.id;
-- Asha NULL | Ravi Asha | Meera Asha | John Ravi | Priya Asha | Karan Priya | Sara Priya | Vikram Asha | Neha Asha
```
- **CROSS JOIN**: every combination, no ON. Useful for calendars × products or generating test data. An accidental cross join multiplies row counts.
- **SELF JOIN**: a table joined to itself with different aliases. Used for hierarchies (employee → manager), comparing rows in the same table (pairs, previous day), finding duplicates.
- **Non-equi join**: ON can use any condition, for example `ON o.order_date BETWEEN p.starts_on AND p.ends_on` (match orders to price periods).
- **Fan-out trap**: joining a 1:N relationship and then summing a column of the "one" side counts it several times. Aggregate the "many" side in a subquery first, then join.

## Set Operations: UNION, INTERSECT, EXCEPT | sky
```sql
SELECT city FROM employees UNION SELECT city FROM customers ORDER BY city;
-- Bengaluru, Chennai, Delhi, Mumbai, Pune, NULL (distinct values from both)
SELECT city FROM employees UNION ALL SELECT city FROM customers;
-- 13 rows: 9 + 4, duplicates kept
SELECT city FROM employees INTERSECT SELECT city FROM customers ORDER BY city;
-- Delhi, Mumbai, Pune, NULL (in both)
SELECT city FROM employees EXCEPT SELECT city FROM customers ORDER BY city;
-- Bengaluru, Chennai (employees only)
```
- Rules: the queries need the **same number of columns** with compatible types. Column names come from the first query; one ORDER BY goes at the very end.
- **UNION removes duplicates** (an extra sort or hash step); **UNION ALL keeps them** and is faster. Use UNION ALL unless you need de-duplication.
- Set operations treat **NULLs as equal** (unlike `=`).
- **JOIN vs UNION**: a JOIN adds **columns** (combines tables side by side); a UNION adds **rows** (stacks results).
- Oracle writes `MINUS` (21c also accepts EXCEPT). MySQL supports INTERSECT and EXCEPT from 8.0.31.

## Interview Q&A | sky | wide
Q: What types of joins are there?
A: INNER (only matches), LEFT and RIGHT OUTER (all rows from one side plus matches), FULL OUTER (all rows from both), CROSS (every combination) and SELF joins (a table joined to itself), plus semi-joins and anti-joins written with EXISTS and NOT EXISTS.
Q: INNER JOIN vs LEFT JOIN?
A: INNER JOIN returns only rows with a match in both tables. LEFT JOIN returns every row from the left table and NULLs for the right side where there is no match.
Q: Why does my LEFT JOIN behave like an INNER JOIN?
A: A WHERE condition on a right-table column rejects the NULL-extended rows. Move that condition into the ON clause, or allow NULL explicitly.
Q: How do you find rows in table A that are not in table B?
A: `LEFT JOIN B ... WHERE B.key IS NULL`, `WHERE NOT EXISTS (SELECT 1 FROM B WHERE ...)`, or `SELECT key FROM A EXCEPT SELECT key FROM B`. Avoid NOT IN when B's column can be NULL.
Q: How many rows does a CROSS JOIN return?
A: The product of the row counts: 9 employees CROSS JOIN 4 departments gives 36 rows.
Q: What is a self join? Give an example.
A: Joining a table to itself through two aliases, for example employees e JOIN employees m ON m.id = e.manager_id to show each employee's manager.
Q: UNION vs UNION ALL?
A: UNION returns distinct rows, which costs a sort or hash. UNION ALL returns every row, including duplicates, and is cheaper.
Q: JOIN vs UNION?
A: A join combines columns from related tables row by row. A union stacks the rows of two compatible queries.
Q: How do you do a FULL OUTER JOIN in MySQL?
A: A LEFT JOIN, then UNION ALL a RIGHT JOIN restricted to unmatched rows (`WHERE left.id IS NULL`).
Q: Can you join on something other than equality?
A: Yes. ON accepts any boolean condition: ranges (BETWEEN), inequalities and even functions. These are called non-equi or theta joins.
Q: Join vs subquery: which is faster?
A: Modern optimisers often produce the same plan for both. Use a join when you need columns from both tables and EXISTS when you only test for a match; check the plan with EXPLAIN when it matters.

# 10 | Day 5 · Subqueries | Nested queries, WHERE subqueries with IN, EXISTS, ANY and ALL, FROM subqueries (derived tables), scalar subqueries, correlated subqueries, LATERAL | Day 5: Subqueries

## What a Subquery Is | rose
- A **subquery** (inner or nested query) is a SELECT inside another statement, written in parentheses. The outer query uses its result.
- By **result shape**: **scalar** (one row, one column), **row** (one row, several columns), **table** (many rows).
- By **dependency**: **non-correlated** (runs on its own, conceptually once) vs **correlated** (refers to a column of the outer query, conceptually re-evaluated for each outer row).
- Where they can appear: **WHERE** (and HAVING), **FROM** (derived tables), **SELECT list** (scalar subqueries), and inside INSERT, UPDATE and DELETE.
- Subqueries can be **nested** several levels deep; past two levels, a CTE (sheet 11) is usually easier to read.

## WHERE Subqueries | blue
```sql
-- Scalar subquery: paid above the company average (96444.44)
SELECT name, salary FROM employees
WHERE salary > (SELECT AVG(salary) FROM employees)
ORDER BY salary DESC, name;                                   -- Asha, Meera, Ravi, Sara

-- Multi-row subquery with IN
SELECT name FROM employees
WHERE dept_id IN (SELECT id FROM departments WHERE name IN ('Sales', 'HR'))
ORDER BY id;                                                  -- Priya, Karan, Sara, Vikram

-- ALL and ANY
SELECT name, salary FROM employees
WHERE salary > ALL (SELECT salary FROM employees WHERE dept_id = 2)
ORDER BY id;                                                  -- above every Sales salary: Asha, Ravi, Meera
SELECT name, salary FROM employees
WHERE salary < ANY (SELECT salary FROM employees WHERE dept_id = 3);   -- below some HR salary: Neha
```
- A scalar subquery must return **at most one row**: more is a runtime error, zero rows gives NULL.
- `= ANY (...)` is the same as `IN (...)`; `<> ALL (...)` is the same as `NOT IN (...)`, with the same NULL trap. `SOME` is a synonym for ANY.
- `> ALL (subquery)` = greater than the maximum; `> ANY (subquery)` = greater than the minimum. If the subquery is empty, `> ALL` is TRUE for every row.
- **Nested subqueries**: the employee(s) with the second highest salary:
```sql
SELECT name, salary FROM employees
WHERE salary = (SELECT MAX(salary) FROM employees
                WHERE salary < (SELECT MAX(salary) FROM employees))
ORDER BY name;                                                -- Meera, Ravi (120000)
```

## EXISTS and NOT EXISTS | green
```sql
SELECT c.name FROM customers c
WHERE EXISTS (SELECT 1 FROM orders o WHERE o.customer_id = c.id AND o.amount > 200)
ORDER BY c.id;                                                -- Anil, Bina

SELECT d.name FROM departments d
WHERE NOT EXISTS (SELECT 1 FROM employees e WHERE e.dept_id = d.id);   -- Marketing
```
- `EXISTS` is TRUE as soon as the subquery finds **one** row; the select list is ignored (`SELECT 1` by convention). It never returns duplicates of the outer row (a **semi-join**).
- **IN vs EXISTS**: same result for "has a match". Modern optimisers turn both into a semi-join, so performance is usually equal; check EXPLAIN.
- **NOT EXISTS vs NOT IN**: NOT EXISTS is NULL-safe; NOT IN returns nothing if the subquery yields a NULL. Prefer NOT EXISTS (an **anti-join**).

## FROM Subqueries (Derived Tables) | amber
```sql
SELECT dept_id, avg_salary
FROM (
  SELECT dept_id, ROUND(AVG(salary), 2) AS avg_salary
  FROM employees
  GROUP BY dept_id
) AS dept_avg
WHERE avg_salary > 80000
ORDER BY avg_salary DESC;                                     -- 1 | 120000.00,  2 | 87666.67
```
- A subquery in FROM acts as a temporary table for the outer query. MySQL and SQL Server require an alias (`AS dept_avg`); PostgreSQL made it optional in version 16.
- Use it to aggregate first and then filter or join, or to filter on a **window function** result (window functions are not allowed in WHERE, sheet 12).
- **Aggregate before joining** to avoid fan-out double counting:
```sql
SELECT c.name, t.order_count, t.spent
FROM customers c
JOIN (SELECT customer_id, COUNT(*) AS order_count, SUM(amount) AS spent
      FROM orders GROUP BY customer_id) t ON t.customer_id = c.id
ORDER BY t.spent DESC;                                        -- Bina 2 860.00 | Anil 3 460.00 | Chen 1 80.00
```
- **LATERAL** (PostgreSQL, MySQL 8.0.14+) and **CROSS APPLY / OUTER APPLY** (SQL Server, Oracle 12c+) let a FROM subquery refer to columns of tables listed before it. Classic use: top N per parent row.
```sql
SELECT c.name, o.id, o.order_date
FROM customers c
CROSS JOIN LATERAL (
  SELECT id, order_date FROM orders
  WHERE customer_id = c.id
  ORDER BY order_date DESC
  LIMIT 2
) o
ORDER BY c.id, o.order_date DESC;    -- Anil 106, 102 | Bina 105, 103 | Chen 104   (Dev has none)
```

## Correlated and SELECT-List Subqueries | violet
```sql
-- Correlated subquery: earns more than the average of their own department
SELECT e.name, e.dept_id, e.salary
FROM employees e
WHERE e.salary > (SELECT AVG(x.salary) FROM employees x WHERE x.dept_id = e.dept_id)
ORDER BY e.id;                                                -- Asha, Priya, Sara

-- Scalar subquery in SELECT: a value per row
SELECT c.name,
       (SELECT COUNT(*) FROM orders o WHERE o.customer_id = c.id) AS order_count
FROM customers c
ORDER BY c.id;                                                -- Anil 3 | Bina 2 | Chen 1 | Dev 0
```
- A correlated subquery refers to the outer row (`e.dept_id`), so logically it runs **once per outer row**. Optimisers often rewrite it into a join, but on big tables it can still be slow.
- Faster rewrites: join to a grouped derived table, or use a window function:
```sql
SELECT name, dept_id, salary
FROM (SELECT name, dept_id, salary, id, AVG(salary) OVER (PARTITION BY dept_id) AS dept_avg
      FROM employees) t
WHERE salary > dept_avg
ORDER BY id;                                                  -- Asha, Priya, Sara
```
- A SELECT-list subquery must return one value per row. Unlike `COUNT` after a LEFT JOIN, it naturally returns 0 for Dev.

## Subqueries in INSERT, UPDATE and DELETE | rose
```sql
UPDATE employees SET salary = salary * 1.05
WHERE dept_id = (SELECT id FROM departments WHERE name = 'HR');            -- Vikram

DELETE FROM orders
WHERE customer_id IN (SELECT id FROM customers WHERE city IS NULL);        -- Chen's order 104

INSERT INTO departments (id, name)
SELECT 10 + COUNT(*), 'Dept ' || (10 + COUNT(*)) FROM departments;         -- 14 | Dept 14
```
- **MySQL error 1093**: you can't modify a table and read the same table in a subquery (`DELETE FROM t WHERE id IN (SELECT ... FROM t)`). Wrap the subquery in a derived table that MySQL materialises, or rewrite it as a multi-table DELETE with a JOIN.

## Interview Q&A | sky | wide
Q: What is a correlated subquery?
A: A subquery that refers to a column of the outer query, so it is logically evaluated for each outer row, for example comparing each employee with their own department's average.
Q: Subquery vs JOIN?
A: Use a join when you need columns from both tables. Use EXISTS or IN when you only need to test for related rows, because it never duplicates the outer rows. Optimisers often produce similar plans.
Q: IN vs EXISTS?
A: Both test membership and usually become the same semi-join. EXISTS stops at the first match and works naturally with correlated conditions; with NOT, prefer NOT EXISTS because NOT IN breaks on NULLs.
Q: What is a derived table?
A: A subquery in the FROM clause that acts as a temporary, unnamed table for the outer query. It needs an alias in most databases.
Q: Can a subquery return several columns?
A: Yes, as a row or table subquery: `WHERE (dept_id, salary) IN (SELECT dept_id, MAX(salary) FROM employees GROUP BY dept_id)` works in PostgreSQL, MySQL and Oracle, but not SQL Server.
Q: What happens when a scalar subquery returns more than one row?
A: The statement fails at runtime with an error such as "more than one row returned by a subquery used as an expression".
Q: How do you find employees who earn more than their department average?
A: A correlated subquery in WHERE, a join to per-department averages from a derived table, or AVG(salary) OVER (PARTITION BY dept_id) in a subquery.
Q: What does `> ALL` mean, and what if the subquery is empty?
A: The value must be greater than every value returned, which equals "greater than the maximum". With an empty subquery the condition is TRUE for every row.
Q: What is LATERAL or CROSS APPLY?
A: A FROM subquery that can reference earlier tables in the same FROM, evaluated per row. It is the clean way to get, say, the latest two orders for each customer.

# 11 | Day 6 · CASE WHEN & CTEs | Searched and simple CASE, CASE in ORDER BY, GROUP BY, aggregates and UPDATE, common table expressions, multiple CTEs, recursive CTEs | Day 6: CASE & CTEs

## CASE Expressions | rose
```sql
-- Searched CASE: conditions are tested top to bottom, the first TRUE wins
SELECT name, salary,
       CASE
         WHEN salary >= 120000 THEN 'Senior band'
         WHEN salary >= 90000  THEN 'Mid band'
         ELSE 'Junior band'
       END AS band
FROM employees
ORDER BY salary DESC, name;
-- Asha Senior | Meera Senior | Ravi Senior | Sara Mid | Priya Mid | John Mid | Karan Junior | Vikram Junior | Neha Junior

-- Simple CASE: compares one expression with values
SELECT id, status,
       CASE status WHEN 'delivered' THEN 'Done' WHEN 'cancelled' THEN 'Void' ELSE 'Open' END AS stage
FROM orders
ORDER BY id;
-- 101 Done | 102 Done | 103 Open | 104 Void | 105 Open | 106 Open
```
- CASE is an **expression**: it returns a value, so it can go anywhere a value can (SELECT, WHERE, ORDER BY, GROUP BY, inside aggregates, UPDATE SET, JOIN ON).
- **Order matters** in a searched CASE: put the most specific condition first.
- **No ELSE and no match → NULL.** All branches must return compatible types.
- A simple CASE cannot match NULL (`CASE city WHEN NULL ...` never fires, because it uses `=`). Use a searched `WHEN city IS NULL`.
- Shortcuts: MySQL `IF(cond, a, b)`, SQL Server `IIF(cond, a, b)`, Oracle `DECODE(x, v1, r1, default)`.

## CASE in Practice | blue
```sql
-- Custom sort order
SELECT id, status FROM orders
ORDER BY CASE status WHEN 'pending' THEN 1 WHEN 'shipped' THEN 2 WHEN 'delivered' THEN 3 ELSE 4 END, id;
-- 105 pending | 106 pending | 103 shipped | 101 delivered | 102 delivered | 104 cancelled

-- Pivot: headcount per department as columns
SELECT COUNT(CASE WHEN dept_id = 1 THEN 1 END)     AS engineering,
       COUNT(CASE WHEN dept_id = 2 THEN 1 END)     AS sales,
       COUNT(CASE WHEN dept_id IS NULL THEN 1 END) AS unassigned
FROM employees;                                    -- 4 | 3 | 1

-- Bucket and group
SELECT CASE WHEN amount >= 300 THEN 'large' ELSE 'small' END AS size, COUNT(*) AS orders
FROM orders
GROUP BY CASE WHEN amount >= 300 THEN 'large' ELSE 'small' END
ORDER BY size;                                     -- large 2 | small 4

-- Filter with CASE (often clearer as plain AND/OR)
SELECT name FROM employees
WHERE CASE WHEN dept_id = 2 THEN salary > 90000 ELSE salary > 120000 END
ORDER BY id;                                       -- Asha, Priya, Sara

-- Different raise per department in one statement
UPDATE employees
SET salary = CASE WHEN dept_id = 1 THEN salary * 1.10
                  WHEN dept_id = 2 THEN salary * 1.05
                  ELSE salary END;
```
- PostgreSQL and MySQL also accept `GROUP BY 1` (the first select column) or the alias; SQL Server needs the full expression.

## Common Table Expressions (CTEs) | green
```sql
WITH dept_stats AS (
  SELECT dept_id, AVG(salary) AS avg_salary, COUNT(*) AS headcount
  FROM employees
  WHERE dept_id IS NOT NULL
  GROUP BY dept_id
)
SELECT d.name, s.headcount, ROUND(s.avg_salary, 0) AS avg_salary
FROM dept_stats s
JOIN departments d ON d.id = s.dept_id
ORDER BY s.avg_salary DESC;
-- Engineering 4 120000 | Sales 3 87667 | HR 1 65000
```
- A **CTE (Common Table Expression)** is a **named, temporary result set** defined with `WITH` that exists for **one statement**. Think of it as a derived table you name up front.
- Why use one: **readability** (top-to-bottom steps instead of nested subqueries), **reuse** of the same intermediate result more than once in the statement, and **recursion**.
- Several CTEs are separated by commas, and each can use the ones before it:
```sql
WITH order_totals AS (
  SELECT customer_id, SUM(amount) AS spent
  FROM orders
  WHERE status <> 'cancelled'
  GROUP BY customer_id
),
shares AS (
  SELECT customer_id, spent, 100.0 * spent / SUM(spent) OVER () AS pct
  FROM order_totals
)
SELECT c.name, s.spent, ROUND(s.pct, 1) AS pct_of_revenue
FROM shares s
JOIN customers c ON c.id = s.customer_id
ORDER BY s.spent DESC;
-- Bina 860.00 65.2 | Anil 460.00 34.8
```
- **CTE vs subquery vs view vs temp table**: a CTE lives for one statement and mainly helps readability; a **view** stores the query definition in the database for reuse by any query; a **temporary table** physically stores rows for the session and can be indexed.
- **Performance**: PostgreSQL 12+ inlines a non-recursive CTE that is referenced once (older versions always materialised it, an "optimisation fence"); you can force either with `AS MATERIALIZED` / `AS NOT MATERIALIZED`. SQL Server always inlines, so a CTE referenced twice is computed twice. MySQL 8 may merge or materialise it.
- Supported in MySQL 8.0+, PostgreSQL, SQL Server 2005+, Oracle and SQLite.
- PostgreSQL also allows **data-modifying CTEs**: `WITH moved AS (DELETE FROM orders WHERE ... RETURNING *) INSERT INTO orders_archive SELECT * FROM moved;`

## Recursive CTEs | amber
```sql
-- The org chart under Asha, with depth and path
WITH RECURSIVE chain AS (
  SELECT id, name, 0 AS depth, CAST(name AS VARCHAR(200)) AS path      -- anchor member: the root
  FROM employees
  WHERE manager_id IS NULL
  UNION ALL
  SELECT e.id, e.name, c.depth + 1, CAST(c.path || ' > ' || e.name AS VARCHAR(200))   -- recursive member
  FROM employees e
  JOIN chain c ON e.manager_id = c.id
)
SELECT path, depth FROM chain ORDER BY path;
-- Asha 0 | Asha > Meera 1 | Asha > Neha 1 | Asha > Priya 1 | Asha > Priya > Karan 2
-- Asha > Priya > Sara 2 | Asha > Ravi 1 | Asha > Ravi > John 2 | Asha > Vikram 1

-- Generate the numbers 1 to 5
WITH RECURSIVE n AS (
  SELECT 1 AS x
  UNION ALL
  SELECT x + 1 FROM n WHERE x < 5
)
SELECT x FROM n;                                   -- 1 2 3 4 5
```
- How it runs: the **anchor** query runs once; the **recursive member** then runs repeatedly against the rows produced by the previous round, until a round returns no rows. `UNION ALL` stacks all rounds together.
- **Always make it terminate**: a stopping WHERE, a depth limit, or cycle detection. A cycle in the data (A manages B, B manages A) loops forever. PostgreSQL 14+ has a `CYCLE` clause; elsewhere carry the visited path and check it.
- Safety limits: SQL Server stops at **100** levels by default (`OPTION (MAXRECURSION n)`, 0 = unlimited); MySQL's `cte_max_recursion_depth` defaults to **1000**.
- Keyword: `WITH RECURSIVE` in PostgreSQL, MySQL and SQLite; just `WITH` in SQL Server and Oracle (Oracle also has its older `CONNECT BY` syntax).
- Uses: org charts, category trees, bill of materials, graph paths, filling date gaps (PostgreSQL also has `generate_series`).

## Interview Q&A | sky | wide
Q: What is the difference between a simple and a searched CASE?
A: A simple CASE compares one expression against values with equality (`CASE status WHEN 'x' THEN ...`). A searched CASE evaluates independent boolean conditions (`CASE WHEN salary > 100 THEN ...`) and can test ranges and NULL.
Q: What does CASE return if nothing matches and there's no ELSE?
A: NULL.
Q: How do you pivot rows into columns?
A: Conditional aggregation: one `SUM(CASE WHEN category = 'x' THEN amount END)` or `COUNT(CASE ...)` per output column, grouped by the row key. SQL Server and Oracle also have PIVOT.
Q: What is a CTE and why use it?
A: A named temporary result defined with WITH for a single statement. It makes multi-step queries readable, lets you reference the same intermediate result more than once and enables recursion.
Q: CTE vs subquery vs temporary table?
A: CTEs and subqueries exist only inside one statement and are usually inlined by the optimiser. A temporary table stores rows for the whole session, can be indexed and reused across statements.
Q: Is a CTE materialised?
A: It depends: PostgreSQL 12+ inlines single-use CTEs unless you write MATERIALIZED, SQL Server always inlines, and MySQL may do either.
Q: Explain a recursive CTE.
A: It has an anchor query and a recursive query joined by UNION ALL. The recursive part refers to the CTE itself and runs on the previous round's rows until no new rows appear. It is used for hierarchies and series.
Q: How do you prevent infinite recursion?
A: Add a termination condition (depth limit or WHERE), detect cycles by tracking the visited path, and rely on safety limits such as MAXRECURSION or cte_max_recursion_depth.
Q: Can you use CASE in WHERE and ORDER BY?
A: Yes. It is just an expression: it can drive custom sort orders and conditional filters, though plain AND and OR conditions are often clearer in WHERE.

# 12 | Day 6 · Window Functions: ROW_NUMBER, RANK & PARTITION BY | OVER, PARTITION BY, ORDER BY, ranking functions, top N per group, LAG and LEAD, running totals, frames | Day 6: Window Functions

## What Window Functions Are | rose
- A window function computes a value **over a set of rows related to the current row** (its "window") **without collapsing the rows**. GROUP BY returns one row per group; a window function keeps every row and adds the group-level value beside it.
- Syntax: `function(...) OVER (PARTITION BY ... ORDER BY ... frame)`.
- **PARTITION BY** splits rows into independent groups (like GROUP BY, but rows are kept). Without it, the whole result is one partition.
- **ORDER BY** inside OVER orders rows within each partition. Ranking, LAG/LEAD and running totals need it.
- **Frame** chooses which rows around the current one an aggregate sees (`ROWS BETWEEN 2 PRECEDING AND CURRENT ROW`).
```sql
SELECT name, dept_id, salary,
       ROUND(AVG(salary) OVER (PARTITION BY dept_id), 2)          AS dept_avg,
       salary - ROUND(AVG(salary) OVER (PARTITION BY dept_id), 2) AS diff_from_avg,
       SUM(salary) OVER ()                                        AS payroll_of_these_rows
FROM employees
WHERE dept_id = 2
ORDER BY salary DESC;
-- Sara  2 98000.00 87666.67  10333.33 263000.00
-- Priya 2 95000.00 87666.67   7333.33 263000.00
-- Karan 2 70000.00 87666.67 -17666.67 263000.00
```
- Window functions run **after WHERE, GROUP BY and HAVING**, in the SELECT step. So the window above only sees the Sales rows, and **you cannot filter on a window function in WHERE**: wrap the query in a CTE or subquery. (Snowflake, BigQuery and DuckDB have a `QUALIFY` clause for this; PostgreSQL, MySQL and SQL Server don't.)
- Available in MySQL 8.0+, PostgreSQL, SQL Server 2005+ (full frames since 2012), Oracle and SQLite 3.25+.

## ROW_NUMBER, RANK and DENSE_RANK | blue
```sql
SELECT name, salary,
       ROW_NUMBER() OVER (ORDER BY salary DESC, name) AS row_num,
       RANK()       OVER (ORDER BY salary DESC)       AS rnk,
       DENSE_RANK() OVER (ORDER BY salary DESC)       AS dense_rnk
FROM employees
ORDER BY salary DESC, name
LIMIT 5;
-- Asha  150000  1  1  1
-- Meera 120000  2  2  2   ← tie
-- Ravi  120000  3  2  2
-- Sara   98000  4  4  3   ← RANK skips 3, DENSE_RANK doesn't
-- Priya  95000  5  5  4
```
- **ROW_NUMBER**: 1, 2, 3, 4: always unique. Ties get an arbitrary order unless you add a **tie-breaker** column (here `name`).
- **RANK**: ties share a rank and leave **gaps** after them (1, 2, 2, 4), like sports rankings.
- **DENSE_RANK**: ties share a rank with **no gaps** (1, 2, 2, 3). "The 3rd highest salary" usually means DENSE_RANK = 3.
- Also: **NTILE(n)** splits rows into n roughly equal buckets (quartiles with NTILE(4)), **PERCENT_RANK** and **CUME_DIST** give relative position.

## PARTITION BY: Top N per Group | green
```sql
WITH ranked AS (
  SELECT name, dept_id, salary,
         DENSE_RANK() OVER (PARTITION BY dept_id ORDER BY salary DESC) AS rnk
  FROM employees
  WHERE dept_id IS NOT NULL
)
SELECT dept_id, name, salary, rnk
FROM ranked
WHERE rnk <= 2
ORDER BY dept_id, rnk, name;
-- 1 Asha   150000 1 | 1 Meera 120000 2 | 1 Ravi 120000 2
-- 2 Sara    98000 1 | 2 Priya  95000 2
-- 3 Vikram  65000 1
```
- Ranking restarts at 1 in every partition (department).
- Which function for "top N per group"? **ROW_NUMBER** gives exactly N rows per group; **RANK / DENSE_RANK** include ties, so a group may return more than N.
- **De-duplicate**, keeping the newest row per key: `ROW_NUMBER() OVER (PARTITION BY email ORDER BY updated_at DESC) = 1` in a CTE, then keep (or delete) by that number.
- Window functions can be combined with GROUP BY; they are applied to the grouped rows: `RANK() OVER (ORDER BY SUM(amount) DESC)` ranks customers by total spend.

## LAG, LEAD, FIRST_VALUE and LAST_VALUE | amber
```sql
SELECT id, order_date, amount,
       LAG(amount)       OVER (ORDER BY order_date)          AS prev_amount,
       LEAD(order_date)  OVER (ORDER BY order_date)          AS next_order_date,
       amount - LAG(amount, 1, 0) OVER (ORDER BY order_date) AS change
FROM orders
ORDER BY order_date;
-- 101 2026-01-05 250.00 NULL   2026-01-20  250.00
-- 102 2026-01-20 120.00 250.00 2026-02-03 -130.00
-- 103 2026-02-03 560.00 120.00 2026-02-10  440.00
-- 104 2026-02-10  80.00 560.00 2026-03-15 -480.00
-- 105 2026-03-15 300.00  80.00 2026-03-28  220.00
-- 106 2026-03-28  90.00 300.00 NULL       -210.00

SELECT customer_id, id, amount,
       FIRST_VALUE(amount) OVER (PARTITION BY customer_id ORDER BY order_date) AS first_order_amount
FROM orders
ORDER BY customer_id, order_date;
-- 1 101 250 250 | 1 102 120 250 | 1 106 90 250 | 2 103 560 560 | 2 105 300 560 | 3 104 80 80
```
- `LAG(col, offset, default)` reads a previous row; `LEAD(...)` reads a following row. Offset defaults to 1, default value to NULL. Uses: day-over-day change, time between events, "same value three times in a row" (sheet 19).
- `FIRST_VALUE`, `LAST_VALUE`, `NTH_VALUE(col, n)` read a specific row of the frame.
- **LAST_VALUE trap**: with ORDER BY, the default frame ends at the **current row**, so LAST_VALUE just returns the current row. Write `ROWS BETWEEN UNBOUNDED PRECEDING AND UNBOUNDED FOLLOWING`.

## Running Totals, Moving Averages and Frames | violet
```sql
SELECT id, order_date, amount,
       SUM(amount) OVER (ORDER BY order_date)                          AS running_total,
       SUM(amount) OVER (PARTITION BY customer_id ORDER BY order_date) AS customer_running,
       ROUND(AVG(amount) OVER (ORDER BY order_date
                               ROWS BETWEEN 2 PRECEDING AND CURRENT ROW), 2) AS moving_avg_3,
       ROUND(100.0 * amount / SUM(amount) OVER (), 1)                  AS pct_of_total
FROM orders
ORDER BY order_date;
-- 101  250.00   250.00  250.00 250.00 17.9
-- 102  120.00   370.00  370.00 185.00  8.6
-- 103  560.00   930.00  560.00 310.00 40.0
-- 104   80.00  1010.00   80.00 253.33  5.7
-- 105  300.00  1310.00  860.00 313.33 21.4
-- 106   90.00  1400.00  460.00 156.67  6.4
```
- A **running total** is `SUM(...) OVER (ORDER BY ...)`; per group, add PARTITION BY. **Percent of total**: divide by `SUM(...) OVER ()`.
- **Frames**: `ROWS` counts physical rows; `RANGE` groups **peers** (rows with the same ORDER BY value) and, in PostgreSQL 11+, accepts value offsets such as `RANGE BETWEEN INTERVAL '7 days' PRECEDING AND CURRENT ROW`.
- **Default frame**: with ORDER BY it is `RANGE BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW`, so **tied rows get the same running total**. Use `ROWS` (or a unique tie-breaker) for a strict row-by-row sum. Without ORDER BY the frame is the whole partition.
- **Named windows** avoid repetition: `... RANK() OVER w ... WINDOW w AS (PARTITION BY dept_id ORDER BY salary DESC)` (PostgreSQL, MySQL, SQLite, SQL Server 2022+).

## Interview Q&A | sky | wide
Q: ROW_NUMBER vs RANK vs DENSE_RANK?
A: ROW_NUMBER numbers rows uniquely (1, 2, 3, 4). RANK gives ties the same number and skips the next ones (1, 2, 2, 4). DENSE_RANK gives ties the same number without gaps (1, 2, 2, 3).
Q: PARTITION BY vs GROUP BY?
A: GROUP BY collapses each group into one output row. PARTITION BY defines groups for a window function but keeps every input row, adding the group-level result to each.
Q: Why can't I use a window function in WHERE?
A: WHERE is evaluated before window functions are computed. Compute it in a CTE or subquery and filter in the outer query.
Q: How do you get the top 3 earners per department?
A: `DENSE_RANK() OVER (PARTITION BY dept_id ORDER BY salary DESC)` in a CTE, then `WHERE rnk <= 3`. Use ROW_NUMBER if you need exactly three rows even with ties.
Q: How do you compute a running total?
A: `SUM(amount) OVER (ORDER BY order_date ROWS BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW)`, with PARTITION BY for per-group totals.
Q: What are LAG and LEAD used for?
A: Comparing a row with the previous or next row: period-over-period growth, gaps between events, detecting consecutive values or status changes.
Q: ROWS vs RANGE?
A: ROWS counts physical rows around the current row. RANGE includes all peers that share the current ORDER BY value and can use value distances. The default frame with ORDER BY is RANGE, which makes ties share running totals.
Q: How do you delete duplicates with a window function?
A: Number rows with `ROW_NUMBER() OVER (PARTITION BY duplicate_key ORDER BY id)` and delete the rows whose number is greater than 1.
Q: Why does LAST_VALUE return the current row?
A: The default frame ends at the current row. Extend it with `ROWS BETWEEN UNBOUNDED PRECEDING AND UNBOUNDED FOLLOWING`.
Q: Can window functions be used with GROUP BY?
A: Yes. They run after grouping, so they can rank or total the aggregated values, for example `RANK() OVER (ORDER BY SUM(amount) DESC)`.

# 13 | Views, Stored Procedures, Functions & Triggers | Views and updatable views, materialised views, procedures and functions in each dialect, function vs procedure, row and statement triggers | Views, Procs & Triggers

## Views | rose
```sql
CREATE VIEW employee_directory AS
SELECT e.id, e.name, e.email, d.name AS department
FROM employees e
LEFT JOIN departments d ON d.id = e.dept_id;

SELECT name, department FROM employee_directory WHERE department = 'Sales' ORDER BY name;
-- Karan Sales | Priya Sales | Sara Sales

CREATE OR REPLACE VIEW employee_directory AS
SELECT e.id, e.name, e.email, d.name AS department, e.city
FROM employees e
LEFT JOIN departments d ON d.id = e.dept_id;     -- PostgreSQL can only add columns at the end this way

DROP VIEW employee_directory;
```
- A **view** is a **stored query** that behaves like a virtual table. It stores **no data**: every query against it runs the underlying SELECT (the optimiser merges it into your query).
- Uses: **hide complexity** (joins in one place), **security** (expose only some columns or rows and grant access to the view, not the table), a **stable interface** while tables change underneath.
- **Updatable views**: a simple view over one table (no aggregates, DISTINCT, GROUP BY or UNION) accepts INSERT, UPDATE and DELETE. `WITH CHECK OPTION` rejects changes that would make a row fall outside the view's WHERE. Complex views need INSTEAD OF triggers.
- Syntax: `CREATE OR REPLACE VIEW` (PostgreSQL, MySQL, Oracle); SQL Server uses `CREATE OR ALTER VIEW`.

## Materialised Views | blue
```sql PostgreSQL
CREATE MATERIALIZED VIEW dept_payroll AS
SELECT dept_id, SUM(salary) AS payroll, COUNT(*) AS headcount
FROM employees
GROUP BY dept_id;

SELECT payroll FROM dept_payroll WHERE dept_id = 1;    -- 480000.00
REFRESH MATERIALIZED VIEW dept_payroll;                -- recompute; CONCURRENTLY needs a unique index
```
- A materialised view **stores the result physically**: fast to read, but **stale until refreshed**.
- PostgreSQL refreshes it on demand. Oracle can refresh on commit or incrementally (fast refresh with materialised view logs). SQL Server's equivalent is an **indexed view**, kept up to date automatically on every write. **MySQL has none**: use a summary table refreshed by a scheduled job or triggers.
- **View vs materialised view**: always fresh but recomputed on every read, vs precomputed and fast but possibly stale.

## Stored Procedures | green
```sql PostgreSQL
CREATE TABLE salary_audit (dept_id INT, pct NUMERIC, changed_at TIMESTAMPTZ);

CREATE PROCEDURE give_raise(p_dept INT, p_pct NUMERIC)
LANGUAGE plpgsql
AS $$
BEGIN
  UPDATE employees SET salary = salary * (1 + p_pct / 100) WHERE dept_id = p_dept;
  INSERT INTO salary_audit (dept_id, pct, changed_at) VALUES (p_dept, p_pct, NOW());
END;
$$;

CALL give_raise(3, 10);
SELECT salary FROM employees WHERE id = 8;             -- 71500.00
```
```sql MySQL
DELIMITER //
CREATE PROCEDURE give_raise(IN p_dept INT, IN p_pct DECIMAL(5,2))
BEGIN
  UPDATE employees SET salary = salary * (1 + p_pct / 100) WHERE dept_id = p_dept;
END //
DELIMITER ;

CALL give_raise(3, 10);
```
```sql SQL-Server
CREATE PROCEDURE dbo.give_raise @dept INT, @pct DECIMAL(5,2)
AS
BEGIN
  SET NOCOUNT ON;
  UPDATE employees SET salary = salary * (1 + @pct / 100) WHERE dept_id = @dept;
END;
GO

EXEC dbo.give_raise @dept = 3, @pct = 10;
```
- A **stored procedure** is named logic stored in the database. It takes IN, OUT (and INOUT) parameters, runs many statements, can return result sets and (in MySQL, SQL Server, Oracle and PostgreSQL 11+) can control transactions. Called with `CALL` (MySQL, PostgreSQL) or `EXEC` (SQL Server).
- **Pros**: fewer network round trips, logic close to the data, a permission boundary (grant EXECUTE instead of table access), cached plans.
- **Cons**: harder to version, test and debug; vendor lock-in; business logic split between application and database; database CPU is the most expensive to scale.
- `DELIMITER` is a **MySQL client** command so the `;` inside the body doesn't end the CREATE statement. `GO` is a batch separator understood by SQL Server tools, not part of T-SQL. PostgreSQL wraps the body in `$$` dollar quotes.

## Functions | amber
```sql PostgreSQL
CREATE FUNCTION annual_bonus(p_salary NUMERIC, p_pct NUMERIC DEFAULT 10)
RETURNS NUMERIC
LANGUAGE sql
IMMUTABLE
AS $$ SELECT ROUND(p_salary * p_pct / 100, 2) $$;

SELECT name, annual_bonus(salary) AS bonus, annual_bonus(salary, 20) AS big_bonus
FROM employees WHERE id = 1;                           -- Asha | 15000.00 | 30000.00
```
- **Function vs procedure**: a function **returns a value** (a scalar or a table) and is used **inside a query** (`SELECT f(x)`, WHERE, or FROM for table-valued functions). A procedure is **called on its own** to perform actions.
- Functions can't COMMIT or ROLLBACK. SQL Server functions can't modify tables at all; procedures can return several result sets and OUT parameters.
- SQL Server has scalar functions, **inline table-valued functions** (fast, like parameterised views) and multi-statement table-valued functions. PostgreSQL functions declare `RETURNS TABLE (...)` or `SETOF` for row sets, and a volatility (`IMMUTABLE`, `STABLE`, `VOLATILE`) that controls caching and whether they can be used in an index.

## Triggers | violet
```sql PostgreSQL
CREATE TABLE salary_history (
  emp_id      INT,
  old_salary  NUMERIC,
  new_salary  NUMERIC,
  changed_at  TIMESTAMPTZ DEFAULT NOW()
);

CREATE FUNCTION log_salary_change() RETURNS trigger
LANGUAGE plpgsql
AS $$
BEGIN
  IF NEW.salary <> OLD.salary THEN
    INSERT INTO salary_history (emp_id, old_salary, new_salary) VALUES (OLD.id, OLD.salary, NEW.salary);
  END IF;
  RETURN NEW;
END;
$$;

CREATE TRIGGER trg_salary_change
AFTER UPDATE OF salary ON employees
FOR EACH ROW EXECUTE FUNCTION log_salary_change();

UPDATE employees SET salary = 100000 WHERE id = 4;
SELECT emp_id, old_salary, new_salary FROM salary_history;     -- 4 | 90000.00 | 100000.00
```
```sql MySQL
DELIMITER //
CREATE TRIGGER trg_salary_change
AFTER UPDATE ON employees
FOR EACH ROW
BEGIN
  IF NEW.salary <> OLD.salary THEN
    INSERT INTO salary_history (emp_id, old_salary, new_salary) VALUES (OLD.id, OLD.salary, NEW.salary);
  END IF;
END //
DELIMITER ;
```
```sql SQL-Server
CREATE TRIGGER trg_salary_change ON employees
AFTER UPDATE
AS
BEGIN
  SET NOCOUNT ON;
  INSERT INTO salary_history (emp_id, old_salary, new_salary)
  SELECT d.id, d.salary, i.salary
  FROM deleted d
  JOIN inserted i ON i.id = d.id
  WHERE i.salary <> d.salary;            -- fires once per statement, so handle many rows
END;
```
- A **trigger** is code the database runs automatically on `INSERT`, `UPDATE` or `DELETE` (PostgreSQL also `TRUNCATE`).
- **Timing**: `BEFORE` (validate or change the incoming row), `AFTER` (audit, sync other tables), `INSTEAD OF` (make a complex view writable).
- **Level**: **row-level** (`FOR EACH ROW`, sees `OLD` and `NEW`) vs **statement-level** (runs once per statement, however many rows changed).
- Dialects: MySQL supports row-level BEFORE and AFTER triggers only. PostgreSQL supports row and statement level, and the trigger body is a separate function. SQL Server triggers are **statement-level only** and read the `inserted` and `deleted` pseudo-tables. Oracle supports both levels plus compound triggers.
- Uses: audit trails, `updated_at` timestamps, derived or denormalised columns, complex rules. Costs: **hidden side effects**, harder debugging, slower bulk writes, cascading or recursive triggers. If a constraint can express the rule, use the constraint.

## Interview Q&A | sky | wide
Q: What is a view, and why use one?
A: A saved SELECT that acts as a virtual table. It simplifies complex joins, restricts what users can see, and gives applications a stable interface while the tables change.
Q: View vs materialised view?
A: A view stores only the query and is always current. A materialised view stores the result, so it reads fast but must be refreshed and can be stale.
Q: Can you insert into or update a view?
A: Yes, if it is a simple view over one table without aggregates, DISTINCT, GROUP BY or UNION. Add WITH CHECK OPTION to keep changes within the view's filter. Complex views need INSTEAD OF triggers.
Q: Stored procedure vs function?
A: A function returns a value and can be used inside SQL statements, without side effects on transactions. A procedure is invoked with CALL or EXEC, can run many statements, return several result sets or OUT parameters and manage transactions.
Q: Advantages and disadvantages of stored procedures?
A: Fewer round trips, centralised logic, EXECUTE-only permissions and plan reuse; but vendor lock-in, harder testing, versioning and debugging, and logic scattered between the app and the database.
Q: What is a trigger? What types exist?
A: Code that runs automatically when data changes. It can run BEFORE, AFTER or INSTEAD OF an INSERT, UPDATE or DELETE, and fire once per row or once per statement.
Q: BEFORE vs AFTER trigger?
A: A BEFORE trigger can inspect and change the row before it is written, or reject it. An AFTER trigger sees the final row and is used for side effects such as audit logging.
Q: What are inserted and deleted in SQL Server?
A: Pseudo-tables available inside triggers: inserted holds the new row versions, deleted holds the old ones. An UPDATE fills both.
Q: Why be careful with triggers?
A: They hide behaviour from anyone reading application code, slow bulk operations, can cascade into other triggers and make debugging hard. Prefer constraints or explicit application logic.

# 14 | Normalization & Schema Design | Anomalies, functional dependencies, 1NF, 2NF, 3NF, BCNF, denormalization, OLTP vs OLAP, design checklist | Normalization

## Why Normalise: Anomalies | rose
- Start with one wide table that stores everything about an order:
```text
order_id  order_date  customer  customer_city  products          unit_prices   qtys
1001      2026-01-05  Anil      Mumbai         Keyboard, Mouse   1500, 500     1, 2
1002      2026-01-09  Anil      Mumbai         Mouse             500           1
```
- Redundant data causes **anomalies**:
- **Update anomaly**: Anil moves city; every one of his rows must change, and missing one leaves the data inconsistent.
- **Insert anomaly**: you cannot record a new product until somebody orders it.
- **Delete anomaly**: deleting the only order for a product also deletes the fact that the product (and its price) exists.
- **Normalisation** splits tables according to **functional dependencies** to remove this redundancy. `X → Y` ("X determines Y") means each value of X has exactly one value of Y, for example `customer_id → customer_city`.

## First Normal Form (1NF) | blue
- **Atomic values** (one value per cell, no lists), **no repeating groups** (no `product1, product2` columns), every row uniquely identifiable by a key.
- The table above breaks 1NF (`products` holds a list). Fix: one row per order line, with key `(order_id, product)`.
```text
order_id  order_date  customer  customer_city  product   unit_price  qty
1001      2026-01-05  Anil      Mumbai         Keyboard  1500        1
1001      2026-01-05  Anil      Mumbai         Mouse     500         2
1002      2026-01-09  Anil      Mumbai         Mouse     500         1
```

## Second Normal Form (2NF) | green
- **1NF + no partial dependency**: every non-key column must depend on the **whole** primary key, not just part of it. It only matters when the key is composite.
- With key `(order_id, product)`: `order_date`, `customer` and `customer_city` depend only on `order_id`; `unit_price` depends only on `product`. Both are partial dependencies.
- Fix: split into `orders(order_id, order_date, customer, customer_city)`, `products(product, unit_price)` and `order_items(order_id, product, qty)`.

## Third Normal Form (3NF) | amber
- **2NF + no transitive dependency**: a non-key column must not depend on another **non-key** column.
- In `orders`, `customer_city` depends on `customer`, which depends on `order_id`: transitive. Fix: `customers(customer_id, name, city)` and `orders(order_id, order_date, customer_id)`.
> Memory hook: every non-key column depends on "the key, the whole key, and nothing but the key".
```sql
CREATE TABLE shop_customers (
  id    INT PRIMARY KEY,
  name  VARCHAR(100) NOT NULL,
  city  VARCHAR(50)
);
CREATE TABLE products (
  id          INT PRIMARY KEY,
  name        VARCHAR(100) NOT NULL UNIQUE,
  unit_price  DECIMAL(10,2) NOT NULL
);
CREATE TABLE shop_orders (
  id           INT PRIMARY KEY,
  customer_id  INT NOT NULL,
  order_date   DATE NOT NULL,
  FOREIGN KEY (customer_id) REFERENCES shop_customers (id)
);
CREATE TABLE order_items (                -- junction table for the M:N between orders and products
  order_id    INT,
  product_id  INT,
  qty         INT NOT NULL CHECK (qty > 0),
  unit_price  DECIMAL(10,2) NOT NULL,     -- price at the time of sale: history, not redundancy
  PRIMARY KEY (order_id, product_id),
  FOREIGN KEY (order_id) REFERENCES shop_orders (id),
  FOREIGN KEY (product_id) REFERENCES products (id)
);
```

## Boyce-Codd Normal Form (BCNF) | violet
- A stricter 3NF: **for every functional dependency X → Y, X must be a super key**. It differs from 3NF only when a table has overlapping candidate keys.
- Example: `tutoring(student, subject, tutor)`. Each tutor teaches one subject (`tutor → subject`); each student has one tutor per subject, so the key is `(student, subject)`. The table is in 3NF (subject is part of a key), but `tutor` determines `subject` without being a key, so it breaks BCNF: changing a tutor's subject means editing many rows.
- Fix: `tutor_subjects(tutor, subject)` and `student_tutors(student, tutor)`.
- Higher forms (4NF for multi-valued dependencies, 5NF for join dependencies) rarely come up in interviews.

## Denormalisation | sky
- **Deliberately adding redundancy for read performance**: stored totals (`orders.total_amount`), counters (`posts.comment_count`), copied names in reporting tables, pre-joined read models, JSON snapshots.
- Costs: more storage, slower and more complex writes, risk of inconsistency. Keep copies in sync with transactions, triggers, or asynchronous jobs, and **denormalise only after measuring** a real read problem.
- **OLTP** (day-to-day transactions: many small reads and writes) → normalised, usually 3NF. **OLAP** (analytics: big scans and aggregations) → denormalised **star schema** (one central **fact table** of events with **dimension tables** such as date, product and customer) or snowflake schema (normalised dimensions).

## Schema Design Checklist | rose
- Surrogate primary keys (`BIGINT` identity or UUIDv7) plus UNIQUE constraints on natural keys.
- Consistent naming: snake_case, `_id` suffix for foreign keys, one convention for plural or singular table names.
- Correct types: DECIMAL for money, time-zone-aware timestamps, the smallest integer that fits.
- `NOT NULL` by default; foreign keys with **indexes on the FK columns**; CHECK constraints for simple rules.
- Junction tables for M:N; `created_at` / `updated_at` columns; soft delete only when needed.
- Avoid: comma-separated lists in a column, EAV (entity-attribute-value) tables for core data, one giant table for everything, storing derived data without a sync plan.

## Interview Q&A | sky | wide
Q: What is normalisation and why do it?
A: Organising tables by their functional dependencies to remove redundancy, which prevents update, insert and delete anomalies and keeps data consistent.
Q: Explain 1NF, 2NF and 3NF.
A: 1NF: atomic values, no repeating groups, a key. 2NF: 1NF plus no non-key column depending on only part of a composite key. 3NF: 2NF plus no non-key column depending on another non-key column.
Q: What is the difference between 3NF and BCNF?
A: 3NF allows a dependency X → Y when Y is part of a candidate key. BCNF requires the left side of every functional dependency to be a super key. They differ only with overlapping candidate keys.
Q: What is a functional dependency?
A: A rule X → Y meaning each value of X determines exactly one value of Y, such as employee_id → name.
Q: Partial vs transitive dependency?
A: A partial dependency is on part of a composite key (fixed by 2NF). A transitive dependency is a non-key column depending on another non-key column (fixed by 3NF).
Q: When would you denormalise?
A: When measured read performance requires it, typically for reporting, dashboards, counters or high-read APIs, accepting extra write cost and keeping the copies in sync.
Q: What are the disadvantages of normalisation?
A: More tables and joins, so some reads are more complex and slower. That is why analytics systems denormalise.
Q: OLTP vs OLAP?
A: OLTP serves many small, concurrent transactions and is normalised. OLAP serves large analytical queries over history and uses denormalised star or snowflake schemas, often in column stores.
Q: What is a star schema?
A: A central fact table holding measurable events (sales lines) with foreign keys to surrounding dimension tables (date, product, store, customer) that describe them.

# 15 | Transactions, ACID & Isolation Levels | BEGIN, COMMIT, ROLLBACK, SAVEPOINT, ACID and WAL, read phenomena, isolation levels per database, MVCC vs locking, row locks, deadlocks | Transactions & ACID

## Transactions | rose
```sql transaction
BEGIN;                                    -- MySQL: START TRANSACTION   SQL Server: BEGIN TRANSACTION
UPDATE accounts SET balance = balance - 500 WHERE id = 1;
SAVEPOINT after_debit;
UPDATE accounts SET balance = balance + 500 WHERE id = 2;
-- ROLLBACK TO SAVEPOINT after_debit;     -- would undo only the second update
COMMIT;                                   -- make both permanent (ROLLBACK would undo both)
```
- A **transaction** is a group of statements that succeeds or fails **as one unit**: money leaves account 1 and arrives in account 2, or neither happens.
- **Savepoints** mark a point you can roll back to without abandoning the whole transaction. SQL Server writes `SAVE TRANSACTION name` and `ROLLBACK TRANSACTION name`.
- **Autocommit**: without BEGIN, MySQL, PostgreSQL and SQL Server commit every statement on its own. DDL commits implicitly in MySQL and Oracle.
- **Errors inside a transaction**: PostgreSQL marks the whole transaction failed ("current transaction is aborted") until you ROLLBACK (or roll back to a savepoint). MySQL rolls back only the failed statement and keeps the transaction open. SQL Server may continue after some errors, so use `SET XACT_ABORT ON` with `TRY...CATCH`.
- **Keep transactions short**: they hold locks, and in PostgreSQL a long-open transaction stops VACUUM from cleaning up old row versions. Never wait for user input inside one.

## ACID | blue
- **Atomicity**: all or nothing. If anything fails, or the server crashes mid-way, partial changes are undone.
- **Consistency**: every transaction moves the database from one valid state to another; constraints, foreign keys and checks always hold at commit.
- **Isolation**: concurrent transactions don't see each other's uncommitted work, to the degree chosen by the **isolation level**.
- **Durability**: once COMMIT returns, the change survives a crash or power loss.
- How databases deliver it: **WAL (write-ahead logging)**. Every change is written to a sequential log and flushed to disk at COMMIT **before** the data pages themselves are written. After a crash the database replays the log: committed work is redone (**redo**), uncommitted work is undone (**undo**). PostgreSQL calls it the WAL, MySQL InnoDB the redo log (plus undo logs), SQL Server the transaction log.
> One-liner: "Atomicity via undo, durability via the write-ahead log, isolation via locks or MVCC, consistency via constraints."

## Read Phenomena | green
- **Dirty read**: T1 reads a change T2 has **not committed**; T2 then rolls back, so T1 used data that never existed.
- **Non-repeatable read**: T1 reads a row twice and gets different values, because T2 **updated and committed** it in between.
- **Phantom read**: T1 runs the same range query twice and gets **new or missing rows**, because T2 **inserted or deleted** matching rows.
- **Lost update**: T1 and T2 both read a balance of 100, each adds to it and writes back, and one change overwrites the other.
- **Write skew**: two transactions read the same data and each update **different** rows, together breaking a rule (two doctors both go off call because each saw the other still on call).

## Isolation Levels | amber
```text
Level              Dirty read   Non-repeatable read   Phantom read
READ UNCOMMITTED   possible     possible              possible
READ COMMITTED     prevented    possible              possible
REPEATABLE READ    prevented    prevented             possible (per the standard)
SERIALIZABLE       prevented    prevented             prevented
```
- Higher levels prevent more anomalies but cost more locking, blocking or aborted transactions, so throughput drops.
- **Defaults**: MySQL InnoDB **REPEATABLE READ**; PostgreSQL, SQL Server and Oracle **READ COMMITTED**; SQLite effectively SERIALIZABLE.
- **PostgreSQL**: READ UNCOMMITTED behaves like READ COMMITTED (it never shows dirty data). REPEATABLE READ is **snapshot isolation** and also prevents phantoms; a conflicting update fails with a serialization error. SERIALIZABLE uses **SSI** (Serializable Snapshot Isolation), which detects write skew and aborts one transaction (error `40001`), so the **application must retry**.
- **MySQL InnoDB REPEATABLE READ**: plain SELECTs read a consistent snapshot; locking reads and writes take **next-key (gap) locks** that block inserts into the range, preventing phantoms.
- **SQL Server**: lock-based by default, so under READ COMMITTED readers wait for writers. Turning on `READ_COMMITTED_SNAPSHOT` or `SNAPSHOT` isolation switches to row versions kept in tempdb. The `WITH (NOLOCK)` hint means READ UNCOMMITTED: dirty reads, and rows can even be skipped or read twice.
- **Oracle**: offers only READ COMMITTED and SERIALIZABLE, both snapshot-based; readers never block writers.
```sql
SET TRANSACTION ISOLATION LEVEL SERIALIZABLE;
SHOW transaction_isolation;               -- serializable
```
- PostgreSQL: run `SET TRANSACTION` as the first statement inside BEGIN (or write `BEGIN ISOLATION LEVEL SERIALIZABLE`). MySQL: run it before `START TRANSACTION`; it applies to the next transaction (`SELECT @@transaction_isolation` shows the session level). SQL Server: it applies to the session.

## MVCC, Locks and Row Locking | violet
- **MVCC (Multi-Version Concurrency Control)**: a writer creates a **new version** of a row instead of overwriting it, and each reader sees the version that matches its snapshot. Result: **readers don't block writers and writers don't block readers**. PostgreSQL keeps old versions in the table (cleaned by VACUUM); InnoDB and Oracle rebuild them from undo logs; SQL Server uses tempdb when snapshot options are on.
- **Locks**: **shared (S)** locks for reading, **exclusive (X)** locks for writing; writers always block other writers of the same row. Granularity: row, page, table. SQL Server can **escalate** many row locks into one table lock.
- **Explicit row locks**: `SELECT ... FOR UPDATE` locks the rows you are about to change (PostgreSQL, MySQL, Oracle; SQL Server uses `WITH (UPDLOCK, ROWLOCK)`). `FOR SHARE` lets others read but not change them. `NOWAIT` fails instead of waiting.
- **`SKIP LOCKED`** (PostgreSQL 9.5+, MySQL 8.0, Oracle; SQL Server's `READPAST` hint) skips rows other transactions have locked: the standard way to build a **job queue** where each worker grabs a different row.
```sql
SELECT id, amount
FROM orders
WHERE status = 'pending'
ORDER BY id
LIMIT 1
FOR UPDATE SKIP LOCKED;                   -- 105, locked until this transaction ends
```
- **Fixing lost updates**: make the update atomic (`UPDATE stock SET qty = qty - 1 WHERE id = 7 AND qty > 0`), lock first with `SELECT ... FOR UPDATE` (**pessimistic**), or keep a version column and check it (**optimistic**: `UPDATE ... SET version = version + 1 WHERE id = 7 AND version = 3`; 0 rows updated means someone else won, so retry).

## Deadlocks | sky
- T1 locks row A and waits for B; T2 locks B and waits for A. Neither can proceed: a **deadlock**.
- The database detects the cycle and **kills one transaction** (the victim) with an error: MySQL `1213`, PostgreSQL `40P01`, SQL Server `1205`. The application must catch it and **retry** the transaction.
- Prevention: **access rows in a consistent order** (for example by ascending id), keep transactions short, index the columns in WHERE clauses so fewer rows get locked, and use the lowest isolation level that is correct.

## Interview Q&A | sky | wide
Q: What is a transaction?
A: A sequence of operations executed as one unit of work: either all of its changes are committed or none are.
Q: Explain ACID.
A: Atomicity (all or nothing), Consistency (constraints always hold), Isolation (concurrent transactions don't interfere beyond the chosen level) and Durability (committed data survives crashes, thanks to the write-ahead log).
Q: What are dirty reads, non-repeatable reads and phantom reads?
A: A dirty read sees uncommitted data. A non-repeatable read gets a different value when re-reading a row another transaction updated. A phantom read gets different rows when re-running a range query after another transaction inserted or deleted rows.
Q: What are the isolation levels and their default per database?
A: READ UNCOMMITTED, READ COMMITTED, REPEATABLE READ and SERIALIZABLE. MySQL InnoDB defaults to REPEATABLE READ; PostgreSQL, SQL Server and Oracle default to READ COMMITTED.
Q: What is MVCC?
A: Multi-version concurrency control: writers create new row versions and readers read a consistent snapshot, so reads and writes don't block each other. Old versions are cleaned up later (VACUUM in PostgreSQL, undo purge in InnoDB).
Q: Optimistic vs pessimistic locking?
A: Pessimistic locking locks rows up front (SELECT ... FOR UPDATE) and suits high contention. Optimistic locking checks a version column at update time and retries on conflict; it suits low contention and avoids holding locks.
Q: What is a deadlock and how do you handle it?
A: Two transactions each wait for a lock the other holds. The database aborts one; the app retries it. Reduce them with a consistent lock order, short transactions and good indexes.
Q: What happens if the server crashes in the middle of a transaction?
A: On restart the database replays its log: committed transactions are redone and uncommitted ones are rolled back, so the partial transaction disappears.
Q: What does SELECT ... FOR UPDATE do?
A: It reads rows and locks them exclusively until the transaction ends, so no one else can change or lock them in between. Add SKIP LOCKED to skip already-locked rows, as in a job queue.
Q: Why is NOLOCK dangerous in SQL Server?
A: It reads uncommitted data, so results can include rolled-back changes, and during page splits it can skip rows or read them twice.

# 16 | Indexing Deep Dive | B-tree and B+tree vs hash, clustered vs non-clustered, composite indexes and the leftmost prefix rule, covering, partial and expression indexes, when indexes are skipped, PostgreSQL GIN, GiST, BRIN and pgvector | Indexes

## What an Index Is | rose
- An **index** is a separate data structure, kept sorted by its key, that maps key values to row locations: like the index at the back of a book. The database can **seek** straight to matching rows instead of **scanning** the whole table.
- Speeds up WHERE, JOIN, ORDER BY, GROUP BY and MIN/MAX.
- Costs: **every INSERT, UPDATE and DELETE must also update every index**, extra disk and memory, and more work for the optimiser.
```sql
CREATE INDEX idx_employees_dept ON employees (dept_id);
CREATE INDEX idx_orders_cust_date ON orders (customer_id, order_date);
CREATE UNIQUE INDEX idx_departments_lower_name ON departments (LOWER(name));
DROP INDEX idx_employees_dept;            -- MySQL and SQL Server: DROP INDEX idx_employees_dept ON employees
```
- **PRIMARY KEY and UNIQUE constraints create an index automatically. Foreign keys don't** (except in MySQL InnoDB).

## B-Tree / B+Tree vs Hash | blue
- The default index everywhere is a **B+tree** (usually just called "B-tree"): a balanced tree whose **leaf pages hold the keys in sorted order and are linked to each other**. Inner pages only route the search.
- Each page holds hundreds of keys (high **fan-out**), so even millions of rows need only **3 or 4 levels**: a lookup reads 3 or 4 pages, O(log n).
- Because leaves are sorted and linked, a B+tree supports `=`, `<`, `>`, `BETWEEN`, prefix `LIKE 'abc%'`, `ORDER BY` without sorting, and MIN/MAX.
- A **hash index** stores `hash(key) → rows`: O(1) for **equality only**. No ranges, sorting or prefix search.
- Availability: PostgreSQL has `USING HASH`. MySQL InnoDB has no user-created hash indexes (it builds an internal **adaptive hash index** on hot pages; the MEMORY engine has HASH). SQL Server has hash indexes only for memory-optimised tables.

## Clustered vs Non-Clustered | green
- A **clustered index** stores the **table rows themselves in index order**: the leaf level *is* the data. So a table can have **only one**. Range scans on the clustered key read neighbouring rows from neighbouring pages.
- A **non-clustered (secondary) index** is a separate structure whose leaves point to the row. A table can have many. Finding columns that aren't in the index needs an extra lookup per row (**key lookup** in SQL Server, **heap fetch** in PostgreSQL).
- **MySQL InnoDB**: every table is clustered by its **primary key** (or the first UNIQUE NOT NULL index, or a hidden row id). Secondary indexes store the **PK value** as the pointer, so keep PKs short; **random UUID PKs** insert all over the tree and cause page splits (prefer sequential ids or UUIDv7).
- **SQL Server**: you choose any one clustered index (a PRIMARY KEY creates it by default). A table without one is a **heap**.
- **PostgreSQL**: every table is a **heap** and every index is secondary. `CLUSTER` reorders a table once, but the order is not maintained.
- **Oracle**: heap tables by default; an **index-organised table (IOT)** is the clustered form.

## Composite Indexes and the Leftmost Prefix Rule | amber
```sql
CREATE INDEX idx_emp_dept_city_salary ON employees (dept_id, city, salary);

-- The index can be used to seek (a leftmost prefix of its columns is constrained):
--   WHERE dept_id = 1
--   WHERE dept_id = 1 AND city = 'Bengaluru'
--   WHERE dept_id = 1 AND city = 'Bengaluru' AND salary > 100000
--   WHERE dept_id = 1 ORDER BY city                 (rows come out already sorted)
-- Only partly: seek on dept_id, then filter salary inside the index:
--   WHERE dept_id = 1 AND salary > 100000
-- Can't seek (the leading column is missing):
--   WHERE city = 'Bengaluru'
--   WHERE salary > 100000
```
- A composite index is sorted by the first column, then the second within it, and so on, like a phone book sorted by surname then first name. You can't find "everyone named Ravi" quickly in a book sorted by surname.
- **Column order**: put columns compared with **equality first**, then the **range or sort** column. A range condition on one column stops seeking on the columns after it.
- An index on `(a, b)` makes a separate index on `(a)` redundant.
- **Skip scan** softens the rule when the leading column has few distinct values: Oracle, MySQL 8.0.13+ and **PostgreSQL 18** can jump through each leading value.

## Covering, Partial and Expression Indexes | violet
```sql
CREATE INDEX idx_orders_status_amount ON orders (status) INCLUDE (amount);        -- covering (PostgreSQL 11+, SQL Server)
SELECT SUM(amount) FROM orders WHERE status = 'pending';                          -- can be answered from the index alone

CREATE INDEX idx_orders_pending_date ON orders (order_date) WHERE status = 'pending';   -- partial / filtered index

CREATE INDEX idx_emp_lower_email ON employees (LOWER(email));                      -- expression index
SELECT name FROM employees WHERE LOWER(email) = 'asha@corp.com';                   -- Asha (uses the index)
```
- **Covering index**: contains every column a query needs, so the table is never touched: **Index Only Scan** in PostgreSQL, "Using index" in MySQL. `INCLUDE` adds non-key payload columns without affecting sort order.
- **Partial (filtered) index**: indexes only rows matching a WHERE (PostgreSQL, SQLite; SQL Server "filtered index"). Small and fast when queries target a subset, such as pending orders or non-deleted rows.
- **Expression (functional) index**: indexes the result of an expression. The query must use the **same expression**. MySQL 8.0.13+ supports it with double parentheses: `CREATE INDEX idx ON employees ((LOWER(email)))`.

## When Indexes Are Not Used | rose
- **Function or arithmetic on the column**: `WHERE EXTRACT(YEAR FROM hire_date) = 2020`, `WHERE salary * 1.1 > 100000`. Rewrite so the bare column is compared (a **sargable** predicate, from "Search ARGument ABLE"):
```sql
SELECT name FROM employees WHERE EXTRACT(YEAR FROM hire_date) = 2020;                      -- not sargable
SELECT name FROM employees WHERE hire_date >= DATE '2020-01-01' AND hire_date < DATE '2021-01-01';   -- sargable
-- both return Meera, Vikram
```
- **Leading wildcard**: `LIKE '%son'`.
- **Implicit type conversion**: a VARCHAR column compared with a number.
- **Missing leading column** of a composite index.
- **Low selectivity**: `WHERE status = 'active'` when 95% of rows are active; reading the whole table sequentially is cheaper than millions of index lookups.
- **Small tables**, where a scan is cheaper anyway.
- **OR across different columns** (may need two indexes combined with a bitmap OR or index merge), and often `<>` or `NOT IN`.
- **Stale statistics**: the planner misjudges row counts. Run `ANALYZE` (PostgreSQL), `ANALYZE TABLE` (MySQL) or `UPDATE STATISTICS` (SQL Server).

## PostgreSQL Index Types and pgvector | blue
- **B-tree** (default): equality, ranges, sorting.
- **Hash**: equality only.
- **GIN (Generalized Inverted Index)**: for values that contain many items: **JSONB** (`@>`), **arrays** (`@>`, `&&`), **full-text search** (`tsvector @@ tsquery`), and `LIKE '%x%'` with the `pg_trgm` extension.
- **GiST (Generalized Search Tree)**: geometric and spatial data (PostGIS), ranges, nearest-neighbour ordering, and **exclusion constraints** (no overlapping room bookings).
- **BRIN (Block Range Index)**: stores only the min and max per block range, so it is tiny. Ideal for huge tables whose physical order follows the column, such as append-only `created_at` logs.
- **pgvector** extension: a `vector(n)` column type for embeddings, approximate nearest-neighbour indexes **HNSW** and **IVFFlat**, and distance operators `<->` (L2 / Euclidean), `<=>` (cosine distance), `<#>` (negative inner product).
```sql PostgreSQL
CREATE TABLE docs (
  id          BIGINT PRIMARY KEY,
  body        TEXT,
  tags        TEXT[],
  meta        JSONB,
  created_at  TIMESTAMPTZ
);
CREATE INDEX idx_docs_meta ON docs USING GIN (meta);
CREATE INDEX idx_docs_tags ON docs USING GIN (tags);
CREATE INDEX idx_docs_fts  ON docs USING GIN (TO_TSVECTOR('english', body));
CREATE INDEX idx_docs_time ON docs USING BRIN (created_at);

SELECT id FROM docs WHERE meta @> '{"lang": "en"}' AND tags && ARRAY['sql'];
SELECT id FROM docs WHERE TO_TSVECTOR('english', body) @@ TO_TSQUERY('english', 'index & tuning');
```
```sql pgvector
CREATE EXTENSION vector;
CREATE TABLE items (id BIGINT PRIMARY KEY, embedding vector(3));
CREATE INDEX ON items USING hnsw (embedding vector_cosine_ops);
SELECT id FROM items ORDER BY embedding <=> '[0.1, 0.2, 0.3]' LIMIT 5;   -- 5 nearest by cosine distance
```

## Index Good Practice | green
- Index **foreign key columns** and the columns of your most frequent WHERE, JOIN and ORDER BY clauses; prefer one composite index that matches real queries over many single-column ones.
- **Drop unused indexes**: PostgreSQL `pg_stat_user_indexes` (`idx_scan = 0`), MySQL `sys.schema_unused_indexes`, SQL Server `sys.dm_db_index_usage_stats`.
- High-selectivity columns (many distinct values) benefit most.
- Build indexes on busy tables without blocking writes: PostgreSQL `CREATE INDEX CONCURRENTLY`, MySQL online DDL (`ALGORITHM=INPLACE, LOCK=NONE`), SQL Server `WITH (ONLINE = ON)` (Enterprise edition).

## Interview Q&A | sky | wide
Q: What is an index and what does it cost?
A: A sorted structure that lets the database find rows without scanning the table. It speeds reads but slows every write, because each index must be updated, and it uses storage and memory.
Q: How does a B+tree index work?
A: A balanced tree where inner pages route searches and sorted leaf pages hold keys and row pointers, linked together. Lookups take a few page reads and range scans just walk the linked leaves.
Q: Clustered vs non-clustered index?
A: A clustered index defines the physical order of the table's rows, so there can be only one. A non-clustered index is a separate structure pointing to rows; there can be many, and they may need extra lookups.
Q: How many clustered indexes can a table have?
A: One, because rows can be physically ordered only one way. InnoDB always clusters by the primary key; PostgreSQL has none (tables are heaps).
Q: What is the leftmost prefix rule?
A: A composite index on (a, b, c) can seek on a, (a, b) or (a, b, c), but not on b or c alone, because the index is sorted by a first.
Q: What is a covering index?
A: An index containing every column a query needs, so the query is answered from the index without visiting the table.
Q: Why isn't my index being used?
A: Common reasons: a function or cast on the column, a leading wildcard, the leading column of a composite index is missing, low selectivity, a tiny table or stale statistics.
Q: B-tree vs hash index?
A: A B-tree supports equality, ranges and sorting. A hash index supports only equality, with no ordering.
Q: GIN vs GiST vs BRIN?
A: GIN is an inverted index for multi-valued data (JSONB, arrays, full text). GiST is a balanced search tree for geometry, ranges and nearest-neighbour search. BRIN keeps min/max per block range for huge, naturally ordered tables.
Q: Should you index a low-cardinality column like gender or status?
A: Usually not on its own: it matches too many rows for an index to help. A partial index on a rare value, or a composite index, can still be useful.
Q: Does a foreign key create an index?
A: Not in PostgreSQL, SQL Server or Oracle, where you should usually add one. MySQL InnoDB creates it automatically.

# 17 | EXPLAIN & Performance Tuning | Reading EXPLAIN and EXPLAIN ANALYZE, scan types, join algorithms, MySQL and SQL Server plans, a tuning checklist, connection pooling with HikariCP and PgBouncer | EXPLAIN & Tuning

## Reading EXPLAIN | rose
- `EXPLAIN` shows the plan the optimiser **chose**, with estimates. `EXPLAIN ANALYZE` **runs the query** and adds actual times and row counts. Careful with writes: wrap `EXPLAIN ANALYZE UPDATE ...` in `BEGIN ... ROLLBACK`.
- The plans below are real PostgreSQL 18 output for a 200,000-row `events` table with an index on `user_id`:
```text
EXPLAIN ANALYZE SELECT * FROM events WHERE user_id = 42;

Bitmap Heap Scan on events  (cost=4.60..145.32 rows=40 width=25) (actual time=0.062..0.138 rows=40.00 loops=1)
  Recheck Cond: (user_id = 42)
  Heap Blocks: exact=40
  Buffers: shared hit=40 read=2
  ->  Bitmap Index Scan on idx_events_user  (cost=0.00..4.59 rows=40 width=0) (actual time=0.045..0.046 rows=40.00 loops=1)
        Index Cond: (user_id = 42)
        Index Searches: 1
        Buffers: shared read=2
Planning Time: 0.039 ms
Execution Time: 0.209 ms
```
- The plan is a **tree**: read it from the most indented node outwards; each `->` child feeds its parent.
- `cost=startup..total` is in the planner's abstract units (not ms); `rows` is the **estimated** row count; `width` is average bytes per row.
- With ANALYZE: `actual time=first_row..last_row` in ms, actual `rows`, and `loops` (multiply per-loop numbers by loops). **Compare estimated with actual rows**: a big mismatch means stale or missing statistics.
- `Buffers: shared hit` = pages found in memory, `read` = pages read from disk (PostgreSQL 18 shows buffers by default with ANALYZE; earlier versions need `EXPLAIN (ANALYZE, BUFFERS)`).

## Scan Types | blue
```text
EXPLAIN SELECT * FROM events WHERE kind = 'view';            -- 90% of rows match
Seq Scan on events  (cost=0.00..3971.00 rows=179887 width=25)
  Filter: ((kind)::text = 'view'::text)

EXPLAIN SELECT * FROM events WHERE id = 42;                  -- primary key lookup
Index Scan using events_pkey on events  (cost=0.42..8.44 rows=1 width=25)
  Index Cond: (id = 42)

EXPLAIN SELECT user_id FROM events WHERE user_id = 42;       -- only indexed columns needed
Index Only Scan using idx_events_user on events  (cost=0.29..5.00 rows=40 width=4)
  Index Cond: (user_id = 42)

EXPLAIN SELECT * FROM events WHERE user_id + 0 = 42;         -- arithmetic on the column
Seq Scan on events  (cost=0.00..4471.00 rows=1000 width=25)
  Filter: ((user_id + 0) = 42)
```
- **Seq Scan**: reads every page of the table. Correct for small tables or when many rows match.
- **Index Scan**: walks the index, then fetches each matching row from the table. Best for a few rows.
- **Index Only Scan**: answers from the index alone (a covering index). In PostgreSQL it relies on the **visibility map**, so a recently vacuumed table benefits most.
- **Bitmap Index Scan + Bitmap Heap Scan**: collects matching row locations into a bitmap, then reads table pages in physical order. Used for a medium number of rows, and can combine several indexes (BitmapAnd, BitmapOr).
- The last example shows a non-sargable predicate turning an indexed lookup into a full scan.

## Join Algorithms | green
```text
EXPLAIN SELECT u.name, e.kind FROM users u JOIN events e ON e.user_id = u.id WHERE u.id = 7;
Nested Loop  (cost=4.89..152.54 rows=40 width=10)
  ->  Index Scan using users_pkey on users u  (cost=0.28..8.30 rows=1 width=9)
        Index Cond: (id = 7)
  ->  Bitmap Heap Scan on events e  (cost=4.60..143.84 rows=40 width=9)
        Recheck Cond: (user_id = 7)
        ->  Bitmap Index Scan on idx_events_user  (cost=0.00..4.59 rows=40 width=0)
              Index Cond: (user_id = 7)

EXPLAIN SELECT u.name, COUNT(*) FROM users u JOIN events e ON e.user_id = u.id GROUP BY u.name;
HashAggregate  (cost=4938.94..4988.94 rows=5000 width=13)
  Group Key: u.name
  ->  Hash Join  (cost=139.50..3938.95 rows=200000 width=5)
        Hash Cond: (e.user_id = u.id)
        ->  Seq Scan on events e  (cost=0.00..3274.00 rows=200000 width=4)
        ->  Hash  (cost=77.00..77.00 rows=5000 width=9)
              ->  Seq Scan on users u  (cost=0.00..77.00 rows=5000 width=9)
```
- **Nested Loop**: for each row of the outer input, look up matching inner rows. Fast when the outer side is small and the inner join column is indexed.
- **Hash Join**: build a hash table from the smaller input, then probe it with each row of the larger one. Best for big, unsorted equality joins (MySQL has it since 8.0.18).
- **Merge Join**: both inputs sorted on the join key are walked together. Good for large inputs that are already sorted, for example by an index (MySQL has no merge join).

## Plans in Other Databases | amber
- **MySQL** `EXPLAIN`: the `type` column from worst to best is `ALL` (full table scan), `index` (full index scan), `range`, `ref`, `eq_ref`, `const`/`system`. `key` is the chosen index, `rows` the estimate. `Extra` flags: `Using index` (covering), `Using where`, `Using filesort` (an extra sort), `Using temporary` (a temp table). `EXPLAIN ANALYZE` (8.0.18+) and `EXPLAIN FORMAT=TREE` show the iterator tree.
- **SQL Server**: graphical execution plans in SSMS (estimated: Ctrl+L, actual: Ctrl+M), `SET STATISTICS IO, TIME ON` for reads and timings. Operators: Table Scan, Clustered Index Scan, **Index Seek**, **Key Lookup** (the expensive per-row lookup a covering index removes).
- **Oracle**: `EXPLAIN PLAN FOR <query>;` then `SELECT * FROM TABLE(DBMS_XPLAN.DISPLAY);`.

## Tuning Checklist | violet
- **1. Find the slow queries**: PostgreSQL `pg_stat_statements`, MySQL slow query log (`slow_query_log`, `long_query_time`), SQL Server Query Store, or your APM tool. Optimise by total time (frequency × duration), not only the single slowest query.
- **2. Read the plan** with EXPLAIN ANALYZE: big Seq Scans, estimate vs actual mismatches, sorts or hashes spilling to disk, nested loops over many rows, key lookups.
- **3. Index for the query**: composite indexes in the right column order, covering or partial indexes; make predicates **sargable**.
- **4. Fetch less**: select only needed columns, paginate with keyset pagination, avoid the **N+1 query problem** (one query per row from the application) by batching or joining.
- **5. Keep statistics fresh** and tables healthy: `ANALYZE` and autovacuum in PostgreSQL, `ANALYZE TABLE` in MySQL, `UPDATE STATISTICS` in SQL Server.
- **6. Rewrite**: `UNION ALL` instead of `UNION`, `EXISTS` instead of `DISTINCT` over a join, aggregate before joining, avoid functions on indexed columns.
- **7. Infrastructure**: right data types, enough memory for caching (`shared_buffers`, `innodb_buffer_pool_size`), connection pooling, application caching (Redis), read replicas, partitioning (sheet 18).

## Connection Pooling | sky
- Opening a database connection is expensive: TCP and TLS handshakes, authentication, and in PostgreSQL a whole new server **process** per connection (several MB each). A **pool** keeps connections open and lends them to requests.
- **HikariCP**: the default JDBC pool in Spring Boot. Key settings: `maximumPoolSize` (default 10), `minimumIdle` (defaults to the max), `connectionTimeout` (30 s to wait for a free connection), `idleTimeout` (10 min), `maxLifetime` (30 min; keep it below any database or network idle timeout).
- **PgBouncer**: a lightweight proxy that pools connections in front of PostgreSQL. Modes: **session** (a client keeps one server connection for its whole session), **transaction** (a server connection only for the duration of each transaction: the most efficient, but session state such as `SET` or advisory locks doesn't carry over; prepared statements are supported since PgBouncer 1.21), **statement** (multi-statement transactions not allowed).
- **Pool size**: smaller than people expect. A widely quoted starting point from the PostgreSQL and HikariCP wikis is `connections = (CPU cores × 2) + effective disk spindles`; then measure. The total across all application instances must stay under the database's `max_connections`.
- Other poolers: ProxySQL for MySQL; .NET and JDBC drivers for SQL Server pool connections by default.

## Interview Q&A | sky | wide
Q: How would you optimise a slow query?
A: Reproduce it, run EXPLAIN ANALYZE, find the expensive nodes (full scans, bad row estimates, big sorts, key lookups), then add or fix indexes, make predicates sargable, fetch fewer rows and columns, refresh statistics, and re-measure.
Q: EXPLAIN vs EXPLAIN ANALYZE?
A: EXPLAIN shows the estimated plan without running the query. EXPLAIN ANALYZE executes it and reports actual times and row counts.
Q: Why would the database choose a sequential scan when an index exists?
A: When many rows match (low selectivity), the table is small, statistics are stale, or the predicate isn't sargable. Reading pages sequentially can be cheaper than many random index lookups.
Q: What is an index-only scan?
A: A plan that answers the query entirely from the index because it contains every needed column. PostgreSQL also needs the visibility map to confirm rows are visible.
Q: Name the join algorithms.
A: Nested loop (small outer input with an indexed inner side), hash join (large unsorted equality joins) and merge join (inputs sorted on the join key).
Q: What is the N+1 query problem?
A: Loading a list with one query, then running one more query per item to load related data. Fix it with a join, a batched IN query or eager fetching.
Q: What is a connection pool and why use one?
A: A set of reusable open connections. It avoids the cost of opening connections per request and caps how many connections hit the database.
Q: What are PgBouncer's pooling modes?
A: Session, transaction and statement pooling. Transaction mode gives the best reuse but drops session-level state between transactions.
Q: How large should a connection pool be?
A: Small: roughly CPU cores times two plus disks as a starting point, then tune by measuring. Too many connections cause contention and context switching, and the sum across all app instances must fit within max_connections.

# 18 | Partitioning, Sharding & Replication | Range, list and hash partitioning, partition pruning, sharding strategies and shard keys, read replicas, synchronous vs asynchronous replication, failover | Scaling

## Partitioning | rose
- **Partitioning** splits one large logical table into smaller physical pieces **inside one database server**. Queries still use the parent table name.
- **Range**: by value ranges, typically one partition per month or year. Old data can be archived by **dropping or detaching a partition** instead of a huge DELETE.
- **List**: by discrete values, such as region or country.
- **Hash**: by hash of a key modulo N, spreading rows evenly when there's no natural range.
- Benefits: **partition pruning** (a query that filters on the partition key reads only the matching partitions), smaller indexes, faster maintenance per partition, cheap data retention.
- Costs: queries **without** the partition key must visit every partition; primary keys and unique constraints must include the partition key (PostgreSQL); thousands of partitions slow down planning.
```sql PostgreSQL
CREATE TABLE events (
  id          BIGINT GENERATED ALWAYS AS IDENTITY,
  user_id     BIGINT NOT NULL,
  created_at  TIMESTAMPTZ NOT NULL,
  payload     JSONB,
  PRIMARY KEY (id, created_at)                 -- must include the partition key
) PARTITION BY RANGE (created_at);

CREATE TABLE events_2026_01 PARTITION OF events FOR VALUES FROM ('2026-01-01') TO ('2026-02-01');
CREATE TABLE events_2026_02 PARTITION OF events FOR VALUES FROM ('2026-02-01') TO ('2026-03-01');
CREATE TABLE events_default PARTITION OF events DEFAULT;

CREATE TABLE customers_by_region (id BIGINT, region TEXT NOT NULL) PARTITION BY LIST (region);
CREATE TABLE customers_in PARTITION OF customers_by_region FOR VALUES IN ('IN');
CREATE TABLE customers_us PARTITION OF customers_by_region FOR VALUES IN ('US');

CREATE TABLE sessions (id BIGINT, user_id BIGINT NOT NULL) PARTITION BY HASH (user_id);
CREATE TABLE sessions_p0 PARTITION OF sessions FOR VALUES WITH (MODULUS 2, REMAINDER 0);
CREATE TABLE sessions_p1 PARTITION OF sessions FOR VALUES WITH (MODULUS 2, REMAINDER 1);

ALTER TABLE events DETACH PARTITION events_2026_01;   -- archive January without a DELETE
```
- MySQL declares partitions inside CREATE TABLE (`PARTITION BY RANGE / LIST / HASH / KEY`). SQL Server uses a **partition function** plus a **partition scheme** (range only).
- **Vertical partitioning** splits **columns** instead of rows, for example moving rarely used large columns into a separate table.

## Sharding | blue
- **Sharding** is horizontal partitioning **across several database servers**. Each shard holds a subset of the rows with the same schema. It scales **writes and storage** beyond one machine.
- **Range-based**: user ids 1 to 1M on shard 1, and so on. Simple, but new or popular ranges create hotspots.
- **Hash-based**: `hash(user_id) % N`. Even spread, but changing N moves most data, which is why **consistent hashing** is used.
- **Directory / lookup-based**: a mapping service says which shard holds each key. Flexible, at the cost of an extra lookup and another component.
- **Geo or tenant-based**: by region or customer, which also helps data-residency rules.
- **Choosing a shard key**: high cardinality, even distribution, and present in most queries so each query hits a single shard (for example `tenant_id` or `user_id`).
- Pain points: **cross-shard joins and transactions**, globally unique ids (UUIDs, Snowflake-style ids), rebalancing, hotspots, operational overhead. Exhaust query tuning, vertical scaling, caching, read replicas and partitioning first.
- Tools: **Vitess** (MySQL, built at YouTube), **Citus** (PostgreSQL extension), application-level routing; distributed SQL databases (CockroachDB, YugabyteDB, Google Spanner, TiDB) shard automatically.

## Replication | green
- **Replication** copies data from a **primary** (master) to one or more **replicas** (standbys, formerly "slaves"). Purposes: **read scaling**, **high availability** (failover) and offloading backups or reports.
- **Read replicas**: send writes to the primary and reads to replicas. Watch **replication lag**: a user who just saved something may not see it on a replica (**read-your-own-writes**). Route that user's reads to the primary for a short time, or read critical data from the primary.
- **Asynchronous** replication: the primary commits without waiting for replicas. Fast, but if the primary dies, the most recent commits can be lost. The default in MySQL and PostgreSQL.
- **Synchronous** replication: COMMIT waits until a replica confirms. No data loss on failover, but higher write latency, and writes stall if the synchronous replica is unavailable. **Semi-synchronous** (MySQL): the primary waits until at least one replica has **received** the transaction (not necessarily applied it).
- Mechanisms: PostgreSQL **streaming replication** ships the WAL (physical copy of the whole cluster) and **logical replication** sends row changes per table (publications and subscriptions). MySQL replicates through the **binary log** (row-based or statement-based), with GTIDs and **Group Replication** / InnoDB Cluster. SQL Server has **Always On availability groups** and log shipping. Oracle has **Data Guard**.
- **Failover**: promote a replica to primary, automatically with tools like Patroni (PostgreSQL), MySQL InnoDB Cluster, or managed services such as Amazon RDS Multi-AZ.
- **Multi-primary** (multi-master): several nodes accept writes (Galera, Group Replication multi-primary mode). Conflicts must be detected and resolved.
- **Replication is not a backup**: an accidental `DELETE` replicates within milliseconds. Keep point-in-time backups too.

## A Typical Scaling Path | amber
```text
1. Fix queries and indexes (most performance problems end here)
2. Scale up: more CPU, RAM and faster disks
3. Connection pooling and application caching (Redis)
4. Read replicas for read-heavy traffic
5. Partition the biggest tables (time-based data, archiving)
6. Shard, or move to distributed SQL, when writes or storage outgrow one primary
```

## Interview Q&A | sky | wide
Q: Partitioning vs sharding?
A: Partitioning splits a table into pieces within one database server. Sharding spreads rows across multiple servers, each holding part of the data.
Q: What types of partitioning are there?
A: Range (date ranges), list (discrete values such as region) and hash (even spread by hashed key). Vertical partitioning splits columns rather than rows.
Q: What is partition pruning?
A: The planner skipping partitions that can't contain matching rows because the query filters on the partition key.
Q: How do you choose a shard key?
A: Pick a column with many distinct, evenly distributed values that appears in most queries, so that each query goes to a single shard and no shard becomes a hotspot.
Q: Synchronous vs asynchronous replication?
A: Synchronous waits for a replica to confirm before COMMIT returns: no data loss on failover but slower writes. Asynchronous returns immediately: faster but can lose the last transactions and lets replicas lag.
Q: What is replication lag, and how do you deal with it?
A: The delay before a replica reflects the primary's changes. Route reads that must be fresh (right after a user's write) to the primary, monitor lag, and keep replicas sized for the write load.
Q: Master-slave vs master-master?
A: Primary-replica has one writable node and read-only copies, which is simple and conflict-free. Multi-primary allows writes on several nodes for availability, but needs conflict detection and resolution.
Q: Vertical vs horizontal scaling for databases?
A: Vertical means a bigger machine: simple, no code changes, but limited. Horizontal means more machines: read replicas for reads, sharding for writes, at the cost of complexity.
Q: Is replication a backup?
A: No. Replication copies mistakes instantly. You still need backups with point-in-time recovery.

## Q1. Second Highest Salary (LeetCode 176) | blue
- Return the second highest **distinct** salary, or NULL if there isn't one.
```sql
SELECT MAX(salary) AS second_highest
FROM employees
WHERE salary < (SELECT MAX(salary) FROM employees);              -- 120000.00

-- Alternative 1: OFFSET, wrapped so that "no row" becomes NULL
SELECT (SELECT DISTINCT salary FROM employees ORDER BY salary DESC LIMIT 1 OFFSET 1) AS second_highest;

-- Alternative 2: DENSE_RANK
SELECT MAX(salary) AS second_highest
FROM (SELECT salary, DENSE_RANK() OVER (ORDER BY salary DESC) AS r FROM employees) t
WHERE r = 2;                                                    -- MAX returns NULL when no row has r = 2
```
- Traps: forgetting **DISTINCT** (with salaries 150, 150, 120 the OFFSET version would return 150 instead of 120), and returning **no row** instead of NULL when there is only one distinct salary.

## Q2. Nth Highest Salary (LeetCode 177) | green
```sql
-- N = 3: the third highest distinct salary
SELECT DISTINCT salary
FROM (SELECT salary, DENSE_RANK() OVER (ORDER BY salary DESC) AS r FROM employees) t
WHERE r = 3;                                                    -- 98000.00

SELECT DISTINCT salary FROM employees ORDER BY salary DESC LIMIT 1 OFFSET 2;   -- 98000.00 (OFFSET N - 1)
```
- **DENSE_RANK**, not RANK: with RANK the two 120000 salaries take ranks 2 and 2, so rank 3 doesn't exist.
- In a MySQL function, `LIMIT` can't take an expression: compute `SET N = N - 1;` first and then `LIMIT 1 OFFSET N`. SQL Server: `OFFSET @n - 1 ROWS FETCH NEXT 1 ROWS ONLY`.

## Q3. Duplicate Emails and Deleting Them (LeetCode 182 and 196) | amber
```sql
SELECT email, COUNT(*) AS times
FROM person
GROUP BY email
HAVING COUNT(*) > 1
ORDER BY email;                                                 -- a@x.com 2 | b@x.com 2

-- Delete duplicates, keeping the lowest id
DELETE FROM person p
USING person q
WHERE p.email = q.email AND p.id > q.id;                         -- PostgreSQL: deletes ids 3 and 5

-- Portable version with a window function
DELETE FROM person
WHERE id IN (
  SELECT id FROM (
    SELECT id, ROW_NUMBER() OVER (PARTITION BY email ORDER BY id) AS rn FROM person
  ) t
  WHERE rn > 1
);                                                              -- deletes ids 3 and 5
```
```sql MySQL
DELETE p FROM person p
JOIN person q ON p.email = q.email AND p.id > q.id;
```
```sql SQL-Server
WITH ranked AS (
  SELECT id, ROW_NUMBER() OVER (PARTITION BY email ORDER BY id) AS rn FROM person
)
DELETE FROM ranked WHERE rn > 1;                                -- SQL Server can delete through a CTE
```
- The portable version also works in MySQL 8: the window function forces the derived table to be materialised, which avoids error 1093 (selecting from the table being modified).

WITH ranked AS (

## Q8. Consecutive Numbers (LeetCode 180) | green
- Numbers that appear at least three times in a row (ordered by id).
```sql
SELECT DISTINCT num AS consecutive_num
FROM (
  SELECT num,
         LAG(num, 1) OVER (ORDER BY id) AS prev1,
         LAG(num, 2) OVER (ORDER BY id) AS prev2
  FROM logs
) t
WHERE num = prev1 AND num = prev2
ORDER BY num;                                                   -- 1, 2

-- Self-join version (assumes ids have no gaps)
SELECT DISTINCT a.num
FROM logs a
JOIN logs b ON b.id = a.id + 1 AND b.num = a.num
JOIN logs c ON c.id = a.id + 2 AND c.num = a.num
ORDER BY a.num;                                                 -- 1, 2
```
- LAG follows **row order**, so it still works if ids have gaps; the self join compares **id values** and breaks on gaps.

## Q9. Rising Temperature (LeetCode 197) | amber
- Dates whose temperature is higher than the **previous calendar day's**.
```sql
SELECT w.id, w.record_date
FROM weather w
JOIN weather y ON y.record_date = w.record_date - 1
WHERE w.temperature > y.temperature
ORDER BY w.id;                                                  -- 2 (Jan 2), 5 (Jan 6)
```
- Jan 5 is **not** returned: Jan 4 is missing, so there is no "yesterday" to compare with.
- The **trap**: `LAG(temperature) OVER (ORDER BY record_date)` compares with the previous **row**, which wrongly reports Jan 5 (30 > 20 on Jan 3). Check the gap too:
```sql
SELECT id, record_date
FROM (
  SELECT id, record_date, temperature,
         LAG(temperature) OVER (ORDER BY record_date) AS prev_temp,
         LAG(record_date) OVER (ORDER BY record_date) AS prev_date
  FROM weather
) t
WHERE temperature > prev_temp AND record_date - prev_date = 1
ORDER BY id;                                                    -- 2, 5
```
- Previous day in other dialects: MySQL `DATE_SUB(w.record_date, INTERVAL 1 DAY)` or `DATEDIFF(w.record_date, y.record_date) = 1`; SQL Server `DATEADD(day, -1, w.record_date)`.

## Q10. Consecutive Login Streaks: Gaps and Islands | violet
- For each user, find runs of consecutive login days of length 2 or more (the pattern behind "Game Play Analysis", "active users N days in a row" and HackerRank's "SQL Project Planning").
```sql
WITH numbered AS (
  SELECT user_id, login_date,
         login_date - CAST(ROW_NUMBER() OVER (PARTITION BY user_id ORDER BY login_date) AS INT) AS island
  FROM logins
)
SELECT user_id, MIN(login_date) AS streak_start, MAX(login_date) AS streak_end, COUNT(*) AS days
FROM numbered
GROUP BY user_id, island
HAVING COUNT(*) >= 2
ORDER BY user_id, streak_start;
-- 1 | 2026-03-01 | 2026-03-03 | 3
-- 2 | 2026-03-03 | 2026-03-04 | 2
```
- The trick: within a run of consecutive dates, **date minus row number is constant**. That constant ("island") becomes the GROUP BY key.
- Dialects: MySQL `DATE_SUB(login_date, INTERVAL rn DAY)`; SQL Server `DATEADD(day, -rn, login_date)`.

# 20 | Rapid-Fire & Tricky Questions | NULL and join gotchas, dialect one-liners, cheat sheet, how to answer, big Q&A | Rapid-fire

## Gotchas That Catch People | rose
- `NULL = NULL` is NULL (unknown), not TRUE: use `IS NULL` or `IS NOT DISTINCT FROM`.
- `NOT IN (subquery)` returns **no rows** if the subquery contains a NULL: use NOT EXISTS.
- `COUNT(col)` skips NULLs; `COUNT(*)` doesn't. `AVG` divides by the non-NULL count.
- `SUM` over zero rows is NULL, not 0: wrap it in COALESCE.
- A WHERE condition on the right table of a LEFT JOIN turns it into an INNER JOIN.
- `BETWEEN` on timestamps misses most of the last day: use `>= start AND < next_day`.
- `LIMIT` without `ORDER BY` returns arbitrary rows.
- `7 / 2 = 3` in PostgreSQL and SQL Server; `3.5000` in MySQL.
- `UNION` silently removes duplicates; `UNION ALL` doesn't.
- `DISTINCT` applies to the whole row, not the first column.
- A SELECT alias can't be used in WHERE; window functions can't be filtered in WHERE.
- `ROW_NUMBER` assigns ties in arbitrary order unless you add a tie-breaker.
- `LAST_VALUE` with ORDER BY returns the current row (default frame).
- Oracle treats `''` as NULL; MySQL and SQL Server compare strings case-insensitively by default.
- SQL Server allows only one NULL in a UNIQUE column; PostgreSQL and MySQL allow many.
- TRUNCATE can be rolled back in PostgreSQL and SQL Server, not in MySQL or Oracle.
- A CHECK constraint passes when its expression is NULL (only FALSE is rejected).
- `AVG(int_column)` truncates to an integer in SQL Server.

## One-Line Cheat Sheet | green
- **Order**: FROM → WHERE → GROUP BY → HAVING → SELECT → DISTINCT → ORDER BY → LIMIT.
- **Sub-languages**: DDL (CREATE, ALTER, DROP, TRUNCATE), DML (INSERT, UPDATE, DELETE), DQL (SELECT), DCL (GRANT, REVOKE), TCL (COMMIT, ROLLBACK).
- **Keys**: PK = unique + not null, one per table; FK = referential integrity; UNIQUE allows NULLs.
- **Joins**: INNER = matches; LEFT/RIGHT = all of one side; FULL = all of both (not in MySQL); CROSS = product; SELF = same table twice.
- **Ranking**: ROW_NUMBER 1234, RANK 1224, DENSE_RANK 1223.
- **Top N per group**: rank with PARTITION BY in a CTE, filter outside.
- **Dialects**: LIMIT (MySQL/PG) vs TOP (SQL Server) vs FETCH FIRST (Oracle, standard); AUTO_INCREMENT vs IDENTITY vs GENERATED AS IDENTITY; IFNULL vs ISNULL vs NVL vs COALESCE; `||` vs `+` vs CONCAT.
- **ACID**: atomicity, consistency, isolation, durability. **Defaults**: MySQL REPEATABLE READ, others READ COMMITTED.
- **Indexes**: B+tree default; one clustered index; leftmost prefix; covering = no table access; sargable predicates.
- **Normal forms**: 1NF atomic, 2NF no partial dependency, 3NF no transitive dependency, BCNF every determinant is a key.
- **Scaling**: indexes → bigger box → cache and pool → read replicas → partitions → shards.

## How to Answer Well | amber
- **Definition → small example → when you'd use it → trade-off**, then stop.
- For query questions, **say the grain and edge cases first** ("one row per department; ties included; NULL departments excluded"), then write the query step by step with CTEs.
- Name the **dialect** you're writing and mention the equivalent in the interviewer's database if it differs (LIMIT vs TOP).
- Tie answers to experience: "A report query took 40 s because of `WHERE DATE(created_at) = ...`; rewriting it as a range let it use the index and it dropped to 30 ms."

## Big Interview Q&A | sky | wide
Q: What is the difference between DELETE, TRUNCATE and DROP?
A: DELETE removes chosen rows with full logging and triggers. TRUNCATE quickly removes all rows and resets identity. DROP removes the table itself.
Q: WHERE vs HAVING?
A: WHERE filters rows before grouping; HAVING filters groups after aggregation and can use aggregate functions.
Q: What is a primary key vs a unique key?
A: Both enforce uniqueness. The primary key is one per table and never NULL; unique keys can be many and accept NULLs.
Q: What is a foreign key?
A: A column referencing another table's key; the database rejects values without a matching parent and applies ON DELETE / ON UPDATE actions.
Q: Explain the different joins.
A: INNER keeps matches, LEFT and RIGHT keep all rows from one side, FULL keeps all from both, CROSS forms every combination, and a self join joins a table to itself.
Q: UNION vs UNION ALL?
A: UNION removes duplicate rows; UNION ALL keeps all rows and is faster.
Q: What is a subquery and a correlated subquery?
A: A subquery is a query nested in another. A correlated subquery references the outer query's columns, so it is evaluated per outer row.
Q: What is a CTE?
A: A named temporary result set defined with WITH for one statement, used for readability, reuse and recursion.
Q: ROW_NUMBER vs RANK vs DENSE_RANK?
A: ROW_NUMBER is unique per row; RANK shares ranks for ties and leaves gaps; DENSE_RANK shares ranks without gaps.
Q: How do you find the second highest salary?
A: `SELECT MAX(salary) FROM t WHERE salary < (SELECT MAX(salary) FROM t)`, or DENSE_RANK = 2, or DISTINCT with LIMIT 1 OFFSET 1 wrapped to return NULL.
Q: How do you find and delete duplicate rows?
A: Find with GROUP BY ... HAVING COUNT(*) > 1. Delete with ROW_NUMBER() OVER (PARTITION BY the duplicate columns ORDER BY id) and remove rows numbered above 1, or a self join on the duplicate columns with a lower id.
Q: What is normalisation? Name the normal forms.
A: Structuring tables to remove redundancy and anomalies: 1NF (atomic values), 2NF (no partial dependency), 3NF (no transitive dependency), BCNF (every determinant is a candidate key).
Q: What is an index? Clustered vs non-clustered?
A: A structure that speeds up lookups at the cost of slower writes. A clustered index stores the table rows in key order (one per table); a non-clustered index is separate and points to rows (many per table).
Q: What are ACID properties?
A: Atomicity, Consistency, Isolation and Durability: the guarantees a transaction gives.
Q: What are the transaction isolation levels?
A: READ UNCOMMITTED, READ COMMITTED, REPEATABLE READ and SERIALIZABLE, which progressively prevent dirty reads, non-repeatable reads and phantoms.
Q: What is a view? A stored procedure? A trigger?
A: A view is a saved query used like a table. A stored procedure is named server-side logic called with CALL or EXEC. A trigger is logic that runs automatically on INSERT, UPDATE or DELETE.
Q: SQL vs MySQL vs SQL Server?
A: SQL is the language. MySQL (Oracle, open source) and SQL Server (Microsoft, T-SQL) are database products that implement it with their own dialects.
Q: MySQL vs PostgreSQL in one sentence?
A: MySQL is simpler and very common for read-heavy web apps; PostgreSQL is more standards-compliant and extensible, with richer types, indexes and transactional DDL.
Q: How do you optimise a slow query?
A: Measure with EXPLAIN ANALYZE, add the right (composite or covering) indexes, make predicates sargable, fetch fewer rows and columns, fix N+1 patterns and keep statistics fresh.
Q: What is SQL injection and how do you prevent it?
A: Attacker input concatenated into SQL changes the query (for example `' OR '1'='1`). Prevent it with parameterised queries / prepared statements (or an ORM that uses them), input validation and least-privilege database accounts. Never build SQL by string concatenation.
Q: What is the difference between CHAR and VARCHAR?
A: CHAR is fixed length and padded; VARCHAR stores only the actual characters up to the limit.
Q: Can you use an aggregate without GROUP BY?
A: Yes. The whole table (after WHERE) becomes one group and the query returns one row.
Q: What is a self-referencing foreign key used for?
A: Hierarchies such as employee → manager or category → parent category, usually queried with self joins or recursive CTEs.
Q: What is a composite key?
A: A key made of two or more columns, such as (order_id, product_id) in an order-items table.
Q: Partitioning vs sharding vs replication?
A: Partitioning splits a table within one server, sharding splits data across servers, and replication copies the same data to several servers.
