# 01 | CI/CD Interview Cheat Sheet | Concepts, pipeline stages, GitHub Actions, Jenkins, deployment strategies and secrets. | CI/CD on one page

### Concepts

## CI vs Continuous Delivery vs Deployment
> **CI:** merge small changes often; every push is built and tested automatically. **Continuous Delivery:** every passing build is *releasable*, deploy is a manual click. **Continuous Deployment:** every passing build goes to production automatically.
- Goals: fast feedback, fewer integration surprises, repeatable releases.
! Delivery = ready to ship; Deployment = shipped.

## Typical Pipeline
```text
commit -> build -> unit tests -> static analysis / security scan -> package (jar/image)
       -> publish artifact -> deploy to staging -> integration/e2e tests -> approve -> deploy to prod -> monitor
```
- Fail fast: cheap checks first. Build **once**, promote the same artifact through environments.
! Build once, deploy many.

### Tools

## GitHub Actions
```yaml
name: ci
on: { push: { branches: [main] }, pull_request: {} }
jobs:
  build:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-java@v4
        with: { distribution: temurin, java-version: 21, cache: maven }
      - run: mvn -B verify
      - uses: docker/build-push-action@v6
        if: github.ref == 'refs/heads/main'
        with: { push: true, tags: ghcr.io/${{ github.repository }}:${{ github.sha }} }
```
- Concepts: **workflow** (YAML in `.github/workflows`), **event**, **job** (runs on a runner), **step**, **action**, **matrix**, **secrets**, **environments** with approvals, caching.
! Event triggers a workflow; workflow has jobs; jobs have steps.

## Jenkins
```groovy
pipeline {
  agent any
  stages {
    stage('Build') { steps { sh 'mvn -B clean package' } }
    stage('Test')  { steps { sh 'mvn test' } post { always { junit 'target/surefire-reports/*.xml' } } }
    stage('Deploy'){ when { branch 'main' } steps { sh './deploy.sh' } }
  }
}
```
- **Jenkinsfile** (pipeline as code), controller + agents, plugins, credentials store. Declarative vs scripted pipelines.
! Keep the pipeline in the repo, not in the UI.

## Vercel / Render / Cloud Deploys
- **Vercel:** Git push gives preview deploys per PR and production on main (great for Next.js). **Render:** web services, workers, cron, managed Postgres from a repo. Environment variables set per environment.
! Preview deploys per PR speed up reviews.

### Delivery

## Deployment Strategies
- **Rolling:** replace instances gradually. **Blue/green:** two environments, switch traffic instantly, instant rollback. **Canary:** send a small % to the new version first. **Feature flags:** deploy code dark, release by toggle.
- Always have a **rollback** plan and **health checks**.
! Canary limits blast radius; blue/green limits downtime.

## Secrets & Security in Pipelines
- Store secrets in the CI secret store or a vault, never in the repo; least-privilege tokens; prefer short-lived **OIDC** credentials to cloud. Scan dependencies (Dependabot, Snyk), images (Trivy), code (SAST), secrets (gitleaks). Pin action versions.
! A leaked CI secret is a production breach.

## Pipeline Best Practices
- Fast (under ~10 min), deterministic, cache dependencies, run tests in parallel, **branch protection** requiring green checks and reviews, version artifacts with the commit SHA, notify on failure, infrastructure as code (Terraform).
! A flaky test is a bug in the pipeline; fix or quarantine it.

### More CI/CD

## Matrix, Caching, Reusable Workflows & IaC
```yaml
strategy: { matrix: { java: [17, 21], os: [ubuntu-latest, windows-latest] } }
- uses: actions/cache@v4
  with: { path: ~/.m2, key: m2-${{ hashFiles('**/pom.xml') }} }
```
- **Reusable workflows** (`workflow_call`), **environments** with required reviewers, **Terraform** `plan` in PRs and `apply` on merge, DORA metrics (deploy frequency, lead time, change-failure rate, recovery time), **GitOps** (Argo CD syncs the cluster from git).
! Cache by the lock-file hash.

### Must-Know Questions

## CI/CD Questions
Q*: Difference between Continuous Delivery and Continuous Deployment?
A: Delivery keeps every build ready to release with a manual approval; Deployment releases every passing build automatically.
Q*: How do you do zero-downtime deployment?
A: Rolling updates with readiness checks, or blue/green with a traffic switch, plus backward-compatible DB migrations.
Q*: How do you handle secrets in a pipeline?
A: Use the CI secret store or a vault, inject at runtime, never commit them, rotate regularly and prefer OIDC.
Q*: How do you roll back a bad release?
A: Redeploy the previous artifact version (immutable, tagged), switch blue/green back, or turn off the feature flag.
Q: What is a pipeline as code?
A: Defining the pipeline in a versioned file (Jenkinsfile, workflow YAML) alongside the application code.
Q: Why build the artifact once?
A: So the exact thing tested in staging is what runs in production.
