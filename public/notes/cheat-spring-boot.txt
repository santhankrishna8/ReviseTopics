# 01 | Spring Boot Interview Cheat Sheet | Every card: a crisp definition you can say out loud, a concrete example, the key points, and a hook to remember it. Spring Boot 4 (current) with the Boot 3 names interviewers still use. | Spring Boot on one page

### Spring Core

## Spring vs Spring Boot
> **Spring Framework** is the core platform for Java apps: dependency injection, AOP, MVC, data access, transactions. **Spring Boot** is built on Spring and removes setup work with **auto-configuration**, **starters** and an **embedded server**, so an app runs with `java -jar`.
- **Without Boot:** configure the DispatcherServlet, data source, Jackson, and deploy a WAR to Tomcat yourself.
- **With Boot:** add `spring-boot-starter-web`, write a controller, run `main()`.
! Spring = the engine; Spring Boot = the car with the engine already installed.

## Inversion of Control (IoC)
> **IoC** means the **framework controls object creation and wiring**, not your code. The **Spring container (IoC container)** creates objects (**beans**), injects their dependencies and manages their lifecycle.
- **Without IoC:** `OrderService service = new OrderService(new OrderRepository());`
- **With IoC:** Spring creates both and hands `OrderRepository` to `OrderService` automatically.
! Hollywood principle: "Don't call us, we'll call you."

## Dependency Injection
> **Dependency Injection (DI)** is how IoC is done: a class **receives** the objects it needs (dependencies) from the container instead of creating them.
```java
@Service
class OrderService {
  private final PaymentClient payments;
  OrderService(PaymentClient payments) {   // constructor injection (recommended)
    this.payments = payments;
  }
}
```
- **Types:** constructor (best: required, immutable, easy to test), setter (optional dependencies), field `@Autowired` (short but hides dependencies, hard to test).
- With a single constructor, `@Autowired` isn't needed.
! DI = the restaurant brings the ingredients; you just cook.

## Bean
> A **bean** is any object **created and managed by the Spring container**. You declare beans with stereotype annotations (`@Component`, `@Service`...) or `@Bean` methods.
- **Example:** `@Service class OrderService`: Spring creates one `OrderService` at startup and injects it wherever it is needed.
- The container is the **ApplicationContext**; by default each bean is a **singleton** (one shared instance).
! A bean is an object Spring adopted: it creates it, feeds it, and cleans up after it.

## BeanFactory vs ApplicationContext
> **BeanFactory** is the basic container: it creates beans **lazily** (on first request). **ApplicationContext** extends it with enterprise features: **eager** singleton creation at startup, events, internationalisation, AOP integration, environment/profiles. Spring Boot always uses an ApplicationContext.
- **Example:** a misconfigured singleton fails **at startup** with ApplicationContext (eager), but only when first requested with a plain BeanFactory.
! BeanFactory = a basic toolbox; ApplicationContext = the full workshop.

## @Component vs @Service vs @Repository vs @Controller
> All mark a class as a Spring bean found by **component scanning**; the names describe the **layer** and add small extras.
```text
@Component       generic bean
@Service         business logic layer
@Repository      data layer + converts DB exceptions to Spring's DataAccessException
@Controller      web layer, returns views (HTML)
@RestController  @Controller + @ResponseBody: returns JSON
```
! Same badge, different department name.

## @Component vs @Bean
> **@Component** goes on **your own class** and Spring finds it by scanning. **@Bean** goes on a **method** inside a `@Configuration` class and is used for objects you can't annotate (third-party classes) or that need custom setup.
```java
@Configuration
class AppConfig {
  @Bean
  Clock clock() { return Clock.systemUTC(); }   // a JDK class you can't annotate, exposed as a bean
}
```
! @Component = "I am a bean"; @Bean = "here is how to make a bean".

## Bean Scopes
> A **scope** decides how many instances of a bean exist: **singleton** (default, one per container), **prototype** (new instance each time it's requested), and web scopes **request**, **session**, **application**.
- **Example:** `@Scope("prototype") class ReportBuilder` gives each caller a fresh builder; a `@RequestScope` bean holds the current request's user.
- Singletons are shared by all threads, so keep them **stateless** (no request-specific fields).
! Singleton = the office printer everyone shares; prototype = a new notepad for each person.

## Bean Lifecycle
> Spring **creates** the bean → **injects** dependencies → calls `@PostConstruct` (initialise) → bean is **in use** → on shutdown calls `@PreDestroy` (cleanup).
```java
@Component
class CacheLoader {
  @PostConstruct void load() { System.out.println("warming cache"); }
  @PreDestroy void close() { System.out.println("releasing resources"); }
}
```
! Born, given tools, warms up, works, cleans up before leaving.

## @Qualifier & @Primary
> When **two beans of the same type** exist, Spring doesn't know which to inject. **@Primary** marks the default one; **@Qualifier("name")** picks a specific one at the injection point.
- **Example:** `EmailNotifier` and `SmsNotifier` both implement `Notifier`: mark email `@Primary`, inject `@Qualifier("smsNotifier") Notifier` where SMS is needed.
! @Primary = the default choice; @Qualifier = asking for one by name.

## AOP (Aspect-Oriented Programming)
> **AOP** adds common behaviour (logging, security, transactions) **around** methods without changing their code. An **aspect** holds the logic, **advice** says when it runs (`@Before`, `@After`, `@Around`), a **pointcut** says which methods.
- **Example:** an `@Around("execution(* com.shop.service.*.*(..))")` aspect logs how long every service method takes, without touching the services.
- Spring's `@Transactional`, `@Cacheable` and `@Async` work through AOP **proxies**.
- **Self-invocation trap:** calling a `@Transactional` method from another method **in the same class** bypasses the proxy, so no transaction starts.
! AOP = a security guard placed around every door, without rebuilding the doors.

### Spring Boot Basics

## Auto-Configuration
> **Auto-configuration** means Spring Boot **creates beans automatically** based on what's on the classpath and in your properties: add a database driver and you get a `DataSource`; add Spring Web and you get an embedded Tomcat.
- **Example:** add `spring-boot-starter-data-jpa` + the MySQL driver + `spring.datasource.url`, and Boot creates the DataSource, EntityManager and transaction manager for you.
- It's conditional (`@ConditionalOnClass`, `@ConditionalOnMissingBean`), so **your own beans always win**.
- See what was applied: run with `--debug`.
! Boot looks in your bag (classpath) and sets up the tools it finds.

## Starters
> **Starters** are dependency bundles that bring everything needed for a feature, with compatible versions.
```text
spring-boot-starter-web (Boot 4: -webmvc)  REST APIs + Tomcat + Jackson
spring-boot-starter-data-jpa               JPA + Hibernate + connection pool
spring-boot-starter-security               Spring Security
spring-boot-starter-validation             Bean Validation
spring-boot-starter-test                   JUnit 5, Mockito, AssertJ
spring-boot-starter-actuator               health, metrics endpoints
```
! One starter = one ready-made meal kit.

## @SpringBootApplication
> **@SpringBootApplication** on the main class combines three annotations: **@Configuration** (can define beans), **@EnableAutoConfiguration** (turn on auto-config) and **@ComponentScan** (find beans in this package and below).
```java
@SpringBootApplication
public class ShopApplication {
  public static void main(String[] args) {
    SpringApplication.run(ShopApplication.class, args);   // starts the context + embedded server
  }
}
```
- Keep this class in the **root package**, otherwise beans in sibling packages won't be found.
! One annotation = config + auto-config + scan.

## Embedded Server
> Spring Boot runs with an **embedded web server** (Tomcat by default, Jetty optional; Boot 4 dropped Undertow) inside the app, so you run a **fat JAR** with `java -jar app.jar` instead of deploying a WAR to an external server.
- **Example:** `java -jar shop.jar` starts Tomcat on port 8080 inside the app; no separate server install.
- Change the port with `server.port=9090`.
! The server travels inside the app, like a food truck instead of renting a restaurant.

### Configuration

## application.properties / application.yml
> Spring Boot reads settings from `application.properties` or `application.yml`: server port, database URL, logging levels and your own custom values.
```yaml application.yml
server:
  port: 8080
spring:
  datasource:
    url: jdbc:mysql://localhost:3306/shop
    username: app
    password: ${DB_PASSWORD}     # from an environment variable
logging.level.com.shop: DEBUG
```
! One settings file instead of settings scattered through code.

## Profiles
> **Profiles** let you keep different settings per environment (dev, test, prod): `application-dev.yml`, `application-prod.yml`, activated with `spring.profiles.active=prod`.
- `@Profile("dev")` creates a bean only in that profile (e.g. a fake payment client in dev).
- Precedence: command-line arguments > environment variables > profile files > `application.yml`.
! Same app, different outfit for each environment.

## @Value vs @ConfigurationProperties
> **@Value** injects a **single** property; **@ConfigurationProperties** binds a **group** of properties into a typed class (validated, IDE autocomplete).
```java
@ConfigurationProperties(prefix = "app.mail")
record MailProperties(String host, int port) {}       // app.mail.host, app.mail.port

@Component
class Greeter {
  Greeter(@Value("${app.greeting:Hello}") String greeting) {}   // default after ':'
}
```
! @Value = pick one item; @ConfigurationProperties = take the whole labelled box.

### REST APIs

## Building a REST Controller
> A **@RestController** maps HTTP requests to Java methods and returns objects converted to **JSON** (by Jackson).
```java
@RestController
@RequestMapping("/api/products")
class ProductController {
  @GetMapping("/{id}")
  Product get(@PathVariable Long id) { return new Product(id, "Pen", 10); }

  @PostMapping
  ResponseEntity<Product> create(@RequestBody Product p) {
    return ResponseEntity.status(HttpStatus.CREATED).body(p);   // 201
  }
}
record Product(Long id, String name, double price) {}
```
- Mapping annotations: `@GetMapping`, `@PostMapping`, `@PutMapping`, `@PatchMapping`, `@DeleteMapping`.
! URL + HTTP method in, Java method runs, JSON out.

## @PathVariable vs @RequestParam vs @RequestBody
> **@PathVariable** reads a value from the URL path (`/products/42`); **@RequestParam** reads a query parameter (`/products?page=2`); **@RequestBody** reads the JSON body into an object.
- **Example:** `GET /orders/7?expand=items` → `@PathVariable Long id` = 7, `@RequestParam String expand` = "items".
! Path = which item, param = how you want it, body = the data you're sending.

## ResponseEntity
> **ResponseEntity** lets you control the full HTTP response: **status code**, **headers** and **body**.
- `ResponseEntity.ok(product)` (200) · `ResponseEntity.notFound().build()` (404) · `ResponseEntity.status(HttpStatus.CREATED).body(p)` (201).
! ResponseEntity = the whole envelope, not just the letter.

## HTTP Methods & Status Codes
> **HTTP methods** say what to do with a resource; **status codes** say how it went.
```text
GET read · POST create · PUT replace · PATCH update part · DELETE remove
Idempotent (same result if repeated): GET, PUT, DELETE  — not POST
200 OK · 201 Created · 204 No Content
400 Bad Request · 401 Unauthorized (not logged in) · 403 Forbidden (no permission)
404 Not Found · 409 Conflict · 500 Server Error · 503 Unavailable
```
! 2xx = success, 4xx = your (client's) fault, 5xx = server's fault.

### Validation & Errors

## Bean Validation
> **Bean Validation** checks request data with annotations; add `@Valid` on the request body and Spring returns **400 Bad Request** automatically if a rule fails.
```java
record CreateUser(
    @NotBlank String name,
    @Email String email,
    @Min(18) int age) {}

// in a controller: create(@Valid @RequestBody CreateUser user)
```
- Common: `@NotNull`, `@NotBlank`, `@Size(min, max)`, `@Min`, `@Max`, `@Email`, `@Pattern`, `@Past`, `@Positive`.
! Annotations are the rules; @Valid is the referee who checks them.

## Global Exception Handling
> **@RestControllerAdvice** with **@ExceptionHandler** methods handles exceptions from **all controllers** in one place and returns a clean error response.
```java
class ProductNotFoundException extends RuntimeException {
  ProductNotFoundException(Long id) { super("Product " + id + " not found"); }
}
@RestControllerAdvice
class GlobalErrors {
  @ExceptionHandler(ProductNotFoundException.class)
  ResponseEntity<String> notFound(ProductNotFoundException ex) {
    return ResponseEntity.status(HttpStatus.NOT_FOUND).body(ex.getMessage());   // 404
  }
}
```
- Boot also supports **ProblemDetail** (a standard JSON error format: `type`, `title`, `status`, `detail`).
! One complaints desk for the whole company instead of one per room.

### Data Access (JPA)

## JPA vs Hibernate vs Spring Data JPA
> **JPA** is the Java **specification** (rules) for mapping objects to database tables. **Hibernate** is the most popular **implementation** of JPA (the ORM). **Spring Data JPA** sits on top and **generates repository code** for you.
- **Example:** `productRepository.save(p)`: Spring Data calls JPA's `persist`, and Hibernate generates `INSERT INTO products ...`.
- **ORM (Object-Relational Mapping):** work with Java objects; the framework writes the SQL.
! JPA = the rulebook, Hibernate = the player, Spring Data = the coach who does the paperwork.

## Entity
> An **entity** is a Java class mapped to a database table with `@Entity`; each object is one row.
```java
@Entity
@Table(name = "products")
class ProductEntity {
  @Id @GeneratedValue(strategy = GenerationType.IDENTITY)   // auto-increment primary key
  Long id;
  @Column(nullable = false) String name;
  double price;
}
```
! Class = table, field = column, object = row.

## Repositories
> A **repository** is an interface extending `JpaRepository<Entity, IdType>`; Spring generates the implementation, including CRUD methods and queries derived from method names.
```java
interface ProductRepository extends JpaRepository<ProductEntity, Long> {
  List<ProductEntity> findByNameContainingIgnoreCase(String part);   // derived query
  @Query("select p from ProductEntity p where p.price > :min")
  List<ProductEntity> expensive(@Param("min") double min);           // custom JPQL
}
```
- Built in: `save`, `findById`, `findAll`, `deleteById`, `count`, `existsById`, paging with `Pageable`.
- **CrudRepository vs JpaRepository:** basic CRUD vs CRUD + paging, sorting, flush and batch operations.
! You write the method name; Spring writes the SQL.

## Entity Relationships
> Relationships map foreign keys: `@OneToOne`, `@OneToMany` / `@ManyToOne` (customer has many orders), `@ManyToMany` (students and courses, via a join table).
- **Example:** `@ManyToOne Customer customer;` in `Order` and `@OneToMany(mappedBy = "customer") List<Order> orders;` in `Customer`.
- `mappedBy` marks the non-owning side; the **owning side** (usually `@ManyToOne`) holds the foreign key.
- **Cascade** passes operations from parent to children (save an order → save its items).
! The "many" side holds the key, like each order holding its customer's ID.

## Lazy vs Eager Loading & N+1 Problem
> **Lazy loading** fetches related data only when you access it; **eager loading** fetches it immediately with the parent. Collections are lazy by default.
- **N+1 problem:** 1 query loads N orders, then N more queries load each order's customer = N+1 queries.
- **Fixes:** `JOIN FETCH` in JPQL, `@EntityGraph`, batch fetching, or DTO projections.
- **LazyInitializationException:** touching a lazy field after the transaction (session) is closed.
! N+1 = going to the shop once per item instead of once with a list.

## @Transactional
> **@Transactional** runs a method inside a **database transaction**: everything commits together, or everything **rolls back** if a runtime exception is thrown.
```java
@Service
class TransferService {
  @Transactional
  public void transfer(long from, long to, double amount) {
    // debit(from) and credit(to): both succeed or both are undone
  }
}
```
- Rolls back on **unchecked** exceptions by default (`rollbackFor = Exception.class` for checked ones).
- **Propagation:** `REQUIRED` (default: join the current transaction or start one), `REQUIRES_NEW` (always a separate new one).
- Doesn't work on `private` methods or calls from inside the same class (proxy is bypassed).
! All or nothing, like a bank transfer.

### Security

## Spring Security
> **Spring Security** protects the app with a chain of **filters** that handle **authentication** (who are you?) and **authorization** (what can you do?).
```java
@Configuration
class SecurityConfig {
  @Bean
  SecurityFilterChain security(HttpSecurity http) throws Exception {
    return http
        .authorizeHttpRequests(auth -> auth
            .requestMatchers("/public/**").permitAll()
            .requestMatchers("/admin/**").hasRole("ADMIN")
            .anyRequest().authenticated())
        .httpBasic(Customizer.withDefaults())
        .build();
  }
  @Bean
  PasswordEncoder passwordEncoder() { return new BCryptPasswordEncoder(); }   // store hashes only
}
```
- Passwords are stored **hashed** with `BCryptPasswordEncoder`. Method level: `@PreAuthorize("hasRole('ADMIN')")`.
- **401** = not authenticated; **403** = authenticated but not allowed.
! Authentication = showing your ID card; authorization = which doors that card opens.

## JWT Authentication
> A **JWT (JSON Web Token)** is a signed token (`header.payload.signature`) the server gives after login; the client sends it in every request (`Authorization: Bearer <token>`) and the server verifies the signature, without storing a session.
- **Example:** login returns `eyJhbGciOi...`; the next call `GET /api/orders` sends `Authorization: Bearer eyJhbGciOi...`.
- **Stateless:** scales across many servers and microservices. **Downside:** hard to revoke before it expires (use short expiry + refresh tokens).
- **Session vs JWT:** the server remembers you (session cookie) vs you carry proof (token).
! JWT = a signed boarding pass: the gate checks the signature, not a passenger list.

## CORS & CSRF
> **CORS** is a browser rule that blocks calls to a **different origin** unless the server allows it (configure `allowedOrigins`). **CSRF** is an attack that tricks a logged-in browser into sending unwanted requests using its cookies.
- **Example:** an Angular app on `localhost:4200` calling an API on `localhost:8080` needs the API to allow the origin `http://localhost:4200`.
- Keep CSRF protection for cookie/session apps; it's usually disabled for **stateless JWT** APIs.
! CORS = "may this website call me?"; CSRF = "did the user really mean to send this?".

### Testing

## Testing in Spring Boot
> Spring Boot tests use **JUnit 5**, **Mockito** and **AssertJ**, with test "slices" that load only the part of the app being tested.
```text
Plain unit test + Mockito   service logic, no Spring (fastest)
@WebMvcTest                 controllers only, with MockMvc
@DataJpaTest                repositories with an in-memory DB
@SpringBootTest             the whole application (integration test)
```
- `@Mock` = plain Mockito mock; `@MockitoBean` (formerly `@MockBean`) = replaces a bean inside the Spring context.
! Test the brick alone first, then the wall, then the house.

## Unit Test with Mockito
> **Mockito** creates **fake dependencies** (mocks) so you can test one class in isolation and control what its dependencies return.
```java
@ExtendWith(MockitoExtension.class)
class PriceServiceTest {
  @Mock TaxClient tax;
  @InjectMocks PriceService service;

  @Test
  void addsTax() {
    when(tax.rate()).thenReturn(0.18);                  // stub
    assertThat(service.withTax(100)).isEqualTo(118.0);
    verify(tax).rate();                                 // was it called?
  }
}
interface TaxClient { double rate(); }
class PriceService {
  private final TaxClient tax;
  PriceService(TaxClient tax) { this.tax = tax; }
  double withTax(double price) { return price + price * tax.rate(); }
}
```
! A mock is a stunt double: it does exactly what the script (when/thenReturn) says.

### Production Features

## Actuator
> **Spring Boot Actuator** adds production endpoints to monitor and manage the app: `/actuator/health`, `/actuator/info`, `/actuator/metrics`, `/actuator/prometheus`, `/actuator/loggers`.
- **Example:** `GET /actuator/health` → `{"status":"UP"}`; a load balancer stops sending traffic when it turns `DOWN`.
- Only `health` is exposed by default: `management.endpoints.web.exposure.include=health,info,metrics`.
- Kubernetes uses `/actuator/health/liveness` and `/readiness` probes.
! Actuator = the car's dashboard: speed, fuel, warning lights.

## Logging
> Spring Boot uses **SLF4J** with **Logback** by default; set levels per package with `logging.level.com.shop=DEBUG`.
- Levels: TRACE < DEBUG < INFO < WARN < ERROR.
- Use placeholders: `log.info("Order {} placed", orderId)`; never log passwords or tokens.
! Log like a black box recorder: enough to explain the crash, nothing secret.

## Caching, Async & Scheduling
> **@Cacheable** stores a method's result so repeated calls skip the work; **@Async** runs a method in a background thread; **@Scheduled** runs a method on a timer or cron.
- Enable with `@EnableCaching`, `@EnableAsync`, `@EnableScheduling`.
- **Example:** `@Cacheable("products")` on `findById`; `@Scheduled(cron = "0 0 2 * * *")` for a nightly report.
! Cache = remember the answer; Async = do it later; Scheduled = do it on time.

### Microservices

## Monolith vs Microservices
> A **monolith** is one application deployed as a single unit. **Microservices** split the system into small, **independently deployable services**, each owning one business capability and its own database.
```text
             monolith                 microservices
deploy       all together             each service alone
scale        whole app                only the busy service
tech         one stack                each service can differ
complexity   simple to start          network, data, ops overhead
```
- **Example:** an e-commerce app split into User, Product, Order and Payment services.
! Monolith = one big restaurant kitchen; microservices = a food court of specialised stalls.

## Microservice Building Blocks
> Microservices need shared infrastructure to **route, find, configure, balance and connect** each other.
- **API Gateway:** single entry point that routes requests, handles auth, rate limiting (Spring Cloud Gateway).
- **Service Discovery:** services register and find each other by name (Eureka; DNS in Kubernetes).
- **Config Server:** central configuration for all services (Spring Cloud Config).
- **Load Balancer:** spreads calls across instances (Spring Cloud LoadBalancer).
- **Communication:** synchronous REST (`RestClient`, OpenFeign) or asynchronous messaging (**Kafka**, RabbitMQ).
! Gateway = reception desk, discovery = phone book, config server = shared rulebook.

## Circuit Breaker
> A **circuit breaker** stops calling a service that keeps failing, returns a **fallback** immediately, and retries later, preventing one failure from bringing down the whole system (cascading failure).
- **Example:** Inventory is down: after 5 failures the breaker opens and Order service returns "stock unknown" instantly instead of waiting 30 seconds per call.
- States: **Closed** (normal) → **Open** (too many failures, calls blocked) → **Half-Open** (a few test calls) → Closed again if they succeed.
- Implemented with **Resilience4j** (`@CircuitBreaker(name = "inventory", fallbackMethod = "fallback")`), often with retry and timeout.
! Like a home electrical breaker: trips to protect the house, then you reset it.

## Distributed Transactions: Saga Pattern
> A **Saga** manages a business transaction across several services as a **sequence of local transactions**; if a step fails, **compensating actions** undo the previous steps.
- **Example:** Order created → Payment charged → Inventory reserved fails → refund payment → cancel order.
- **Choreography:** services react to each other's events (Kafka). **Orchestration:** a central coordinator tells each service what to do.
- **Outbox pattern:** save the event in the same database transaction as the data, then publish it, so events are never lost.
! A saga is a chain of promises, each with an "undo" plan.

## Kafka Basics
> **Apache Kafka** is a distributed **event streaming platform**: producers write messages to **topics**, consumers read them; messages are stored durably and can be replayed.
- **Example:** Order service publishes `OrderPlaced`; Email, Inventory and Analytics services each consume it independently.
- **Topic** split into **partitions** (parallelism; order guaranteed within a partition). **Consumer group:** each partition is read by one consumer in the group.
- Spring: `KafkaTemplate.send("orders", order)` and `@KafkaListener(topics = "orders")`.
! Kafka = a durable conveyor belt of events that many teams can read at their own pace.

### Quick Answers

## Interview One-Liners
- **Spring vs Spring Boot:** framework vs ready-to-run, auto-configured Spring.
- **IoC / DI:** the container creates objects and injects what they need.
- **@Component vs @Bean:** annotate your class vs factory method for any object.
- **@Controller vs @RestController:** returns views vs returns JSON.
- **@PathVariable vs @RequestParam:** part of the URL path vs `?key=value`.
- **@Transactional:** all-or-nothing; rolls back on runtime exceptions.
- **Lazy vs eager:** load related data when used vs immediately.
- **N+1 problem:** one query per row; fix with JOIN FETCH / EntityGraph.
- **401 vs 403:** not logged in vs not allowed.
- **Monolith vs microservices:** one deployable vs many independent services.
- **Circuit breaker:** stop calling a failing service, use a fallback, retry later.
